# API Contracts

Every endpoint in `apps/api` is recorded here in the same task that adds it:
method, path, request shape, response shape, auth, error cases.

**Status:** Epic 9.17 complete — 54 paths, 64 operations.
No endpoint was added or removed in 9.17; `POST /clients/{clientId}/scans`
changed what it *does*. **2026-09-30:** share, invite and reset links moved
to fragment form; `GET /reports/{token}` and `GET /reports/{token}.pdf` replaced
by `POST /reports/shared` and `POST /reports/shared/pdf` with the token in the
body. The path and operation counts are unchanged.
**Machine-readable source of truth:** `packages/shared-types/openapi.json`,
generated by `apps/api/scripts/export_openapi.py`. This document explains
intent; the schema defines the shapes.

## Conventions (set in Epic 0, applied from Epic 1)

- Base path: `/api/v1`
- Content type: `application/json; charset=utf-8`
- Casing: `camelCase` in JSON bodies, `kebab-case` in path segments.
- IDs: prefixed ULIDs (e.g. `scan_01J...`) so an ID is self-describing in logs.
- Errors: RFC 9457 `application/problem+json` — `{ type, title, status, detail, instance }`.
- Pagination: cursor-based — `?limit=&cursor=`, response `{ data: [], nextCursor: string | null }`.
- Timestamps: RFC 3339 UTC strings.
- Logs (2026-09-29): structlog is configured once, in `create_app`
  (`avp_api/logs.py`). `LOG_LEVEL` wins when set; otherwise INFO on staging and
  production and DEBUG everywhere else. uvicorn's access log is kept with the
  query string dropped from `/auth/google/callback` (Google's `code` and `state`) and any stale `/auth/google/pending`,
  and all query strings under `/reports/` redacted. No log line carries a token,
  a link that carries one, or an email address. Since 2026-09-30, share tokens
  travel in request bodies (`POST /reports/shared` and `/reports/shared/pdf`),
  never in the path. Since 2026-10-02 the API also logs its own memory, as
  numbers and our own ids only (`app.memory_at_start`, `scan.phase_memory`,
  `browser.memory`, `browser.slot_waited`, `browser.slot_busy`; the three about
  the browser carry `scan_id` or `client_id`); `docs/runbook.md`, "Reading the
  API's memory", says what each carries.
- Security headers (2026-10-03, checklist 3.1): every API response, an error or
  a CORS preflight included, carries six headers, added by
  `avp_api/security_headers.py` unless the response already set that header
  itself: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Content-Security-Policy: frame-ancestors 'none'`,
  `Referrer-Policy: no-referrer`,
  `Strict-Transport-Security: max-age=63072000; includeSubDomains` and
  `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), browsing-topics=()`.
  The one response without them is an unhandled-exception 500, which Starlette
  builds outside every middleware.
  The web app sends its own set on every page except the proxied `/api/v1`
  paths, where a browser gets the API's set, once (`apps/web/next.config.mjs`).

### Authentication

An **httpOnly session cookie**, not a bearer token. Deployed it is named
`__Host-avp_session` with the default `SESSION_COOKIE_NAME` (`avp_session` on
local http), `Secure`, `SameSite=Lax`, `Path=/`, with no `Domain`. It is
first-party: the web app serves this API under its own origin at `/api/v1`, so
every call the web app makes is same-origin. The one cross-site step is
Google's redirect back to the sign-in callback, a top-level navigation, which
is why the cookie is `Lax` and not `Strict`.
Below, "the session cookie" means that cookie.

Chosen because this is seat-based software: when an agency removes a seat, that
person's access must end immediately. A JWT cannot be revoked without a
server-side blocklist consulted on every request — which is a session store
with extra steps. Consequences: `httpOnly` means XSS cannot read the cookie,
revocation is a `DEL`, and "sign out everywhere" is a set scan.

Sessions live in Redis; only the SHA-256 digest of the token is stored, so a
Redis dump does not yield working cookies. Every authenticated request re-reads
the user and agency from Postgres, so a suspended user or deleted agency loses
access on their *next* request.

Redis calls are bounded: connect and read each time out after 2 seconds
(`REDIS_CONNECT_TIMEOUT_SECONDS`, `REDIS_SOCKET_TIMEOUT_SECONDS`, both optional;
the workers read the same names). When Redis is down or too slow, any route that
touches it — sign-in, every authenticated request — answers `503
service-unavailable` (fail closed) within about that time, with no host, URL or
address in the body or the log.

Cross-origin callers must send `credentials: 'include'`, and the origin must be
listed in `CORS_ALLOW_ORIGINS` — browsers reject wildcard CORS with credentials.

**Writes need a listed `Origin` (2026-10-01).** A `POST`, `PUT`, `PATCH` or
`DELETE` that sends an `Origin` header must send one equal to a
`CORS_ALLOW_ORIGINS` entry, with or without the session cookie (list each origin
exactly, scheme and host with no trailing `/`, as CORS requires; `null` never
matches), so sign-in, sign-up, password
reset, invitation accept and Google sign-up complete are covered too. A write
that carries the session cookie must send a listed `Origin`; a missing one is
refused as well. A refusal is `403 origin-not-allowed`, answered before any route
runs, and nothing changes. Browsers send `Origin` on these requests themselves,
so the web app needs no change. Not checked: reads (`GET`), a write with neither
the session cookie nor an `Origin` (a server or command-line caller), and
`POST /billing/webhook` (that method and path only; a `PUT`, `PATCH` or `DELETE`
there is checked like any write), which Stripe signs instead. The refusal's log
line (`security.origin_refused`) carries the method, a redacted path,
`origin_present` and, when an `Origin` was sent, either `origin_host` (the
lower-cased DNS host name only) or `origin_kind` (`ip`, `opaque` or `unparsed`);
never the full header, a port, userinfo or an IP literal (a DNS name that
contains an address, such as `10-0-0-1.sslip.io`, is still a name and is logged).
Only a bare origin is read as a host; userinfo, a path, a query or a fragment
make it `unparsed`.

| `/problems/seat-limit-reached` | 409 | Carries `seatsUsed`, `seatLimit` |

| `/problems/checkout-in-progress` | 409 | Another checkout for the same agency holds its row lock for more than 3 s. Nothing was created; retry |
| `/problems/invalid-reset-token` | 400 | Reset link unknown, expired, used, or orphaned |
| `/problems/invalid-invitation` | 400 | Invitation unknown, expired, accepted, revoked, or orphaned |

| `/problems/billing-not-configured` | 503 | A Stripe setting is unset. `detail` names the variable |
| `/problems/plan-price-mismatch` | 503 | Checkout refused: the latest price check found the Stripe Price is not the plan (amount, currency, interval or archived) and a fresh read made for this request confirms it. `detail` is one plain sentence: "Subscribing is not available right now because the plan's price is not set up correctly. Please try again later." It names no amount, Price id or setting. Nothing is created at Stripe. The fresh read waits at most 10 s; a read that fails or takes longer never refuses |
| `/problems/google-sign-in-not-configured` | 503 | Google sign-in is not configured on this deployment |

| `/problems/subscription-required` | 402 | The route is for paying agencies and this agency is not one. ## Endpoints

### Health

#### `GET /api/v1/health`
Liveness. **No auth.** Touches no dependency deliberately — a liveness probe
that checks the database causes an orchestrator to restart healthy API pods
during a database blip, turning a partial outage into a total one.

```json
{ "status": "ok", "version": "0.1.0" }
```

#### `GET /api/v1/ready`
Readiness. **No auth.** Verifies Postgres and Redis. Returns `503` with
`status: "degraded"` if either is unreachable.

```json
{ "status": "ready", "checks": { "postgres": "ok", "redis": "ok" } }
```

### Auth

#### `POST /api/v1/auth/sign-up`
Create an agency and its first user, and sign them in. **No auth.**

The first user of an agency is always `owner` — an agency with no owner has
nobody who can manage seats. Signing in as part of signup is deliberate:
requiring a fresh login right after choosing a password is friction with no
security value.

**Request**
```json
{
  "agencyName": "Meridian Search Partners",
  "fullName": "Dana Whitfield",
  "email": "dana@meridiansearch.example",
  "password": "at least 12 characters"
}
```

Password rules follow NIST SP 800-63B: 12–256 characters, no composition
requirements. Composition rules push users toward predictable substitutions.
A password using fewer than 5 distinct characters is rejected.

**Response `201`** — body is `MeOut` (below). Sets the session cookie.

**Errors:** `429 rate-limited` (with `Retry-After` header in seconds; detail "Too many attempts. Try again in N minutes."; 5 per email and 10 per IP per hour, checked before the 409), `503 service-unavailable` (Redis down), `409 email-already-registered`, `422 validation-failed`.

#### `POST /api/v1/auth/login`
**No auth.**

```json
{ "email": "dana@meridiansearch.example", "password": "..." }
```

**Response `200`** — `MeOut`. Sets the session cookie.

**Errors:** `429 rate-limited` (with `Retry-After` header in seconds; detail "Too many attempts. Try again in N minutes."; 10 failed attempts per email and 30 per IP per 15 minutes; successful logins are given back), `503 service-unavailable` (Redis down), `401 invalid-credentials`.

Unknown email, wrong password, and suspended account all return an *identical*
response, and the unknown-email path performs a dummy Argon2 verification so
that response latency does not leak account existence.

#### `POST /api/v1/auth/logout`
**Auth required.** Revokes the current session only. **`204`, no body.**

#### `POST /api/v1/auth/logout-all`
**Auth required.** Revokes every session for the caller, on every device.
**`204`, no body.**

#### `POST /api/v1/auth/change-password`
**Auth required.** Change your own password while signed in — Epic 9.14.

**Recorded here as part of the work that built it.** This endpoint had no
contract anywhere before that epic: not built, and not in the "planned, not yet
built" table either. The house rule is that the shape is agreed before it is
implemented, so it is written here in the same form as every other Auth entry.

```json
{
  "currentPassword": "...",
  "newPassword": "at least 12 characters"
}
```

`newPassword` carries the SIGN-UP rules — the same `Password` annotated type
`sign-up`, `reset-password/confirm` and `invitations/accept` all use, imported
rather than restated. `currentPassword` deliberately does not: it is a
credential being *presented*, not set, and applying the length rule to it would
`422` on a password that predates a rule change and leak which submitted strings
are even eligible to be somebody's password.

**Response `200`** — `MeOut`. Sets a NEW session cookie.

**The current password is re-verified server-side even though the caller holds a
valid session.** A session proves somebody got in once; it does not prove they
are still the account holder. An unlocked laptop, a borrowed phone and a stolen
cookie all present a perfectly valid session, and without this check any of them
becomes permanent ownership of the account.

**Every OTHER session is revoked. This one is not.** That is deliberately not
`reset-password/confirm`'s answer copied across:

| | reset-confirm | change-password |
|---|---|---|
| What the caller proved | control of an inbox | knowledge of the current password |
| Other sessions | revoked | revoked |
| The caller's session | revoked; signed out | re-minted; stays signed in |

The reset flow signs the caller out because the person holding a link proved
control of a mailbox, not knowledge of a password — they may be recovering from
a compromise, they might not be the account holder at all, and one deliberate
sign-in confirms they hold the new password. Neither applies here: the caller has
just demonstrated the current password, so signing them out of the session they
are actively using is friction with no security value, the same argument
`sign-up` already makes.

The *other* sessions are a separate question with the same answer. The commonest
reason to change a password while signed in is believing somebody else has it,
and a change that left every other device alive would fail at the one job the
user thought they were doing. `logout-all` exists for the explicit version, but
requiring two deliberate actions to achieve the obvious intent of one is a trap.

The caller's token is **re-minted rather than spared**: "revoke everything except
this digest" is a special case inside the revocation path, and a bulk revoke with
an exception in it is the kind of code that later fails to revoke.

**On timing:** there is deliberately no dummy Argon2 hash here. `authenticate`
burns one on the unknown-email path because login latency would otherwise reveal
whether an address has an account. Nothing equivalent exists here — there is
exactly one user, the authenticated caller, and no branch depending on a fact
they do not already hold. A wrong current password does return faster, because
success goes on to hash the new password and write it; that tells an observer
only that a guess made against a session they already control was wrong, which
the `401` says outright. A test asserts the refusal still pays for a real Argon2
verification rather than short-circuiting.

**Errors:** `401 authentication-required` (no session), `401 invalid-credentials`
(wrong current password — no "no such user" branch exists, because the caller is
authenticated), `422 validation-failed` for a new password that fails the sign-up
rules **or** that is the current one. Reusing the current password is a
field-level `422` rather than a silent success: accepting it would revoke every
other session for a change that did not happen, and nobody could tell.

`429 rate-limited` (with `Retry-After` header in seconds; detail "Too many
attempts. Try again in N minutes."; 10 failed attempts per account and 30 per IP
per 15 minutes; successful changes are given back), `503 service-unavailable`
(Redis down). It is the login limit for the same reason: a stolen session cookie
must not become an unmetered oracle for the current password. The check runs
**before** the password is verified, so a limited request costs no Argon2, is
not a timing oracle and revokes no session. The account bucket is keyed on the
signed-in account's email (normalised, HMAC-hashed, never stored or logged in the
clear) on its own `rl:change_password:*` keys, separate from login's. An
unauthenticated request still gets `401` first. Optional settings, defaults
shown, nothing to set on Render: `CHANGE_PASSWORD_LIMIT_PER_EMAIL` (10),
`CHANGE_PASSWORD_LIMIT_PER_IP` (30), `CHANGE_PASSWORD_WINDOW_SECONDS` (900).
The per-account budget is separate from login's: a cookie holder gets at most 10
guesses per 15 minutes here, in addition to login's own, and this is chosen so a
stolen cookie cannot lock the victim out of login. `logout-all` (no password
needed) revokes a stolen session. A completed password reset also clears this
budget.

#### `POST /api/v1/auth/reset-password/request`
Ask for a reset link. **No auth.** Built in Epic 9.13; **recorded here in 9.14,
which is late** — the convention at the top of this file is that an endpoint is
recorded in the same task that adds it, and these two were not. Noted rather
than quietly backfilled.

```json
{ "email": "dana@meridiansearch.example" }
```

**Always `200`, and the same body for every address.** Which of two bodies
depends on the deployment — whether it can send email at all (2026-09-29):

```json
{
  "status": "accepted",
  "detail": "If that address has an account, a reset link is on its way. The link works once and expires in an hour.",
  "emailConfigured": true
}
```

```json
{
  "status": "accepted",
  "detail": "Password reset by email is not available on this service yet, so no link was sent.",
  "emailConfigured": false
}
```

**Byte-identical** whether the address has an account, has a suspended one, or
has never been seen. Any observable difference is an oracle for enumerating who
banks here — precisely what `login` already burns a dummy Argon2 hash to avoid.
Tests assert the identity in both modes, because a different sentence is as
good an oracle as a different status. `emailConfigured` is not such a
difference: it says whether `RESEND_API_KEY` is set, the same for every
address, and the web reads it so that it never says "check your email" when
nothing was sent.

Only the token's SHA-256 digest is stored, following `SessionStore`'s rule
rather than `Scan.share_token`'s: a reset token is minted, emailed once, and
never shown back, so nobody needs it read back and a table dump must yield
nothing. Requesting a second link retires the first.

With no `RESEND_API_KEY` nothing is sent, and nothing is logged in its place.
Until 2026-09-29 the link was logged instead — a live credential in logs the
host keeps. The log line now carries the event, the user id and the fact that
email was not sent; never the link, the token or the address.

**Errors:** `429 rate-limited` (with `Retry-After` header in seconds; detail "Too many attempts. Try again in N minutes."; 3 per email and 10 per IP per hour; byte-identical for an address with and without an account; with Redis down this endpoint still answers 200), `422 validation-failed` (if the body is not an email address).

#### `POST /api/v1/auth/reset-password/confirm`
Redeem a reset link and set the new password. **No auth.** Epic 9.13.

```json
{ "token": "...", "newPassword": "at least 12 characters" }
```

**Response `200`** — `{ "status": "reset", "detail": "..." }`.

**Every existing session is revoked, and the caller is NOT signed in
afterwards** — both deliberate, and both different from `change-password` above.
A reset is what someone does when they believe the account is compromised, so
leaving the attacker's session alive would defeat the exercise; and the person
holding the link proved control of an inbox rather than knowledge of the old
password, so signing in once with the new one confirms they hold it.

**A successful reset clears that email's login rate-limit counter**, so the
next login (or 10 failed logins) starts fresh.

**Errors:** `400 invalid-reset-token` for unknown, expired, already-used and
belonging-to-an-inactive-user alike — one response, no branch that says which.
`422 validation-failed`.

#### `POST /api/v1/auth/invitations/accept`
Redeem a seat invitation, choose a password, and sign in. **No auth** — the
holder has no account to authenticate with yet; that is what the link is for.

```json
{
  "token": "opaque-256-bit-token-from-the-email",
  "fullName": "Sam Okafor",
  "password": "at least 12 characters"
}
```

Password rules are the SIGN-UP rules, imported rather than restated — the same
`Password` annotation `sign-up` and `reset-password/confirm` carry. A path that
sets a first password with weaker rules than registration is the way in.

**Response `200`** — `MeOut`. Sets the session cookie.

**`200`, not `201`:** nothing is created. The `User` row was inserted when the
invitation was sent and has occupied a seat ever since; this fills it.

**It signs the caller in, unlike `reset-password/confirm`.** That endpoint
leaves the caller signed out because they proved control of an inbox rather
than knowledge of a password, so one deliberate sign-in confirms they hold the
new one. There is no prior state to protect here: this is a first password on a
seat that has never been used, which is the case sign-up already calls "friction
with no security value".

**Errors:** `400 invalid-invitation` for unknown, expired, already-accepted,
revoked, and pointing-at-a-since-removed-seat alike — one response, no branch
that says which. `422 validation-failed`.

#### `GET /api/v1/auth/me`
**Auth required.** The whole authenticated context in one call, so the web app
shell does not need three round trips per page load.

**Response `200`** — `MeOut`:
```json
{
  "user": {
    "id": "user_01J...",
    "email": "dana@meridiansearch.example",
    "fullName": "Dana Whitfield",
    "role": "owner",
    "status": "active",
    "lastLoginAt": "2026-08-20T05:31:44Z",
    "createdAt": "2026-08-20T05:29:02Z",
    "signInMethods": ["email"]
  },
  "agency": {
    "id": "agcy_01J...",
    "name": "Meridian Search Partners",
    "slug": "meridian-search-partners",
    "seatLimit": 3,
    "createdAt": "2026-08-20T05:29:02Z"
  },
  "seats": { "used": 1, "limit": 3 },
  "feedbackEmail": null,
  "scanEmails": { "available": false, "enabled": true }
}
```

`signInMethods` — Epic 20 — is how the account can be signed into: `"email"`
(a password), `"google"`, or both. An account created through Google that
never set a password has only `"google"`, and Settings says so instead of
offering a password change. Named for the door rather than the credential,
because no auth response may carry the word "password" (`test_password_is_never_returned`).

`feedbackEmail` — 2026-10-06 — is the API's `FEEDBACK_EMAIL`: the one address the web's
"Send feedback" link writes to, or `null` when it is unset, which is the default and means the
web draws no link at all. It is **required** (the key is always there), so every route that
builds the context has to decide it, and it is on the signed-in context and on no other
response. `MeOut` is also what sign-up (`201`), login, change-password, an accepted invitation
and Google's sign-up completion return; each of those either needs a session or sets one in
that same response, and `tests/test_feedback_email.py` lists these six operations so a seventh
must be added on purpose. A signed-out `GET /auth/me` is the same `401` as ever, and the public
plan, a shared report and the reset routes carry nothing of it. The setting is checked as one
email address when the API starts: a blank is unset, and anything else that is not one address
stops the start with a message that names `FEEDBACK_EMAIL` and does not repeat the value. It is
not a secret and is shown to every signed-in user. From it the web builds
`mailto:<address>?subject=AVP feedback: <route shape>`: the subject carries the shape of the
page (`/clients/…/alerts`), never an id, a token or a client's name. Nothing about it is logged.

`scanEmails` — F1, 2026-10-06 — is the scan-finished email switch for the caller. **Required** on
the same six context operations as `feedbackEmail`, and on no other response (not the seat list).
`available` is a fact about the deployment, the same for every user: `EMAIL_SCAN_NOTIFICATIONS`
is on AND email is configured. `enabled` is the caller's own choice (`users.scan_emails`,
default `true`). The web shows the switch only when `available` is `true`.

**Errors:** `401 authentication-required`.

#### `PUT /api/v1/auth/me/scan-emails`
**Auth required.** Turn the emails sent when a scan you started finishes on or off.

```json
{ "enabled": false }
```

**Response `200`** — `{ "available": true, "enabled": false }` (the same object as `MeOut.scanEmails`).

**Only the caller's own choice.** No user id is in the request: the row written is the caller's,
matched by user id and agency id. `enabled` must be a JSON `true` or `false`, and a body that
names anything else is a `422`. Idempotent. Accepted whether or not the feature is on (`available`
says), because it writes one boolean that nothing reads while the feature is off.

**Errors:** `401 authentication-required`, `422 validation-failed`.

**The emails themselves (F1)** go out only when `EMAIL_SCAN_NOTIFICATIONS` is on and
`RESEND_API_KEY` is set, to the user who started the scan (`scans.requested_by_user_id`), who
is active, in the scan's agency and has not opted out. A sweep every 60 s finds scans that reached
a final status in the last 15 minutes with no `scans.notified_at`, claims each with one
conditional UPDATE, then sends, at most once. SUCCEEDED and PARTIAL: "Your report for <client> is
ready" (PARTIAL adds one sentence) linking `/scans/<id>/report`; a scan that raised alerts: a
second email counting them by kind, linking `/clients/<id>/alerts`; FAILED: "did not finish",
linking `/clients/<id>`. CANCELLED sends nothing. Plain text; the client's name and counts are all
that is said of the scan.

#### Google sign-in — Epic 20

"Sign in with Google" beside the password form, not instead of it. Sessions
afterwards are the same httpOnly cookie; seat and tenancy rules are the
password flow's. Authorization code with PKCE (S256), a server-side `state`
and `nonce`, and the ID token verified server-side (signature against
Google's JWKS, audience, issuer, expiry, nonce) even though it arrived over
TLS from the token endpoint. All four routes are unauthenticated. All three
settings — `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`,
`GOOGLE_OAUTH_REDIRECT_URL` — must be set; unset, the button's target answers
`503` and nothing else changes.

**The account-linking policy**, decided and recorded in build-log Epic 20:
a Google identity whose verified email matches an ACTIVE account **links
automatically** and stores Google's `sub` on the row; thereafter the `sub`
is matched first and the email second. Refused when the row already carries
a different `sub` (`email-claimed`), when the account is suspended
(`account-suspended`), when an invited seat has no live invitation
(`invitation-expired`), or when the account was soft-deleted
(`account-unavailable`). An
`email_verified: false` identity is refused (`email-unverified`). An INVITED
seat with a live invitation is **accepted** by signing in with Google. A
new address creates nothing until the agency is named.

##### `GET /api/v1/auth/google/start`
A browser navigation. **`302`** to Google's authorization endpoint carrying
`state`, `nonce`, `code_challenge` (S256), `scope=openid email profile`,
`prompt=select_account`. The response also sets the **flow cookie**
(`__Host-avp_google_flow` when the session cookie is Secure, else
`avp_google_flow`): a random value bound to the parked state, `HttpOnly`,
`SameSite=Lax`, `Path=/`, no `Domain`, `Max-Age` = sign-in TTL + 60 s (600 + 60).
**Errors:** `503 google-sign-in-not-configured`.

##### `GET /api/v1/auth/google/callback?code&state` (or `error`)
Where Google returns the browser. **Always `302`**, never a problem
document — a person, not a script, is standing here:

| Outcome | Redirects to |
|---|---|
| existing account | `{PUBLIC_WEB_BASE_URL}/dashboard`, with the session cookie set |
| new address | `{PUBLIC_WEB_BASE_URL}/sign-up/google#ticket=…` (ten minutes, single use; in the fragment, never the query) |
| anything else | `{PUBLIC_WEB_BASE_URL}/?google=error&reason=…` |

The callback consumes the state (single use), then compares the flow cookie
with the digest parked at `/start`; a missing cookie, a flow parked without a
digest, or a different browser's cookie is `browser-mismatch` and no code is
exchanged. Every callback response clears the flow cookie.

`reason` is one of `denied`, `invalid-state`, `browser-mismatch`, `exchange-failed`,
`email-unverified`, `account-suspended`, `email-claimed`,
`invitation-expired`, `account-unavailable`, `not-configured`, or
`unavailable` (something under the route — Redis, Postgres, the session
store — failed; the person still gets a page, never a 500). The URL carries
no token, no email and no Google error text. **Distinct since 2026-09-21**:
until then suspended, claimed-by-another-Google-account and no-live-
invitation all read `account-unavailable`; they are told apart now because
the person reading the sentence has just proven, through Google, that they
hold the very address in question. A soft-deleted account is the one that
stays `account-unavailable`.

##### `POST /api/v1/auth/google/pending`
_Note 2026-10-01:_ the legacy `?ticket=` fallback in
`apps/web/src/lib/googleTicket.ts` is dead ten minutes after this deploys
(tickets live ten minutes); remove it in the next release.

**Request:** `{ "ticket": "…" }` (was `GET ?ticket=…` until 2026-10-01; a `GET`
is now `405`, so the ticket is never in a URL).
**Response `200`** — `GooglePendingOut`: `{ "email": "…", "suggestedName": "…" }`.
Read-only; the ticket is not spent. The ticket is bound to the browser that
signed in: the callback's new-address redirect keeps the flow cookie (renewed,
Max-Age = TTL + 60) and the ticket record carries its digest, so the cookie
must come with this call. **Errors:** `400 invalid-google-ticket` for unknown,
used, expired, and a missing or another browser's flow cookie alike.

##### `POST /api/v1/auth/google/complete`
**Request:** `{ "ticket": "…", "agencyName": "…", "fullName": "…" }` —
the two things `sign-up` asks that Google cannot answer. No email (the
ticket's), no password.

**Response `201`** — `MeOut`, with the session cookie set. The agency and
its OWNER are created, `signInMethods: ["google"]`. The ticket is consumed
first, then the flow cookie must match it (else `400`, nothing created). Every
response, success or refusal, clears the flow cookie. Two Google sign-ins in
two tabs of one browser share one flow cookie, so the earlier one is refused
(`browser-mismatch`); accepted, it fails safe. **Errors:** `400 invalid-google-ticket`, `409 email-already-registered`,
`422 validation-failed`.

### Agencies (seat management) — Epic 1.5, built in 9.14

Recorded as *planned* from Epic 1 until Epic 9.14 built the HTTP surface. The
`invitations` table, `services/seats.py` and `SessionStore.revoke_all_for_user`
already existed and were already tested; only the routes were outstanding.

Both mutating routes require **owner or admin**. A member holds a seat; they do
not decide who else does. An agency id in the path that is not the caller's is a
**`404`, never a `403`** — confirming an id exists is a cross-tenant leak.

#### `GET /api/v1/agencies/{agencyId}/seats`
**Auth required (owner/admin).** The roster behind the count.

`GET /auth/me` carries `seats: {used, limit}` — the number the shell needs. It
has never carried the list, which is what a management screen needs.

**Response `200`**
```json
{
  "members": [ { "...": "UserOut" } ],
  "invitations": [
    {
      "id": "invt_01J...",
      "email": "sam@meridiansearch.example",
      "role": "member",
      "expiresAt": "2026-09-04T09:12:00Z",
      "createdAt": "2026-08-28T09:12:00Z"
    }
  ],
  "seats": { "used": 2, "limit": 3 }
}
```

`members` is ordered owners → admins → members, then by id. A pending invitee
appears in **both** lists: in `members` with `status: "invited"` because they
occupy a seat, and in `invitations` because only that row knows the expiry.
Merging the two would force one of those facts to be dropped.

`invitations` excludes expired rows. The seat an expired invitation left behind
is still consumed — it is held by the `User` row, not this one — so it stays in
`members`, and listing a dead link beside it would invite someone to wait for it.

**No token and no invite URL appears in any response body**, here or below,
with one exception: an invitation made where email is not configured (see
`acceptUrl` below). Otherwise the link goes in exactly one email; a response
body is a place it would be logged by a proxy, kept in a browser's network
panel, and read over an operator's shoulder. Same reasoning
`PasswordResetToken` gives for storing only a digest, applied to the other end
of the credential's life.

**Errors:** `401`, `403`, `404`.

#### `POST /api/v1/agencies/{agencyId}/invitations`
**Auth required (owner/admin).** Invite an address to a seat.

```json
{ "email": "sam@meridiansearch.example", "role": "member" }
```

`role` defaults to `member`, the least-privileged seat there is.

**Response `201`**
```json
{
  "invitation": { "...": "PendingInvitationOut" },
  "user": { "...": "UserOut" },
  "seatConsumed": true,
  "seats": { "used": 2, "limit": 3 },
  "acceptUrl": null
}
```

**`acceptUrl` — 2026-09-29.** Null whenever email is configured: the link goes
in one email and nowhere else. With no `RESEND_API_KEY` it carries the accept
link, in this one response, to the owner or admin who made the invitation —
otherwise the link would reach nobody. The link has the form
`{PUBLIC_WEB_BASE_URL}/invite#<token>` since 2026-09-30, so the token never
reaches a server's request log. It is never shown again (the roster does
not carry it), and re-inviting mints a fresh one and retires it. Only the
token's digest is stored, as before; handing a link once to the authorised
person who asked for it is what `POST /scans/{scanId}/share` already does.

**The seat limit is enforced here, server-side, inside the same transaction as
the insert.** `GET /auth/me`'s `seats` lets a screen grey out the form when the
agency is full, but that is a courtesy: the limit is commercial policy and a
client-side check is a suggestion. A refused invite creates **no user row and no
invitation row** — the check shares the insert's transaction, so there is no
half-applied state to clean up.

**Re-inviting an address that already holds an `invited` seat is allowed, and
consumes no second seat.** The `User` row with `status: "invited"` is what
occupies the seat, and it is the row being re-invited — so the call revokes the
outstanding link, mints a new one, and answers `seatConsumed: false`. Refusing
instead (which the sign-up path's `email-already-registered` check would have
done) leaves an agency with a seat consumed, nobody in it, and no way out except
removing the seat and starting over. A new link retires the old one, the same
rule `reset-password/request` applies for the same reason.

**Re-inviting an address whose seat was REMOVED revives that user row** rather
than inserting a new one, and does consume a seat. `uq_users_email` is
unconditional — it does not exclude soft-deleted rows — so without this, removing
a seat would ban that address from the product permanently, including from the
agency that removed it by mistake. Reviving also keeps
`scans.requested_by_user_id` pointing at a live row instead of orphaning it.

**`201` in both cases.** An invitation row is genuinely created either way; that
is the resource this endpoint makes. Whether a *seat* was newly consumed is a
different question, answered in the body rather than in the status.

**Errors:** `401`, `403`, `404`, `409 seat-limit-reached` (carries `seatsUsed`,
`seatLimit`), `409 email-already-registered` (a live account, here or at another
agency — email is globally unique by design), `422`.

#### `DELETE /api/v1/users/{userId}`
**Auth required (owner/admin).** Release a seat. **`204`, no body.**

**Every session that seat holds is revoked, immediately.** `sessions.py` opens
by saying this case is why the product has a server-side session store rather
than JWTs: "when an agency removes a seat, that person's access has to end
*now*". This endpoint is the case that argument was made for, so it calls
`revoke_all_for_user` rather than relying on the fallback.

There **is** a fallback and it is not the mechanism: `current_principal`
re-reads the user on every request and `401`s on a soft-deleted row, so access
would end on the removed user's next call regardless. That closes the door
within one request; revocation closes it within zero, and the difference is a
request already in flight.

The row is **soft-deleted**. The seat is released while
`scans.requested_by_user_id` and the rest of that person's history stay intact —
the rule `models/base.py` states for the whole schema. Any outstanding
invitation for the address is revoked with it.

Three refusals:

* **`409`** — removing yourself. The session authenticating the request is the
  one about to be revoked, mid-request. `logout-all` is the deliberate version.
* **`409`** — removing the last active owner. `UserRole` says why: an agency with
  no owner has nobody who can manage seats, including nobody who can undo this.
* **`403`** — an admin removing an owner. That would let a seat the owner granted
  be used to remove the owner who granted it.

**Errors:** `401`, `403`, `404` (unknown user, or another agency's — never
`403`, which would confirm the id), `409`.

### Billing (subscriptions) — Epic 9.15

**One plan, $150/month, 3 seats** — $29 from Epic 9.15 until 2026-09-22, then
$160 until 2026-10-04, then $150 (founder decision). The price is
`PLAN_PRICE_USD` in `apps/web/src/components/marketing/PricingCard.tsx` and in
`services/billing.py`, held equal by a web test. A $160.00/month test-mode Price
exists since 2026-09-23 (`price_1UIh3b…`, read back at 16000 USD) and the local
`STRIPE_PRICE_ID` names it; Render's names the same $160 test Price (founder,
2026-10-04). A US$150/month Price is the founder's to create and name in
`STRIPE_PRICE_ID`; until then a deployed API logs `billing.price_mismatch` at start
and hourly (`docs/runbook.md`, "Reading the billing price lines"). The $29.00 Price
(`price_1U9For…`) is still active.
Stripe, in **TEST MODE**: the keys are
`sk_test_…` and `price_…` with `livemode: false`, and **no code anywhere behaves
differently on a live key.** Going live is swapping two environment variables.

**A free trial — 2026-10-04** (founder decision: a 30-day free trial with the card
entered at checkout, charged on day 31 unless the agency cancels). The length is
the setting `STRIPE_TRIAL_DAYS`, **0 by default, which is no trial**, and with 0
checkout sends exactly the parameters it did before the setting existed (what is new
besides is additive: `trialEndsAt`, null unless an agency is trialing, and
`GET /billing/plan`, answering 0). The setting takes
0 to 730 whole days (Stripe's own limit; any other value stops the API from
starting). Above 0:
- checkout sends Stripe `subscription_data.trial_period_days` and
  `payment_method_collection: "always"` for an agency that has never had a
  subscription, and Stripe charges at the trial's end (below, under the checkout);
- the webhook handles `customer.subscription.trial_will_end` as a log line only, and
  stores the trial's end (below);
- `GET /agencies/{agencyId}/billing` says when it ends (`trialEndsAt`), and
  `GET /billing/plan` tells the public pages how long it is.
A trialing agency is `isActive` and has the plan's **full allowance**: forty scans a
month, counted by calendar month (UTC) like any paid agency, so a trial has forty in
each calendar month it touches (up to three): a 30-day trial touches two, or three when
it starts on 30 or 31 January (or on 31 January in a leap year). **One trial per
agency, ever.**

**These endpoints gate nothing themselves; the status they record gates two things.**
Since 2026-09-28 the scan allowance reads `subscription_status` (one free scan per
agency, then 40 a month while it is `active` or `trialing`; `services/scan_allowance.py`
and "The scan allowance" below), and since 2026-10-04 so does the detect route
(`POST /clients/{clientId}/competitors/detect`, launch checklist 3.61). Sign-up,
onboarding, and opening scores and reports are not gated. (Until 2026-10-04 this
paragraph said that nothing was gated and that `subscription_status` recorded only
whether an agency pays, which stopped being true on 2026-09-28.)

All three authenticated routes require **owner or admin**, the same authority
rule Epic 9.14 set for seat management, on the same argument: `UserRole`'s own
docstring says the owner is the billing contact, and a member is not it. The
READ is gated too — a member shown "No active subscription" beside a Subscribe
button that would 403 is a worse screen than one that does not offer it, and
Settings already degrades a forbidden section for the seat roster.

An agency id in the path that is not the caller's is a **`404`, never a `403`**.

**They live in `routers/billing.py` rather than `routers/agencies.py`**, and the
reason is the webhook. Three of these routes are agency-scoped and would sit
happily beside seat management; `POST /billing/webhook` has no session, no
principal, no role and no agency in its path, and is authenticated by an HMAC
over its own raw body. A module whose docstring reads "Owner or admin" would
then carry a route that gate does not describe, and the failure mode is
specific: somebody adds a route, copies the shape above it, and copies the wrong
one.

#### `GET /api/v1/agencies/{agencyId}/billing`
**Auth required (owner/admin).** The agency's subscription, as recorded.

**Response `200`**
```json
{
  "subscriptionStatus": "active",
  "isActive": true,
  "currentPeriodEnd": "2026-09-21T14:13:20Z",
  "hasBillingAccount": true,
  "scansUsedThisPeriod": 12,
  "scanLimit": 40,
  "periodResetsAt": "2026-10-01T00:00:00Z",
  "freeScanRequiresGoogle": false,
  "cancelAtPeriodEnd": false,
  "trialEndsAt": null,
  "trialEligible": false,
  "trialRequiresGoogle": false
}
```

**`trialEndsAt` — 2026-10-04.** When the free trial ends and the card is first
charged, **set only while `subscriptionStatus` is `trialing`** and null in every other
state: for a trial that converted (the date is history), a cancelled or failed one,
and an agency that never had one. The column behind it
(`agencies.subscription_trial_end`) mirrors Stripe's `trial_end`, written by the
webhook from every `customer.subscription.*` event, so it outlives the trial; the
status is what says whether one is under way. Settings says "Free trial until
<day and time, UTC>, then $150 a month" from it (the time, because the instant it
ends is the cancel-by deadline, and the day unpadded, as a date is mid-sentence: for
example "Free trial until 3 Nov 2026, 09:05 UTC, then $150 a month"). A trialing agency is `isActive` and reads `scanLimit: 40` like
any paid agency.

**`trialEligible` — 2026-10-04, round two.** Whether Settings may promise this
agency a free trial: **true only when a trial is on and this agency's own record has
never had a subscription.** "A trial is on" is `STRIPE_TRIAL_DAYS` above 0 with billing
configured, the same reading `GET /billing/plan` gives (0 wherever the Stripe key or the
Price is unset). "Has never had a subscription" is the row test checkout applies
(`services.billing.trial_days_for`): no `stripe_subscription_id`, no
`subscription_status` and no `stripe_event_at` on the agency row (any of the three
means a subscription has existed, `canceled` and `incomplete_expired` included). So it
is false for an agency that is subscribed or trialing, for one that has had its
subscription or its trial, and for every agency while no trial is on. **It cannot see
Stripe's side of checkout's test, the customer's own subscription list**, because this
endpoint never calls Stripe: a read makes no round trip. So `true` means "nothing in our
record says no", and checkout can still refuse the trial to a customer for whom Stripe
remembers an ended subscription that our row never recorded (a webhook that did not land).
That is the one case Settings can be wrong in, and a rare one; checkout never gives more
than it promises. The web promises the trial only on a `true` and never works it out itself.

**A trial needs a Google sign-in — 2026-10-05 (launch checklist 3.72).** A free trial
is given only when the **user who starts the checkout** has a verified Google identity
(`User.google_sub`, `scan_allowance.has_verified_identity`: the free scan's rule, reused). The
rule is on the user and not the agency: a password-only admin of an agency whose owner has
Google gets the plain checkout. So both trial fields are about **the requesting user**, and two
seats of one agency can read them differently:

- `trialEligible` is true only when everything above holds **and** this user has a linked
  Google identity: it is what a Subscribe from this sign-in would get (subject to the Stripe-side
  caveat above). Its meaning is therefore narrower than it was: false for a user without Google.
- `trialRequiresGoogle` is true exactly when the agency's record and the configuration would
  give a trial **and the only thing missing is the Google identity**: checkout would give this
  user no trial, and continuing with Google on the same address would. False when no trial is on,
  when the agency has had a subscription, and for a user who has Google. The two are never both
  true. Settings says, from it, that subscribing now starts the paid plan at once with no free
  trial and offers Continue with Google.

Checkout for a user without Google is **not refused**: it creates the same session a no-trial
checkout does (no `trial_period_days`, no `payment_method_collection`), returns the same `201`
and URL, and logs `billing.checkout_created` with `trial_withheld_no_google: true` (ids and
booleans only: `agency_id`, `session_id`, `user_id`, `trial_days`).

**`cancelAtPeriodEnd` — 2026-09-29.** True when the subscription was cancelled
in Stripe's portal and runs to the end of the period already paid for. Stripe
keeps the status `active` until then, so `isActive` stays true and the plan's
allowance applies until `currentPeriodEnd`; Settings says "Ends" rather than
"Renews". Stored from `customer.subscription.created` and `.updated`;
`.deleted` sets it back to false.

**The scan allowance — 2026-09-28** (`services/scan_allowance.py`). One free
scan per agency for life (`FREE_SCAN_ALLOWANCE = 1`); forty per calendar
month, UTC, on the plan (`PAID_SCANS_PER_MONTH = 40` — 40 × ~$1.70 of engine
cost ≈ $68 against $150 since 2026-10-04, $160 before). `scansUsedThisPeriod` counts scans that hold a
slot — everything not `failed` or `cancelled`, in-flight included — this
month for a paid agency and lifetime for a free one. `scanLimit` is **null
when billing is not configured** on the deployment (no `STRIPE_SECRET_KEY`
or `STRIPE_PRICE_ID`): the gate is off there, matching checkout's
`503 billing-not-configured`. `periodResetsAt` is the first instant of next
month for a paid agency and null for free. The web reads all three from
here and carries no copy of the numbers. `canceled`, `past_due`, `unpaid`
and `paused` are free. **The platform operator is exempt**: a sign-in listed
in `SCAN_ALLOWANCE_EXEMPT_EMAILS` (empty by default) **and** holding a
linked Google identity is not gated, per user, and reads `scanLimit: null`
here. A listed address with no Google link is gated like anyone else
(2026-09-28).

**`freeScanRequiresGoogle` — 2026-09-29.** The free scan starts only for a
requesting user with a linked Google identity (`User.google_sub`): password
sign-up never verifies an address, and an agency costs nothing to make.
The field is true exactly when the gate is on, the agency is free, and the
**requesting user** has no Google link — which is exactly when
`POST /clients/{clientId}/scans` answers `402 SCAN_LIMIT_VERIFY_REQUIRED`.
It describes the caller, not the agency: an owner who signed in with Google
and a password-only teammate read it differently. False for a paid agency
(a payment is identity enough), for an exempt operator, and wherever billing
is not configured. The web shows "Free scan needs Google sign-in" from it
and never works it out itself.

**This endpoint never calls Stripe.** Every field is read from the `agencies`
row that the webhook maintains. That is a deliberate property rather than an
optimisation: a settings screen that reached a payment API on every page load
would be slower, would fail whenever Stripe was slow, and would put a third
party in the render path of a page with four other sections on it — for a value
no fresher than the webhook already makes it.

`subscriptionStatus` is **Stripe's own string, passed through unmapped** —
`active`, `trialing`, `past_due`, `unpaid`, `incomplete`, `incomplete_expired`,
`canceled`, `paused`, or anything Stripe adds later. A client asking "is this
agency paid up" should read `isActive` rather than comparing strings, because
which statuses mean yes is a decision that lives in `services/billing.py`.
Note that `past_due` is **not** active: north-star.md §5.4 row 4 asks for a
billing-failure state rendered as honestly as `partial` is, and counting a
failed payment as active would be the silent degradation that row forbids.

**No Stripe identifier appears in the body.** `hasBillingAccount` is the derived
fact a screen needs — whether the hosted portal has anything to open. The
customer and subscription ids are withheld because the browser has no use for
them and a response body is a place they would be logged by a proxy and kept in
a network panel.

The four subscription fields, `cancelAtPeriodEnd` and `trialEndsAt` are
`null`/`false` for every agency that has not subscribed. (`trialEligible` is the other
way round: it is `true` for an agency that has not subscribed, while a trial is on.)

**Errors:** `401`, `403` (member role), `404` (another agency's id).

#### `GET /api/v1/billing/plan`
**No auth.** What the plan offers the public: the length of its free trial
(2026-10-04). Read by the pricing card and the landing page before anybody has
signed up.

**Response `200`**
```json
{ "trialDays": 30 }
```

`trialDays` is `STRIPE_TRIAL_DAYS`, **0 meaning there is no trial**, so the length is
stated in one place and a page says "the first N days after you subscribe are free"
only for an N above 0 (while the page is still asking, if the request fails, and for 0,
it says nothing about a trial at all). It is **0 wherever checkout cannot start a subscription**
(`STRIPE_SECRET_KEY` or `STRIPE_PRICE_ID` unset): a trial nobody can start is not one
to promise. It describes the offer to a *new* agency; whether a particular agency
still gets it is its own history, which checkout decides (and `GET
/agencies/{agencyId}/billing` says in advance, as `trialEligible`).

`trialDays` is the offer to an account that qualifies: since 2026-10-05 a trial needs a Google sign-in on the user who subscribes, which this public read cannot know, so the signed-out pricing card says the trial is for an account signed in with Google.

**When the web asks (rounds two and three).** At the top of the home page's and Settings'
loaders, in parallel with their first calls, so the pricing card is drawn with its sentence
and does not grow a line a moment later. The page keeps that request and waits for it only
at its **draw point**, when everything else it needs is in: an answer that has already come
wins at once, however slow the other calls were, and one that has not is waited for 0.5 s
(the landing page, whose card sits far below the fold) or 1.5 s (Settings), and only where
the landing page or Settings is what it is about to draw: a slow plan call cannot hold a
page. If it has not answered by then the page is drawn without a trial sentence and the
card awaits the page's own request, so the whole page makes one request, never a second. A
card that was told the answer does not ask. A Settings reload (a seat change) whose plan
call is slow keeps the previous answer, so the sentence never blinks off and on.

**No session, no agency, nothing secret**, and it touches no database and no Stripe,
so it is as cheap as `/health` and has nothing to rate-limit. **Never cached**
(`Cache-Control: no-store`): a cache would keep a page saying "30 days free" after a
deploy turned the trial off, and checkout would not give one. A `GET` is not checked
by the Origin check; CORS is unchanged (the web app reads it same-origin through its
`/api/v1` proxy, and a page on another origin is not let read the answer). **Errors:**
none of its own.

#### `POST /api/v1/agencies/{agencyId}/billing/checkout`
**Auth required (owner/admin).** Start a subscription. No request body.

**Response `201`**
```json
{ "url": "https://checkout.stripe.com/c/pay/cs_test_..." }
```

**A URL, and nothing else.** The frontend navigates to a page Stripe hosts and
the customer comes back. That is why there is **no Stripe JavaScript library in
`apps/web`** — no new frontend dependency, no script on a page taking card
details, and no publishable key to keep in step.

**`201`, because a session really is created** — at Stripe, with an id and a
lifetime, and this call is what makes it. That it lives in someone else's
database does not make it less of a created resource.

**The agency's Stripe customer is created once and reused.** A second visit to
this endpoint does not mint a second customer: `services/billing.py` reads
`agencies.stripe_customer_id` first, and `uq_agencies_stripe_customer_id` is the
backstop under that check for two simultaneous requests. Someone who opens
checkout, thinks better of it, and returns tomorrow is the ordinary case — and a
duplicate customer can hold its own card and its own subscription, with the
webhook updating whichever one our column happened to point at.

**Both Stripe settings are validated before anything is created.** A missing
`STRIPE_PRICE_ID` refuses without having created a customer first, so a
misconfigured server leaves nothing orphaned at Stripe.

**Return URLs come from configuration, never from the request.** `Host` and
`Origin` are attacker-controlled, and a success URL built from a spoofed header
is a phishing page wearing our checkout flow — the same argument
`public_web_base_url` already makes for share links. Neither return URL is
load-bearing in any case: `success_url` carries no session id, and the screen it
lands on reads the database.

**This endpoint does not subscribe anybody.** It returns a URL. The subscription
begins when Stripe says so, over the webhook.

**The free trial — 2026-10-04.** With `STRIPE_TRIAL_DAYS` above 0, a checkout for an
agency that is **eligible** carries two more parameters, and nothing else about the
session changes:

| | `STRIPE_TRIAL_DAYS` = 0, or not eligible | `STRIPE_TRIAL_DAYS` = N, eligible |
|---|---|---|
| `subscription_data` | `{"metadata": {"agency_id": …}}` | `{"metadata": {"agency_id": …}, "trial_period_days": N}` |
| `payment_method_collection` | not sent | `"always"` |

`"always"` makes Stripe take the card at checkout, and Stripe charges when the trial
ends unless the agency cancels first (without it Stripe may skip the card for a
session that costs nothing now, and there would be nothing to charge on day 31). With
0 the session params are exactly what they were before the setting existed.

**Eligible = the agency has never had a subscription**, in both places that could
say so: its own row has no `stripe_subscription_id`, no `subscription_status` and no
`stripe_event_at` (any of the three means a subscription has existed, `canceled` and
`incomplete_expired` included), **and**, when it already has a Stripe customer, that
customer's subscription list, the single call checkout already makes (`status=all`),
is empty: an ended subscription on it counts. No extra Stripe call is made. An
ineligible agency still checks out, to the plain session. An agency that opened a
checkout and left has never had a subscription and still gets the trial. Every
refusal below is unchanged: a trial never gets round a live subscription. The log
line `billing.checkout_created` carries `trial_days` (the days sent, 0 when none).

**A subscription that is live at Stripe refuses a new checkout** (founder
decision 4, 2026-10-01). A second Checkout Session would create a second
subscription beside it, so the answer is a `409` and no Stripe call is made, in
two cases:

- `subscriptionStatus` is `active` or `trialing` (`services.billing.ACTIVE_STATUSES`,
  the same set as `isActive`): `409 subscription-already-active`. `detail` reads
  "This agency already has a current subscription. Manage it from Manage billing
  in Settings."
- `subscriptionStatus` is anything else that is not over: `past_due`, `unpaid`,
  `paused`, `incomplete`, or a status this server has never seen
  (`services.billing.is_live_at_stripe`): `409 subscription-needs-attention`,
  title "Subscription needs attention". `detail` reads "This agency already has a
  subscription that needs attention. Manage it from Manage billing in Settings."
  These are not `isActive` (`isActive` and the scan allowance still count only
  `active` and `trialing`), but Stripe still holds the subscription open.

Neither `detail` carries a Stripe id or the status. Only `null`, `canceled` and
`incomplete_expired` (no subscription, or one that is over) check out. That list
is of what is OVER, not of what is live, on purpose: a status Stripe adds later
refuses a checkout until somebody decides what it means, instead of letting a
second subscription through. The check runs after auth and tenancy, so a member
still gets `403` and another agency's id `404`; the `409` is only ever seen by
that agency's own owner or admin.

**Starting a new checkout expires the previous one, and only then asks about
subscriptions.** Before creating a session for an agency that already has a
Stripe customer, every `open` Checkout Session of that customer is expired, so at
most one payable session exists and two cannot both be paid into two
subscriptions. That comes first. Asked the other way round, a session paid after
we looked at the subscriptions and before we expired it would become a
subscription we never saw, and we would create a second session beside it. In
this order a session paid earlier is a subscription by the time Stripe is asked
(`409`), and one that completes during the expire makes the expire fail (`503`).
If Stripe fails while listing or expiring, or more open sessions exist than one
page (100) holds, the checkout fails with `503 service-unavailable` and creates
nothing; retrying is safe. Concurrent checkouts for one agency serialise on the
agency row, so two first checkouts create one Stripe customer, not two.

**The link expires one hour after it is created** (founder decision 5,
2026-10-01). Every Checkout Session is created with `expires_at` set to now plus
one hour (`services.billing.CHECKOUT_LINK_LIFETIME`), where Stripe's default is 24
hours; Stripe accepts 30 minutes to 24 hours. An unpaid Checkout page stops
accepting payment once the hour is up and Stripe shows it as expired; pressing
Subscribe again makes a new link. Nothing of ours records the expiry, and
`checkout.session.expired` is not a handled event. A shorter life also narrows how
long an older open link can be paid before the next checkout expires it, as above.

**The subscription check also asks Stripe.** For an agency that already has a
customer, once its open sessions are cleared, Stripe is asked for that customer's
subscriptions before anything is created: one list call, every status
(`status=all`), up to 100. Any `active` or `trialing` subscription is `409
subscription-already-active`; failing that, any subscription that is not over
(every status but `canceled` and `incomplete_expired`, one with no readable
status included) is `409
subscription-needs-attention`, even when our row does not say so yet (paid, the
webhook has not landed) or says `canceled`. A paid-up subscription outranks one
that needs attention, whatever order Stripe lists them in. Ended subscriptions
are on that list and refuse nothing. If Stripe fails while listing, the answer is
`503 service-unavailable` and nothing is created. So it is when the list comes
back full (more than 100 subscriptions on one customer, not a real case) with
nothing live on it, because none can then be proved absent; a full page with a
live subscription on it is still the `409`. The `503` `detail` says which step
failed: clearing the previous checkout session, or checking the agency's
existing subscriptions.

**Bounded waiting.** The agency row is locked for the request, but a checkout
waits at most 3 s for it (`lock_timeout`) and then answers `409
checkout-in-progress`. A repeat checkout locks `FOR NO KEY UPDATE`, so scans,
clients and alerts being inserted for the agency are not held up; the first
checkout writes the customer id (a unique-indexed column) and takes the full
lock. The Stripe client used here has a 15 s timeout and one retry per call
rather than the SDK defaults.

**Errors:** `401`, `403`, `404`, `409 subscription-already-active`, `409
subscription-needs-attention`, `409 checkout-in-progress`, `503
service-unavailable` (Stripe failed while clearing the previous session or
checking the customer's subscriptions, or a full page of either left nothing
provable), `503
billing-not-configured` when
`STRIPE_SECRET_KEY` or `STRIPE_PRICE_ID` is unset — `detail` names the exact
variable, the same courtesy `provider_key()` gives every other integration,
`503 plan-price-mismatch` when the latest price check found the Price is not the
plan and a fresh read for this request confirms it (after the two 409s, before
anything is created at Stripe; that read waits at most 10 s, and one that fails or
takes longer never refuses).

#### `POST /api/v1/agencies/{agencyId}/billing/portal`
**Auth required (owner/admin).** Stripe's hosted billing portal. No request body.

**Response `201`**
```json
{ "url": "https://billing.stripe.com/p/session/bps_test_..." }
```

Same shape as checkout, and deliberately a separate response schema rather than
a shared `UrlOut`: they are two resources with two different preconditions — a
portal session requires an existing customer and a checkout session creates one
— and collapsing them would make the OpenAPI schema describe them as
interchangeable.

Update a card, cancel, download invoices. All of it, for one API call and no UI
of our own. Building those screens here would mean handling card details,
dunning states and invoice PDFs — a product in itself, and one Stripe ships.

**Requires an existing Stripe customer.** An agency that has never subscribed
gets `503` with a sentence saying to subscribe first. The portal for such an
agency is an empty page with no card and no invoices, which is a worse answer
than the button not being there — so Settings offers it only once a customer
exists.

**That condition is `hasBillingAccount`, not `isActive`.** A cancelled or
past-due subscription is exactly when somebody needs to reach their invoices and
their card, and hiding the door then would hide it in the only situation that
makes it urgent.

Nothing is written, so nothing is committed.

**Errors:** `401`, `403`, `404`, `503 billing-not-configured`.

#### `POST /api/v1/billing/webhook`
Stripe telling us what happened. **No session auth.**

**The only writer of subscription state in the entire system.** No endpoint a
browser can reach sets `subscription_status`. The redirect after checkout is a
UX nicety; this is the moment the database changes. That is why a signed-in
account's Settings reflects reality even if the browser tab was closed
mid-payment.

**What authenticates it:** an HMAC over the exact bytes of the request body,
keyed on `STRIPE_WEBHOOK_SECRET`, verified with the SDK's
`stripe.Webhook.construct_event`. That is a stronger claim than a session cookie
makes, because it is a claim about the payload rather than about the sender. The
SDK also enforces a replay window (Stripe's 300s default), so a captured header
is not a standing key.

**The raw body is verified, not a parsed model.** The signature covers the bytes
Stripe sent. Parsing and re-serialising first would verify against a payload
that is equal as JSON and different as bytes — which fails for something as
ordinary as key order. This is the commonest way webhook verification is written
wrongly, and it fails closed and confusingly.

**With `STRIPE_WEBHOOK_SECRET` unset the endpoint REFUSES** — `503
billing-not-configured`, naming the variable. It does not fall back to trusting
an unverified payload. That is deliberately the opposite of the answer
`services/email.py` gives for its own unset key, where not sending — and
saying so — is the supported answer: there, the consequence of the
unconfigured path is a message nobody receives; here it would be believing a
stranger about money.

**Handled types:** `checkout.session.completed` (only with `mode == "subscription"`
and a `subscription` id; any other checkout is ignored),
`customer.subscription.created|updated|deleted` and, since 2026-10-04,
`customer.subscription.trial_will_end`. Any other type is ignored. (Stripe sends
`trial_will_end` only if the endpoint is subscribed to it; nothing depends on it.)

**The response is now the typed `WebhookAck`,** always 200 after a valid signature:
- applied → `{"received": true, "handled": true}`;
- duplicate → `{"received": true, "handled": false, "duplicate": true}`;
- stale → `{"received": true, "handled": false, "stale": true}`;
- ignored or unmatched → `{"received": true, "handled": false}`;
- `customer.subscription.trial_will_end` for a known agency →
  `{"received": true, "handled": true}`, see below.

**`customer.subscription.trial_will_end` — 2026-10-04.** Stripe sends it a few days
before a trial ends. It is **a log line and nothing else**: `billing.trial_will_end`
with `agency_id` and `subscription_id` (ids only). It changes no state, does **not**
move the `stripe_event_at` watermark, and leaves **no ledger row**, which is how the
ledger treats every event that changes nothing (an unhandled type, a non-subscription
checkout, an event with no `created`): its rows are for events that were applied, or
were stale and so must not be applied on a retry. A redelivery logs the line again. For
an agency this database does not know it is `unmatched`, as for any type.

**The trial's end is stored from every `customer.subscription.*` event**, as Stripe's
`trial_end` (`agencies.subscription_trial_end`), whatever the status: a trial that
converts, is cancelled, or fails its first charge goes through the same events as any
other subscription (`trialing` → `active` is the `customer.subscription.updated` that is
the first payment; `trialing` → `canceled`/`incomplete_expired`/`past_due` likewise).

**Once:** each handled event id is recorded in `stripe_webhook_events` in the
same transaction as the change it makes. A redelivery is answered `duplicate`
and changes nothing. An event that matches no agency is not recorded, so Stripe's
"Resend" applies it once the agency is linked.

**In order:** the agency row is locked `FOR UPDATE`.
- A `customer.subscription.*` event created strictly before `agencies.stripe_event_at`
  (the newest subscription event applied) is `stale`.
- Only `customer.subscription.*` events advance that watermark; checkout does not,
  because it carries no subscription state of its own.
- Events in the same second apply in arrival order, except for a state-machine
  guard on the same subscription id: a `canceled` or `incomplete_expired` status
  is never overwritten, `incomplete` is never written over another status, and
  `checkout.session.completed`'s `active` is never written over `trialing`
  (2026-10-04). A guarded event is also `stale`.
- An event without a numeric `created` is ignored.

**Why checkout's `active` is kept off `trialing`.** `checkout.session.completed`
carries no subscription status, so it writes a guess, `active`; for a trial's checkout
nothing was paid and that guess is wrong by construction. Stripe does not order it
against `customer.subscription.created` (`trialing`). If `created` lands first the agency
is already `trialing`, and the guard makes the checkout event `stale` (it has nothing to
add: the ids are already stored). If checkout lands first it writes `active` for the moment
until `created`, which is never stale on its account (checkout does not move the
watermark) and overwrites it with `trialing` and the trial's end. Either order ends
`trialing`. Only `trialing` is protected: the guess still overwrites every other
status, as before.

**Response `200` with the typed `WebhookAck`:**
```json
{ "received": true, "handled": true }
```
```json
{ "received": true, "handled": false, "duplicate": true }
```
```json
{ "received": true, "handled": false, "stale": true }
```
```json
{ "received": true, "handled": false }
```

**An unrecognised event type is a `200` with `handled: false`,** not an error. A
Stripe account sends whatever it is configured to send, and answering non-2xx to
an event nobody wants makes Stripe retry it, back off, and eventually mark the
endpoint unhealthy — degrading delivery of the events that do matter. An event
naming a customer this database has never heard of is the same: acknowledged and
ignored, because asking Stripe to retry forever would not conjure a row.

**Errors:** `400 invalid-webhook-signature` (missing, malformed or wrong
signature; also an unparseable body), `503 billing-not-configured`.

### Dashboard

#### `GET /api/v1/dashboard`
**Auth required.** Scoped to the caller's agency.

**Query:** `limit` (1–50, default 10) — how many recent scans to include.

**Response `200`**
```json
{
  "agency": { "...": "AgencyOut" },
  "seats": { "used": 1, "limit": 3 },
  "clientCount": 0,
  "scanCount": 0,
  "recentScans": [],
  "isEmpty": true,
  "scoredScanCount": 0,
  "sharedScanCount": 0,
  "gettingStartedDismissed": false
}
```

`isEmpty` is true when the agency has no clients and no scans, so the frontend
can show the onboarding path rather than an empty table.

**The getting-started facts — Epic 19.** Three more fields in the shape of
`clientCount` and `scanCount`, from which the dashboard derives its
getting-started checklist rather than the server storing per-step flags:

- `scoredScanCount` — scans of this agency with a `SCORED` score. Counted
  over the whole history, not the `recentScans` page, so a scored scan that
  has scrolled off the page still counts. `INSUFFICIENT_DATA` is not a score
  and is not counted. **A `failed` scan is not counted**, even if it kept a score
  row (a deadline that came after scoring): its score is never shown or counted
  (checklist 3.24).
- `sharedScanCount` — scans whose share link would open now: the test the
  public report routes apply to a token (a token is set, its end is after
  now, and the scan has not `failed`). **A link past its end is not
  counted, and neither is a failed scan's**, even while the token is still
  on the row for the agency to withdraw (checklist 3.42). Minting a link
  adds to the count; withdrawing one, a link reaching its end and a scan
  failing each take one off. The count describes the account as it is, not
  a history of links that once existed. A `cancelled` scan's link opens, so
  it is counted; nothing writes `cancelled` today.
- `gettingStartedDismissed` — whether someone at the agency has closed the
  checklist. The one stored fact; the rest are derived on read.

#### `POST /api/v1/dashboard/getting-started/dismiss`
**Auth required.** Any seat holder. Hides the getting-started checklist for
the whole agency — per agency, not per browser, because the checklist
describes the account and a teammate opening the same workspace should see
the same answer. It is not behind the admin gate because it changes what
nobody can do.

**Response `204`**, empty. Idempotent: a second call does not move the
timestamp and is not an error. There is no un-dismiss.

**Errors:** `401 authentication-required`.

Each entry in `recentScans` is a `ScanSummaryOut`:

```json
{
  "id": "scan_01J...",
  "clientId": "clnt_01J...",
  "clientName": "Northaven Dental",
  "clientDomain": "northaven-dental.example",
  "status": "succeeded",
  "errorCode": null,
  "compositeScore": "38.35",
  "createdAt": "2026-08-20T05:40:11Z",
  "finishedAt": "2026-08-20T05:43:02Z"
}
```

`compositeScore` is a **string-encoded decimal or `null`**. It is a string
because the value is `NUMERIC(5,2)` in Postgres and a JSON number would
reintroduce binary-float error on the wire, which `docs/scoring-spec.md`
determinism rule 3 exists to prevent. It is `null` both when a scan is unscored
and when scoring returned `INSUFFICIENT_DATA` — **the UI must render null as
"—", never as 0.** An unrunnable scan must never appear to a client as a bad
score. **It is also `null` for every `failed` scan**, whatever score row the scan
kept (checklist 3.24).

`errorCode` (2026-10-01) is the scan's own code, the same one
`GET /scans/{scanId}` returns, or `null`: why a `partial` or `failed` scan ended
that way (`SCAN_DEADLINE_EXCEEDED`, `ALL_ENGINE_CALLS_FAILED`,
`EXECUTION_FAILED`, `EXECUTOR_LOST`, `EXECUTOR_NEVER_STARTED`). The web turns it
into a sentence; it never shows the code.

Scans are ordered newest-first by `id`. IDs are ULIDs, so that is creation
order and the same column serves as the pagination cursor.

**Errors:** `401 authentication-required`.

### Clients (intake & classification) — Epic 2

#### `POST /api/v1/clients`
**Auth required.** §5.4 step 1: submit a URL, crawl it, classify its industry.

Runs **synchronously**. §7's acceptance criterion is a classified industry
within 30 seconds of submitting a URL; the measured path is a few seconds, so
one round trip is both sufficient and simpler than a polling protocol.

**Request**
```json
{ "url": "northaven-dental.com", "name": null, "classify": true }
```

`url` is permissive — a bare domain, a full URL, or any page on the site. It is
normalised server-side against the Public Suffix List. `name` is an optional
operator label; when absent, the classifier's extracted brand name is used,
falling back to the domain. `classify: false` creates the record without
spending an LLM call (used by tests and by Epic 10's bulk upload).

**Response `201`** — `ClientDetailOut`:
```json
{
  "id": "clnt_01J...",
  "agencyId": "agcy_01J...",
  "name": "Northaven Dental",
  "domain": "northaven-dental.com",
  "kind": "prospect",
  "industry": "dental practice",
  "industryNiche": "cosmetic and implant dentistry",
  "brandName": "Northaven Dental",
  "classificationStatus": "classified",
  "classificationReasonCode": null,
  "industryConfidence": "high",
  "industryConfidenceScore": "0.920",
  "classifiedAt": "2026-08-20T18:04:11Z",
  "classifierModel": "claude-opus-5",
  "crawl": {
    "pagesFetched": 3,
    "urlsFetched": ["https://northaven-dental.com/", "https://northaven-dental.com/about"],
    "schemaTypes": ["LocalBusiness", "Dentist"],
    "wordCount": 1584,
    "h1Count": 1,
    "hasTitle": true,
    "hasMetaDescription": true,
    "detectedLanguage": "en"
  },
  "createdAt": "...", "updatedAt": "..."
}
```

**`classifierModel` and `classifiedAt`** (2026-10-04, launch checklist 3.71) name the
model that was asked to classify the client, and when. Both are `null` unless a model
was asked: for a `pending` client, and for one whose site was never shown to a model
(the crawl was refused or failed: `ROBOTS_DISALLOWED`, `ROBOTS_UNREACHABLE`,
`ADDRESS_NOT_PUBLIC`, `FETCH_FAILED`, `HTTP_*`, `BROWSER_ERROR`, the crawl's own
`TIMEOUT`; or the page had too little text, `INSUFFICIENT_CONTENT`). A call that was
made and failed (`PROVIDER_*`, the model's own `TIMEOUT`) still names the model, with
the time of the attempt. Classifying again replaces both with the new outcome's, `null`
included. Rows stored before 2026-10-04 carry both for refused and failed crawls too.

**`classificationStatus` is the field to branch on.** It has four values, and
three of them mean `industry` is `null`:

| Status | `industry` | Meaning |
|---|---|---|
| `pending` | `null` | Created with `classify: false`; not yet attempted |
| `classified` | **set** | Confident result |
| `ambiguous` | `null` | Crawled fine, but the evidence did not support a confident call |
| `unclassifiable` | `null` | Nothing was classified: the crawler could not read the site, the site is not a business site, or the classifying model could not answer (`classificationReasonCode` says which; the web shows "Could not classify" and one sentence per code, never the code) |

**The UI must never render a null industry as an empty field or a dash that
reads like data.** `ambiguous` is a distinct outcome that needs its own
treatment, for the same reason a null score is not a zero: a wrong industry
silently poisons Epic 3's competitor detection and Epic 4's prompt generation,
and neither has any way to detect that its input was wrong. This is enforced in
the database by `ck_clients_industry_matches_classification_status`.

`classificationReasonCode` explains a non-`classified` status:

| Code | Cause |
|---|---|
| `LOW_CONFIDENCE` | Model confidence below the 0.70 threshold |
| `NOT_A_BUSINESS_SITE` | Parked domain, error page, login wall, directory listing |
| `INSUFFICIENT_CONTENT` | Page carried too little text to classify |
| `FETCH_FAILED` | Site did not resolve or the browser could not load it |
| `HTTP_404`, `HTTP_403`, … | Site answered with that HTTP status (bot or geo blocking) |
| `PROVIDER_QUOTA_EXHAUSTED` | Anthropic credit balance exhausted |
| `PROVIDER_RATE_LIMITED` / `PROVIDER_UNREACHABLE` / `PROVIDER_ERROR` | Upstream model call failed |
| `PROVIDER_REFUSED` | Model declined to answer |
| `PROVIDER_SCHEMA_VIOLATION` | Model answered, but its answer did not fit the classifier's schema (2026-09-11) |
| `ROBOTS_DISALLOWED` | The site's robots.txt was read and forbids AVPScanBot its homepage, so nothing was read (2026-09-29) |
| `ROBOTS_UNREACHABLE` | The site's robots.txt, or that of an address the site sent the crawler to, could not be read at all: no answer (a timeout, a refused connection, a name that does not resolve, a response that has not finished within 10 s), a 5xx, a 429, or redirects that never reach a file. The crawler fetches nothing without it, as for `ROBOTS_DISALLOWED`, but the site forbade nothing (2026-10-03, launch checklist 3.41) |
| `ADDRESS_NOT_PUBLIC` | The site's address, an address the site sent the crawler to (a redirect hop or landing of a navigation, or a robots.txt redirect), or an address Chromium reports it connected to, is not on the public internet (private, loopback, link-local, carrier-grade NAT, multicast, reserved or unspecified, including those forms inside an IPv6 address), so the crawl stopped and nothing was kept (2026-10-01) |

**What the crawler does with robots.txt** (`ai_crawlers.crawl_policy`, RFC 9309 §2.3.1;
`ROBOTS_UNREACHABLE` changed the code reported, not what the crawler does): a 2xx is read
whatever its content type, over its first 512,000 characters, and its rules for AVPScanBot
(else `*`) decide; any other 4xx (404, 410, 403 …) means there is no file, so everything is
allowed; a 429, a 5xx, no answer at all, or redirects that never reach a file mean the file
cannot be read, so **nothing is fetched** and the outcome is `ROBOTS_UNREACHABLE`. Each
request the crawler's gate makes (robots.txt, a HEAD hop of the homepage's redirects, the
audit's sitemap) must finish within **10 s in total**, from the address check to its last
byte, and reads no more than it needs: robots.txt is streamed and dropped at its first
512,000 characters, a sitemap at its first 64 KiB (it is judged by whether it is XML, which
its first characters say). A request that has not finished by then is "no answer": for
robots.txt that is `ROBOTS_UNREACHABLE`; for a HEAD hop and the sitemap it is the failure
they always had (the address is left as it is; no sitemap was found). Only a 2xx answer's
body is read at all (a slow 404 is still "no file", a 5xx is its status), and only as
text the gate can decode: plain, or gzip or deflate coded once (it asks for those two and
no others) and inflated no further than four bytes a character of the cap, in UTF-8,
UTF-16, UTF-32 (those two with a byte-order mark), ASCII, ISO-8859-n or Windows-125x, under
any spelling Python knows for them (a response that names no charset is read as UTF-8).
The charset is checked by name before a byte of the body is read, because decoding is CPU
on the API's one event loop that no deadline can interrupt. Two codings stacked, any other
coding (`br`, `zstd`, …), a corrupt stream, any other charset (UTF-7 or Shift_JIS as much as
one that is not text at all), and a hop whose address is not http or https are "no answer"
too. When a chain of redirects runs out, the last Location's robots.txt is read before it
is handed on.
All the reads before the browser starts, together, must finish within **60 s**
(`PRE_BROWSER_BUDGET_S`): past that the run ends `TIMEOUT` and starts no browser. Rows
stored before 2026-10-03 carry `ROBOTS_DISALLOWED` for the unreadable cases too; nothing
recorded which a row was, so they are not re-labelled.

`BROWSER_BUSY` is never a classification reason (2026-10-02): a read that cannot
get the API's one browser is refused with a `429` (below) and the client is left as
it was, because a site that was never read is not a site that could not be read.

`industryConfidenceScore` is a **string-encoded decimal or `null`**
(`NUMERIC(4,3)`), for the same reason as `compositeScore`: a JSON number is an
IEEE double.

**`crawl` contains FACTS only** — counts, booleans, URLs, and schema.org type
names. Page text is never returned (the facts-only rule); the projection in
`routers/clients.py:_crawl_summary` names every field explicitly so adding one
to `CrawlSignals` cannot silently start returning it.

**Errors:** `401`, `409 invalid-url` (the address has no public domain, or its host is
not a valid hostname: below), `409 conflict` (domain already tracked by
this agency — carries `clientId`), `422 validation-failed`, and `429 rate-limited`
(see below; only with `classify: true`).

**The address must have a public domain and a valid hostname (2026-10-04, launch
checklist 3.67).** Otherwise `409 invalid-url`, with nothing stored and nothing
fetched. `detail` is one of two sentences, each plain, with no code, and neither quotes
anything the person typed (not the address, and not a user name or password written in
front of it). An address with no public domain name in it (an IPv4 address, `localhost`, a
bare suffix such as `co.uk`) gets "That address does not contain a public domain name.
Enter a website address such as example.com." An address whose host is not a valid
hostname, or that has no host at all, gets "That is not a valid website name. Names can
only contain letters, numbers and hyphens, with dots between the parts. Enter an address
such as example.com." EVERY label of the host counts, subdomains included, once an
internationalised label is encoded as punycode (IDNA 2008, with the `idna` package that
httpx, which fetches robots.txt, encodes a name with): each is 1 to 63 characters of
letters, digits and hyphens with no hyphen at either end, and the whole name is at most
253. A space, quote, bracket (an IPv6 literal's too), control character or underscore
fails it; so does an empty label (one trailing dot is the same name, a second is an
empty label); so does an internationalised label that encoding refuses; and so does a
label typed as punycode (`xn--...`) that is not valid punycode for a label IDNA allows,
or that does not encode back to what was typed. An internationalised name is stored as
it always was, lower-case Unicode (`bücher.de`, not `xn--bcher-kva.de`): the punycode
form is what is checked, not what is kept, and a name typed as punycode is stored as
typed. Pages are read by Chromium from `https://` and the stored domain.

An unreachable site is **`201` with `classificationStatus: "unclassifiable"`**,
not an error status. A site that will not load is a normal outcome for a tool
pointed at an arbitrary URL.

**One site read per agency at a time, and four at once (2026-10-02).** With
`classify: true` this request reads the site in the API's one browser. An agency
may have **one** such read queued or running at once, counted across
`POST /clients` (with classification), `POST /clients/{clientId}/reclassify` and
`POST /scans/{scanId}/audit` together, and only **four** agencies may at once.
Past either limit the request is refused with **`429 rate-limited`** and
`Retry-After: 60` before anything is created: "Your agency already has a site
being read. Try again in a minute." for this agency's own second read, and "The
crawler is busy with other pages right now. Try again in a minute." when four
agencies' reads are already inside (it says nothing about any agency). Another
agency's read is not affected below the cap, `classify: false` is not a read, and
**a scan's own audit is not counted and is never refused** by either. Checked
after the agency's own checks, so another agency's id is still a `404`. The counts
are held in the API process (one process per instance: `--workers 1`) and are
released however the read ends.

**The bounds (2026-10-02).** A read waits for the browser at most **60 s**. Past
that it is refused with the same `429` ("The crawler is busy with other pages right
now. Try again in a minute.") and **writes nothing**: no client is created here, a
reclassified client keeps its classification, and a hand-run audit keeps the one
stored. No client is left `unclassifiable` for it, because a site that was never
read is not a site that could not be read. Before it asks for the browser, its reads of robots.txt and the
homepage's redirects must finish within **60 s** in total, or it ends as `TIMEOUT` with
no browser started. Once it has the browser, one run is cut
at **266 s** for the three pages intake asks for (`crawl_run_cap_s`), ending as
`TIMEOUT` with nothing kept. A scan's own audit waits for the browser at most
**120 s** (it was 300 s until 2026-10-03; launch checklist 3.35): long enough for a run
ahead that finishes, not for one that hangs until its own cap cuts it (244.5 s for an
audit, 266 s for the crawl above). It records `BROWSER_BUSY` when that runs out, and the
scan goes on without a Technical Foundation; its own run is cut at **244.5 s**.

#### `GET /api/v1/clients/{clientId}/history` — Epic 9.20
**Auth required.** Every scan of this client that produced a reading, **oldest
first**. Returns `ClientHistoryOut`.

The read behind a client's own space (`/clients/{id}/sources` and
`/clients/{id}/rankings`). **It collects nothing, writes nothing, and computes
no new figure** — every row it reads was written by a scan that already ran.

Ordered oldest-first, the opposite of `GET /clients`, deliberately: a list wants
the newest thing at the top, a trend wants the earliest at the left.

**Why this exists rather than N calls to `GET /scans/{id}/report`**, measured
against real rows for a three-scan client:

| | Report path | This |
|---|---|---|
| Per scan | ~17.6ms warm | ~6.5ms |
| Round trips | N | 1 |
| Cited domains | ranked and **truncated for display** (13 of ~300 citations) | the full per-scan tally, capped at 40 |

The truncation is the decisive one: a Sources trend built from the report's
lists would silently be a trend over whatever survived a display cap, which
moves between scans.

**On what is and is not stored.** The cited-domain counts aggregate persisted
`engine_result_citations` rows. The per-rival figures have **no stored column at
all** — `CompetitorComparison` is derived on read by design
(`scoring_runner.score_scan`: *"a pure function of rows already persisted, so
storing it would create a second copy that can fall out of step with the
first"*). This endpoint calls `score_scan(persist=False)`, whose comparison the
report reads through `scoring_runner.compare_on_read` (a test holds the two
equal), so a figure here cannot disagree with the same figure on the report for
the same scan. Nothing is persisted, and so no `scoring.completed` is logged.

**The subject's own `shareOfVoice` is the stored Score's, as `composite` is**
(2026-10-05, the founder's decision), and is not recomputed on read: a figure derived from
the scan's competitor set as it stood on the day of the read could move after the scan,
beside a composite that had not. It is null when the scan was never scored or the score
left the dimension out. The rivals' figures stay derived on read, from the scan's own
competitor set, which nothing writes once the scan has started.

Scans that produced no reading (queued, running, failed, cancelled) are excluded
from `scans` and counted in `scansWithoutData`, so a client with four scans and
one usable one does not look like a client with one scan.

**No per-competitor composite**, and there never will be: sentiment is
classified toward the subject only and technical foundation is the subject's own
site, so 25% of the weight has no rival input.

**Errors:** `404 not-found` for an unknown id and for another agency's client —
the same rule as `GET /clients/{clientId}` above, and for the same reason.

#### `GET /api/v1/clients/{clientId}/auto-rescan` — F2, 2026-10-06
**Auth required. Reads, starts nothing.** Whether this client is rescanned every month, as

#### `PUT /api/v1/clients/{clientId}/auto-rescan` — F2, 2026-10-06

started 30 or more days ago. The allowance, the one-open-scan rule and the reaper apply; a refusal
is a skip recorded on the client, never a retry loop. Off: nothing is started and the notice is
cleared. On again as another user hands the rescans to that user and clears the notice; on again
as the same user changes nothing. **Errors:** `401`; `403 permission-denied` (a member); `404`
with the body an unknown path gets when the API has `AUTO_RESCAN_ENABLED` off, and
`404 not-found` for an unknown id or another agency's client; `422 validation-failed`.
Automatic scans have `trigger: scheduled`.

#### `POST /api/v1/clients/{clientId}/competitors/detect`
**Auth required.** §5.4 step 2: SERP discovery + AI co-citation discovery,
deduped and ranked.

Runs **synchronously** and **costs money** — roughly six SerpApi searches and
four model calls per run — so it is explicitly operator-triggered rather than
implicit in intake.

**Since Epic 9.17 it is no longer the only way a set gets created.**
`POST /clients/{clientId}/scans` guarantees the scan it starts has one: reusing
the scan's own set, else adopting the client's next list, else carrying the client's
most recent set forward, else running this detection. This endpoint remains the way to *re-run* detection
deliberately — the chain never re-detects for a client that already has a set,
precisely so it cannot spend quota or overwrite an operator's correction on its
own.

**A confirmed other site is not proposed as a rival** (M1 task 1.1, 2026-10-09). A candidate whose
domain, in DNS form, is in the client's confirmed other sites or in those of an active rival on
the client's current list (its next list, else its latest scan's set) is not written, and one
log line per skipped candidate is written: `competitors.skipped` with `reason`
`confirmed_other_site`, `client_id` and `domain`. The response has no new field.

**Where the result goes** (launch checklist 3.78/3.79, 2026-10-05). Into the client's
**next list**, not a scan's set: the response is that list, with `scanId` null because it
belongs to no scan yet, and the next scan that starts adopts it (`POST
/clients/{clientId}/scans`, below). **A scan's own set never changes once the scan has
started**, so a run touches neither a finished scan's set nor a running one's. It used to
write the open scan's set, which a running scan had already read. With no next list yet,
one is made as a copy of the client's latest set (rows, hand edits and struck rivals
included) and detection merges into the copy, so rivals an operator named or struck stay
named and struck. Before this, a run for a client whose latest scan had finished started
a fresh set on the new open scan, and the hand edits in the finished scan's set were not
in it. A client with no set at all starts from an empty list. The scan this route opens,
or reuses, is unchanged: an open QUEUED row a later scan reuses, carrying no set until it
runs. The plan, the 24-hour day and every refusal below are unchanged.

**For paying agencies since 2026-10-04** (launch checklist 3.61). The founder's
decision: the route is allowed for an agency whose subscription is `active` or
`trialing`, and for the platform operator; everyone else gets a plain refusal. The
per-client day below stays for those who are allowed, and a scan's own detection is
unaffected. The reason is 3.53's security review: the day caps a client, not an agency,
and an account can add clients without a classification call and detect once on each,
about six paid searches a time out of a quota the whole platform shares. A press is
allowed when any one of these holds:

- billing is **not configured** on the deployment: the scan allowance's own switch
  (`STRIPE_SECRET_KEY` and `STRIPE_PRICE_ID` both set means billing is configured; with
  neither, or only one, the route is open, because nobody could subscribe there);
- the agency is **paid up**: `subscription_status` is `active` or `trialing`
  (`isActive` on `GET /agencies/{agencyId}/billing`), whichever of its seats presses the
  button, with or without a linked Google identity;
- the signed-in user is the **exempt operator**: an address in
  `SCAN_ALLOWANCE_EXEMPT_EMAILS` **and** a linked Google identity, never the address
  alone, and that user only, not the agency's other seats.

Anything else (no subscription, `past_due`, `unpaid`, `paused`, `incomplete`,
`canceled`, or a status nobody has decided about) is refused with
`402 subscription-required` and one sentence that is the same in every case and names no
status and no code. The plan is checked **after the client is found**, so another
agency's client is a `404` whatever the caller's plan, and **before the day is taken**, so
a refused press makes no search, opens no scan and spends none of the client's day: a
lapsed agency whose day is already taken is told about its plan and not about the day.
It reads the agency's stored status and never asks Stripe, takes no lock and touches no
Redis key. A scan's own detection is not this route: `POST /clients/{clientId}/scans`
still detects for a client that has no competitor set, on any plan the scan itself is
allowed to start on. Nothing new to set on Render: the switch and the operator's
exemption are the scan allowance's own settings, and where billing is configured an
agency without an active plan can no longer press this button once this is deployed.

**Once per client per 24 hours** (2026-10-03, launch checklist 3.53). The founder's
decision: once per client per day from this button, and always allowed as part of a
scan. A second press for the same client inside 24 hours is refused with `429` and
does nothing: no search is made and no scan is opened. The day is taken when a run
**starts**, so a run that then fails (SerpApi down, an error writing the set) still
counts: its searches may already be spent. The check runs after the client is found,
so another agency's client is still a `404` and cannot spend this client's day, and
another client of the same agency has a day of its own. A scan's own detection (the
chain above, for a client with no competitor set yet) never goes through this route:
it is not refused by the day and does not use it up, and neither does `PUT` below.
The day is one Redis key per client (`rl:detect_competitors:client:{digest}`, the
client id hashed as the credential routes hash theirs), set with `SET NX PX 86400000`
in one atomic step, so two presses at once cannot both run. It is a fixed window: it
ends when the key expires. With Redis down the route refuses with `503` rather than
run unmetered, because a run spends paid searches. Nothing to set on Render.

**`scanId` is null** for the client's next list, which is what this route, `GET` and `PUT`
answer with while the client has one: it belongs to no scan until the next scan adopts it.
It is a scan's id only for a set that belongs to a scan, which `GET` returns when the client
has no next list.

**`detectionConfidence` is null, not zero, when only one signal ran.** Zero means
"two independent signals looked and agreed on nothing"; null means agreement was
never measurable. Rendering null as `0%` would be a false claim about evidence
that does not exist — the same distinction as a null score vs a zero score.

**`status`:**

| Status | Meaning |
|---|---|
| `ok` | Usable set with cross-signal agreement |
| `weak_signal` | Ran, but fewer than 3 rivals, no corroboration, or only one signal available. Show it, flag it, invite an override. |
| `no_signal` | Neither signal produced a usable candidate. `competitors` is `[]`. |

**`detectionSource`** is `serp`, `co_citation`, `both`, or `manual`. `both` is
the strongest evidence available: two methods that fail differently agreed.

**Measured precision by source** (10-URL verification, build-log Epic 3.4):
`both` 100%, `co_citation` 100%, `serp`-only **45%**. Treat a `serp`-only rival
as a suggestion, not a finding.

**`usedIndustrySeed`** records whether `Client.industry` seeded the queries.
Industry classification confidence is uncalibrated (Finding 2, open), so when an
operator reports a bad set the first question is whether a bad industry label
seeded it — this makes that answerable without re-running.

#### `PUT /api/v1/clients/{clientId}/competitors`
**Auth required.** Replace the client's competitor list by hand.

```json
{ "competitors": [ { "name": "Zendesk", "domain": "zendesk.com" } ] }
```

**It writes the client's next list, never a scan's own set** (launch checklist 3.78/3.79,
the founder's decision of 2026-10-05). The saved list is for later scans: the next scan that
starts adopts it whole, and **a scan's own set never changes once the scan has started**.
So a save moves nothing a finished scan shows: not its list, its report, its score, its
client-history figure (`GET /clients/{clientId}/history`) or an explicit
`POST /scans/{scanId}/score`. A rival named after a scan finished counts only for later
scans. A scan that is `queued` when the list is saved adopts it when it runs. `scanId` is
null in the response: the list belongs to no scan until one adopts it.

Where a save lands, in order:

1. the client's next list, if it has one: edited in place, under a row lock that an
   adopting scan takes too, so a save that arrives while a scan is adopting the list either
   finishes first or waits, and never writes the set once it is a scan's (it then starts
   a new next list from what is now that scan's set);
2. else a **copy of the client's latest set** (the copy a scan carries forward: rows, hand
   edits and struck rivals), with the replacement applied to the copy;
3. else, for a client with no set on any scan, an empty next list that a non-empty
   replacement fills.

Two first saves at once leave one next list: the second finds the first's and writes that.

**`domain` is checked like a client's own, and never reduced** (launch checklist 3.81). A blank
or missing `domain` is no domain, as before. Anything else is lower-cased, and ONE trailing dot
and ONE leading `www.` are dropped; it is accepted only when what is left is exactly its own
registrable domain under the hostname check client intake uses, and that is what is stored
(`WWW.Rival.com.` is stored as `rival.com`; an internationalised name is stored in the spelling
it was typed, Unicode (`bücher.de`) or punycode (`xn--bcher-kva.de`), and the two are not
converted into each other). A page, a path, a scheme, a port or a subdomain
(`https://www.g2.com/products/x`, `shop.rival.com`) is refused, not cut down to the site it would
name. A domain equal to the client's own (compared in its checked form, so a client stored as `www.acme.com` is `acme.com`, and either spelling of an internationalised name) is refused too. The web editor's Add refuses a pasted page (a `/`, `:`, `@`, `?`, `#` or a space) with the same sentence before Save; the server stays the authority. Every refusal is **`422
validation-failed`** before anything is written, the rest of the list included, with
`errors[].field` `competitors.<index>.domain`, `errors[].type` `invalid_domain` for each of the five
below, and `errors[].message` one plain sentence that quotes nothing typed:

- not a hostname: "That is not a valid website name. Names can only contain letters, numbers and
  hyphens, with dots between the parts. Enter an address such as example.com."
- no public domain in it: "That address does not contain a public domain name. Enter a website
  address such as example.com."
- a page, path or subdomain: "Enter just the domain, like rival.com: no https://, page path or
  subdomain."
- the client's own domain: "That is this client's own domain."
- a platform or publisher: "That is a platform or publisher, so it cannot be added as a rival."

**A rival at a confirmed other site is refused** (M1 task 1.1, the founder's decision of
2026-10-09). A rival whose domain, in DNS form, is in the client's confirmed `otherSites`, or in
those of another rival **this save keeps** (with the sites that rival would carry: kept while its
host stays, none when the save moves it to another host or strikes it), is a `422
validation-failed` with `detail` "One or more fields were invalid.", before anything is written.

brand name (else its name) or the other rival's name: "rmit.edu.vn is confirmed as RMIT
University's other site. Remove it there first." It is made after the client's own-domain check
and before the `404`/`409` checks of the save. The web editor shows it as it shows the others.

**A platform or publisher is refused** (launch checklist 3.90, the founder's decision of
2026-10-06). After the checks above, the domain as it would be stored must not be on the list of
domains detection itself never proposes as rivals (`NON_COMPETITOR_DOMAINS` in `services/serp.py`,
compared as `is_plausible_competitor` compares): review sites and software directories, social
networks and forums, wikis, local directories, marketplaces, publishers and press, job boards and
company databases, search engines and the large platforms (an app store is its operator's domain,
`apple.com` or `google.com`). Stored as a rival, such a domain would type every citation of that
platform as the rival's. So `g2.com`, `WWW.LinkedIn.com.` and `wikipedia.org` are refused with the
sentence above, whatever their spelling. The match is exact: a regional variant (`amazon.co.uk`)
is refused only if the list holds it, and a name that only contains a listed one (`g2labs.com`) is
a rival as before. A platform's own page or subdomain (`apps.apple.com`) is still refused as a
page, with that sentence. The check is part of request validation, so it comes before the
client's own-domain check, which needs the client: a list with a row of each kind is refused for
the platform row first. A rival can still be named without a domain. **Nothing already stored is
changed or rechecked on read:** a list an older version stored with a platform domain on a row is
returned as it is, and is refused when it is saved again, naming that row, until the row is
removed or its domain is cleared.

No new problem type.

**A rival's confirmed other sites** (M1 task 1.1, `GET`/`PUT /clients/{clientId}/other-sites`)
stay on a row this save keeps at the same **host**, and are cleared when the save gives that row
another host, or none: they were confirmed against the old one. The same host in another
spelling is the same host (`xn--bcher-kva.com` for `bücher.com`; compared in DNS form,
`intake.dns_form`), so a rival saved again under the other spelling keeps its sites. A rival
added by the save starts with none.

Replaces wholesale rather than patching rows: an operator correcting a bad
detection is asserting "these are the rivals", and reconciling that against
auto-detected rows invites a half-applied state.

Everything supplied is marked `isManualOverride: true` and **survives later
re-detection**, keeping the top ranks. An empty array clears the list and returns
`status: "no_signal"`.

**Anything currently in the set and not sent back is STRUCK, and stays struck.**
A struck rival is recorded rather than deleted, so a later detection run that
surfaces it again does not reinstate it. Until Epic 3.6 it was simply deleted,
which recorded nothing: additions survived re-detection and removals silently
reverted, so half of "correcting a set" did not hold. Struck rivals never appear
in any response — they are bookkeeping for the next detection run, not
competitors.

Re-sending a struck rival revives it, so an operator can change their mind.

**`detectionConfidence` is cleared to null.** It measures agreement between two
automated signals, and neither produced this set — keeping the old value would
attach a corroboration claim to rows that were never corroborated.

⚠️ **Known, open:** a later *re-detection* sets `detectionConfidence` again from
its own run, and that figure describes only the rows detection found — not the
operator's. The report then presents one corroboration figure for a set that is
part-detected and part-hand-set. Changing this means redefining what the field
measures, which is a scoring-semantics decision rather than a UI one. Recorded
in build-log Epic 3.6.

**A client with no set on any scan** (launch checklist 3.78, 2026-10-05). A non-empty list
now makes the client's next list, recorded as every hand edit is: each row `manual` and
`isManualOverride: true`, `status: "ok"`, `detectionConfidence: null`, no `detectedAt` (no
detection ran). The scan that starts next adopts it, so detection does not run for that
client. Two cases are still the `404` and write nothing: a client with no scan at all, and
an empty list (a set with no rivals would be copied by every later scan and stop detection
ever running for the client; there is nothing to clear).

**`409 conflict` while the client's most recent scan is `running`**, on every path,
detail "A scan of this client is running. Name the rivals after it finishes." A running scan
may or may not have taken the client's list yet, and a save cannot say which, so nothing is
written. A `queued`, `succeeded`, `partial`, `failed` or `cancelled` latest scan is no reason
to refuse. The scan the check reads is scoped to the client's own agency.

Max 10 competitors. **Errors:** `401`; `404` for an unknown client or another agency's,
and for the two cases above, with the same sentence as `GET` above; `409` (above); `422`.

**CORS:** `PUT` was missing from `allow_methods` until Epic 3.6. This is the only
PUT in the API, nothing in a browser called it until the override UI shipped, and
the test suite drives the app through `ASGITransport`, which never issues a
preflight — so the endpoint was unreachable from a browser for five epics while
its own tests passed. `tests/test_cors.py` now derives the allowed method list
from the registered routes.

### Scans (prompt generation & engine execution) — Epic 4

#### `POST /api/v1/clients/{clientId}/scans`
**Auth required.** §5.4 steps 3–4: generate a prompt set, run it against every
engine, extract and persist facts.

**`402 /problems/scan-limit-reached` since 2026-09-28.** One free scan per
agency for life, forty a month on the plan; the body carries `code`
(`SCAN_LIMIT_FREE_USED` / `SCAN_LIMIT_MONTHLY`), `scansUsed`, `scanLimit`
and, for the monthly case, `periodResetsAt`. Enforced here, server-side,
under a `SELECT … FOR UPDATE` on the agency row that the scan's own commit
releases, so two concurrent requests cannot both take the last slot. Off
when billing is not configured. A scan already running is returned as
before; the open queued scan a run adopts is not counted against starting
it. Prompt re-runs are not scans and stay under their own throttle. Viewing,
sharing and exporting reports is never gated.

**`SCAN_LIMIT_VERIFY_REQUIRED` since 2026-09-29.** The free scan needs a
requesting user with a linked Google identity. A password-only user in a
free agency is refused with this code — under the same row lock as the
other two, **before the count is consulted** (so a password-only agency
that never scanned is not told its free scan is used), and with no scan row
created. Checked per user, not per agency: a password-only teammate is
refused where a Google-linked owner of the same agency is not. Paid agencies
and exempt operators are unaffected. The way through is Continue with Google
on the same address, which links the account by its Google-verified email;
`GET /agencies/{agencyId}/billing` says in advance, as
`freeScanRequiresGoogle`.

```json
{
  "type": "/problems/scan-limit-reached",
  "title": "Scan limit reached",
  "status": 402,
  "detail": "The free scan needs a Google sign-in, so that one person gets one. Continue with Google using the same address you sign in with here, or subscribe.",
  "instance": "/api/v1/clients/clnt_01.../scans",
  "code": "SCAN_LIMIT_VERIFY_REQUIRED",
  "scansUsed": 0,
  "scanLimit": 1,
  "periodResetsAt": null
}
```

**Asynchronous since Epic 9.5.** Returns `202` immediately with a QUEUED scan;
the pipeline runs out of band. It used to run inline and answer `201` with the
finished scan, which meant the row sat in an uncommitted transaction for its
whole duration — Epic 9.2 measured ~303s for this endpoint — and was therefore
invisible to every other request, including the dashboard.

**RUNS THE WHOLE PIPELINE SINCE EPIC 9.17, NOT JUST THE ENGINE LOOP.** This
endpoint used to generate prompts, run them against the engines, and stop.
Competitor detection, the technical audit, scoring and fix generation each had
their own endpoint and none of them was ever called automatically, so every
scan a real user started produced a report reading "Not scored",
`NO_COMPETITOR_SET` and `TECHNICAL_FOUNDATION_NOT_MEASURED`. The phases were
built and tested; nothing ran them.

The chain, in `services/scan_executor.py::execute_scan`:

| # | Phase | Notes |
|---|---|---|
| 1 | **Competitor set** | the scan's own set (`existing`) → **adopt the client's next list** (`adopted`: what `PUT` or the button's detection wrote since the last scan) → carry forward the client's latest set (`carried_forward`) → detect (`detected`). Detection, the only branch that spends SerpApi quota, runs **once per client**. |
| 2 | **Prompt generation + engine loop** | Unchanged. |
| 3 | **Technical audit** | Needs only the client's domain. |
| 4 | **Scoring** | Reads the audit, so Technical Foundation is now included rather than excluded as `NOT_YET_MEASURED`. |
| 5 | **Fix generation** | Reads the score, the audit and the competitor set. |

**Competitor detection runs BEFORE the engine loop, not after.** `run_scan`
reads the competitor list at its top and feeds it into prompt generation *and*
fact extraction — which is what produces `position`, `brandsMentioned`, Share of
Voice, and the `competitorId` on every mention and citation. A scan run without
a set does not fail; it reports `succeeded` with the subject at position 1 of 1
in every answer. A set written afterwards would be a set nothing had used.

**A competitor set is carried forward onto each new scan rather than
re-detected; detection runs only for a client with no set on any scan** (in practice its
first scan; a set emptied by hand is carried forward empty). `CompetitorSet` hangs off a *scan*, so a client's second scan
would otherwise start with no rivals. Re-detecting instead would spend six
SerpApi searches per scan against a 250/month quota **and** discard an
operator's `PUT /clients/{clientId}/competitors` correction, because
`persist_detection` preserves manual rows only within the set it is writing.
Suppressed tombstones are carried too, so a struck rival stays struck.

**A list saved or detected since the client's last scan is adopted instead** (launch checklist
3.78/3.79): the client's next list becomes the scan's own set whole, not a copy, under a row
lock, and is logged as `competitors.adopted`. From then on it is that scan's set, and
**nothing writes it again**: everything the scan shows (its score, its report, its
client-history figure, an explicit re-score) reads it by the scan's id, so a rival named
afterwards counts only for later scans.

**One phase failing does not stop the others.** Each is attempted
independently and commits on its own; the report renders whatever is missing
exactly as it already does. A failed audit therefore yields a score with
Technical Foundation excluded, not a scan with no score.

**`status` now reaches a terminal value only after every phase has been
attempted**, which is a change a poller can observe: `succeeded` used to arrive
when the engine loop ended, roughly 30 seconds before the score and the fix list
existed. It now means the report is ready. Nothing else about the status
vocabulary changed, and the terminal value still describes the **engine** phase
— a failed audit is not a failed scan.

Still **costs real money** once it runs: 20–30 prompts across every engine, plus
a sentiment call per mention.

**One execution per scan.** A scan already `running` is returned as it is —
`202`, the same `id` — and no second executor is started. A `queued` scan
handed to two executors is run once: the executor claims it with a single
conditional `UPDATE` (queued → running) before its first paid phase, and the
one that loses the claim exits without touching the row.

**Request**
```json
{ "promptLimit": 6, "engines": ["claude", "claude_search"] }
```

Both fields optional. `promptLimit` (1–30) caps the generated set for cost
control; omit for a real scan. `engines` defaults to **every DEFAULT engine
that has a key configured** — Epic 21, narrowed 2026-09-12. Five have adapters
(`claude`, `claude_search`, `chatgpt`, `perplexity`, `gemini`); **four are
defaults** (`claude`, `chatgpt`, `perplexity`, `gemini`), and a deployment runs
the subset of those whose provider key is set (`ANTHROPIC_API_KEY`,
`OPENAI_API_KEY`, `PERPLEXITY_API_KEY`, `GOOGLE_AI_API_KEY`), in that order.
`claude_search` — Claude with web search — left the default set on 2026-09-12
by the founder's decision (it was 64% of a measured scan's cost); it still runs
when named explicitly in `engines`, and stored `claude_search` rows still
render. Duplicates are collapsed before anything is billed — `["claude",
"claude"]` is one engine.
Two refusals, both `422 validation-failed` before any scan row exists rather
than a failed scan after competitor detection has been paid for: an engine
the enum knows but no adapter backs (`google_ai_overview`, `copilot`), and an
engine with an adapter but no key, whose detail names the variable to set
(`No key configured for engine(s): gemini (GOOGLE_AI_API_KEY). Keyed: …`).
A registered engine WITH a key may be named even when it is not a default —
that is how `claude_search` runs since 2026-09-12. (The key check read the
default set until that day, when the two sets were the same; the suite
caught it refusing the engine the decision had kept runnable.)

**Response `202`** — `ScanOut`. Identity and status only.

```json
{
  "id": "scan_01J...", "status": "queued",
  "clientId": "clnt_01J...", "trigger": "manual",
  "promptCount": 0, "engineResultCount": 0,
  "startedAt": null, "finishedAt": null
}
```

`ScanOut`, **not** `ScanDetailOut` with empty fields: at `202` no prompt set has
been generated and no results exist, and a shape carrying `promptSet: null` and
`results: []` would leave a caller unable to tell "not generated yet" from
"generated, and empty".

The response always reports `queued` — it describes what was accepted, not how
far it has since progressed.

**Observing completion.** Poll **`GET /api/v1/scans/{scanId}`** (below), which
carries the prompt set and results once they exist. `status` moves
`queued → running →` one of `succeeded` / `partial` / `failed`.
`GET /api/v1/dashboard` shows the same statuses across an agency's scans.

**Reuse.** An open (`queued` or `running`) scan for the client is reused rather
than duplicated, so a detect-then-scan flow does not strand an empty scan.
*Concurrent* requests can still race into two scans — the partial unique index
that closes that is Epic 9.6, not yet built.

**Failure while running.** A pipeline that raises lands the scan at `failed`
with `errorCode: "EXECUTION_FAILED"` — an error of ours, and it never counts
against the allowance. A scan whose executor disappears — a deploy or a crash
— is failed with `errorCode: "EXECUTOR_LOST"` once its lease has gone unrenewed
for 180 seconds (a live executor renews every 30). The reaper that does it runs
on the `POST /clients/{clientId}/scans` start route and on the dashboard read,
not on a timer, and a `running` scan whose lease has expired stops holding an
allowance slot at once, reaped or not. A restart never counts. `EXECUTOR_LOST`
distinguishes "the process running this went away" from
`ALL_ENGINE_CALLS_FAILED`, where the pipeline ran and every engine failed.

**A scan that hits its deadline** — the executor stops a scan still running
2,400 seconds after it was claimed — keeps the answers that finished and ends by
what it has, with `errorCode: "SCAN_DEADLINE_EXCEEDED"` either way. When at
least half of its planned prompts (`promptCount`) have an answer — at least one
result that is `ok` or `answered_no_mention` — it ends `partial` and the scan
**counts** against the allowance (founder decision, 2026-10-01: 2 of 4 counts,
2 of 5 does not). The prompts that finished are stored, and scored if scoring
completes within its own 60-second budget (a deadline `partial` can have no
score); `engineResultCount` is the number stored (it can be fewer than
`promptCount` × engines). With fewer than half, or none, it ends `failed` and does
**not** count; the results that finished are still stored, and it is not scored
(when the deadline comes after the engine phase, a score made before it stays).
It also ends `failed`, uncounted and with the same code, when the executor
cannot complete this finalisation itself. A scan whose lease was already gone when
the deadline fired — the reaper had failed it — keeps the reaper's `failed` /
`EXECUTOR_LOST`. The audit, alerts and fix list that had not yet run do not run.

**A scan handed to an executor but never started** (typically after a deploy
restart) is failed with `errorCode: "EXECUTOR_NEVER_STARTED"` if it remains
`queued` for 15 minutes after submission. The reaper fails it on the
`POST /clients/{clientId}/scans` start route, on the dashboard read that
already reaps, and on `GET /scans/{scanId}`. A failed scan never counts against
the allowance, and starting the client again creates a fresh scan. A scan left
open by competitor detection alone is never failed this way.

**`GET /api/v1/scans/{scanId}` response** — `ScanDetailOut` with `promptSet` and
one `results` entry per **prompt × engine pair**.

```json
{
  "id": "scan_01J...", "status": "succeeded",
  "promptCount": 6, "engineResultCount": 12,
  "engineVersions": {
    "claude": "claude-opus-5/parametric",

  "promptSet": {
    "generatedBy": "claude-opus-5",

    "prompts": [{ "id": "prmt_01J...", "text": "...", "intent": "awareness", "position": 1 }]
  },
  "results": [{
    "id": "eres_01J...", "promptId": "prmt_01J...",
    "engine": "claude_search", "status": "ok",
    "mentioned": true, "position": 2, "prominence": "0.812",
    "sentiment": "positive", "sentimentConfidence": "0.900",
    "brandsMentioned": 5, "responseDigest": "3513cdb4a7e1...", "latencyMs": 26997,
    "brandMentions": [{ "entityName": "Zendesk", "isSubject": false, "position": 1 }],
    "citations": [{ "sourceDomain": "g2.com", "sourceType": "review", "citesSubject": false }]
  }]

```

**Prompts are interleaved by intent.** `position` follows that order, so any
prefix of the set is representative of the buyer journey. This matters for
`promptLimit`: without interleaving a capped scan would measure awareness only
while reporting a mention rate that looks whole.

**`responseDigest` is a SHA-256 of the answer, and the answer itself is never
stored or returned** (the facts-only rule). It exists so a re-scan can detect "the
answer changed" without retaining it.

**`status` on each result:**

| Status | Meaning |
|---|---|
| `ok` | Answered, subject mentioned |
| `answered_no_mention` | Answered, subject absent — **a finding, not a failure** |
| `truncated` | The engine ran out of room before finishing (Claude `max_tokens`, OpenAI `length`) — **not an answer, and not an absence**. `errorCode: ANSWER_TRUNCATED` |
| `paused` | The engine stopped to hand control back and nothing resumed it (a paused tool turn). `errorCode: ANSWER_PAUSED` |
| `rate_limited` / `timeout` / `error` | The call did not produce an answer |

A complete answer is an **allowlist** of the vendor's stop reasons, not a
blocklist: a stop reason the API has never seen lands on `error` with
`errorCode: STOP_REASON_UNKNOWN` rather than being read as an answer. Every
incomplete status counts as a failed call for the scan-level `partial` /
`failed` verdict below, and is excluded from the mention-rate denominator
exactly as `timeout` is.

**Scan-level `status`:** `succeeded` (no failed calls), `partial` (some engines
failed), `failed` (all failed, with `errorCode: ALL_ENGINE_CALLS_FAILED`).
`partial` exists so a report can say "one engine was down" rather than
presenting a depressed mention rate as fact. `partial` is also how a scan that
hit its deadline with at least half of its planned prompts answered ends: it then carries
`errorCode: "SCAN_DEADLINE_EXCEEDED"`, and its results are those of the prompts
that finished. They can ALSO include failed engine calls (each result's `status`
says which), so that code says the clock ran out and does not rule out an engine
having been down. With fewer than half of its planned prompts answered, or when the
executor could not complete the finalisation, that scan ends `failed` with the same
code. The allowance counts
`succeeded` and `partial` and never `failed`, whatever the `errorCode`.

**`position` is the subject's rank among detected brands by first appearance.**
Brand detection is scoped to the subject plus **known competitors** — never
open-ended entity extraction. A scan run before Epic 3 detection reports
position 1 of 1 for every mention, because there is nothing else to detect.

**Errors:** `401`, `404` (unknown client, or another agency's), `422`.

#### `GET /api/v1/scans/{scanId}`
**Auth required.** The scan with its prompt set and every engine result.
`404` for an unknown scan or another agency's — never `403`. For a `queued`
scan submitted more than 15 minutes ago, it fails that one scan with
`EXECUTOR_NEVER_STARTED` and returns it as `failed`.

**A `failed` scan is served as stored** (checklist 3.37 review). Its score is withheld
(checklist 3.24 and 3.30), and withheld means not computed and not shown. It does not
mean it cannot be derived from what the scan stored: this route returns the prompt set
(each prompt's `intent`) and every engine result (`status`, `mentioned`, `position`,
`sentiment`, `brandMentions`, `citations`), which are all the inputs Mention Rate, Share of
Voice and Sentiment are computed from. `GET /scans/{scanId}/results` and
`GET /scans/{scanId}/prompts` return the same rows. None of the three applies the
failed-scan rule today; whether they should is the founder's decision and is open.

#### `GET /api/v1/scans/{scanId}/results`
**Auth required.** Cursor-paginated engine results, ascending by id.
Separate from the scan detail because a full scan is 60+ rows with nested
mentions and citations.

**Query:** `limit` (1–200, default 25), `cursor`.

**A `failed` scan's results are served as stored**, `sentiment` and `mentioned` on each
included: see `GET /api/v1/scans/{scanId}`.

#### `GET /api/v1/scans/{scanId}/prompts`
**Auth required.** The generated prompt set, ordered by `position`.
`404` if the scan has no prompt set yet.

**A `failed` scan's prompt set is served as stored**, each prompt's `intent` included:
see `GET /api/v1/scans/{scanId}`.

#### `GET /api/v1/clients/{clientId}/scans`
**Auth required.** A client's scans, newest first. Cursor-paginated.

### Scores (AI Visibility Score) — Epic 5

#### `POST /api/v1/scans/{scanId}/score`
**Auth required.** Computes and stores the composite score for a scan.

**Makes no provider calls and costs nothing.** Scoring is pure arithmetic over
rows Epic 4 already persisted. Sentiment is read from `EngineResult.sentiment`,
never re-classified (scoring-spec.md rule 4) — that is what makes re-scoring
reproducible.

**Response `201`** — `ScoreDetailOut`:
```json
{
  "id": "scor_01J...", "scanId": "scan_01J...", "status": "scored",
  "composite": "66.49",
  "mentionRate": "83.33", "shareOfVoice": "41.18",
  "citationStrength": "60.00", "sentiment": "75.00",
  "technicalFoundation": null,
  "formulaVersion": "v5",
  "weights": {
    "citation_strength": "22.22", "mention_rate": "33.33",
    "sentiment": "16.67", "share_of_voice": "27.78"
  },
  "excludedDimensions": {
    "technical_foundation": "NOT_YET_MEASURED"
  },
  "averagePosition": "1.28", "positionCount": 36,
  "degradationFlags": ["TECHNICAL_FOUNDATION_NOT_MEASURED"],
  "reasonCode": null,
  "inputsDigest": "1f3a422c367d9c3f...",
  "competitors": [
    { "competitorId": "comp_01J...", "name": "Zendesk",
      "mentionRate": "100.00", "shareOfVoice": "35.29", "citationStrength": "100.00",
      "averagePosition": "2.65", "positionCount": 23 }
  ]
}
```

**All score values are string-encoded decimals.** A JSON number is an IEEE
double, which is precisely what scoring-spec.md rule 3 forbids.

**`averagePosition` / `positionCount` are reported, not scored** (v4,
2026-09-27). The mean 1-based ordinal of the brand among the brands an answer
named, over **awareness** answers that named it, and the count it is
averaged over — the subject's from `EngineResult.position`, each rival's
from `BrandMention.position`. Not a dimension: no weight, no sub-score, not
in `inputsDigest`, not on the stored row; derived on read like
`competitors`, so it is on `ScoreDetailOut` and not on the `ScoreOut` list.
**`null` with count `0` when the brand was never named on an awareness
prompt** — never `0`, which would read as ahead of first. The precedent is
Core Web Vitals in the technical audit: a measurement that varies between
runs is shown and moves no score. Measured on the `avp_dev` re-run pairs:
the subject moved 0.04–0.13 of a position; rivals on 9–22 answers moved by
up to 0.6.

**`weights` are the EFFECTIVE weights after exclusions**, not the §6 table.
They always sum to 100, so a stored breakdown re-sums against its own weights.
The §6 table lives in `docs/scoring-spec.md`.

**`excludedDimensions` is `{dimension: reason}`,** and the reasons are not
interchangeable:

| Reason | Meaning | How a report should word it |
|---|---|---|
| `NOT_YET_MEASURED` | Technical Foundation: the scan has no audit row. (Scores stored before 2026-10-05 also carry it for an audit that had failed; stored scores are not re-scored.) | "not yet checked" |
| `AUDIT_FAILED` | Technical Foundation: the scan's audit failed with a code the three `CRAWL_*` reasons below do not cover (`TIMEOUT`, `BROWSER_BUSY`, `BROWSER_ERROR`, `FETCH_FAILED`, `HTTP_<status>`, or no code), 2026-10-05 | "Technical check failed" |
| `NO_POPULATION` | Nothing to measure for this brand (no mentions → no sentiment) | "nothing to measure" |
| `NO_COMPETITOR_SET` | Competitor detection returned nothing | "no comparison was made" |
| `NO_AWARENESS_POPULATION` | The prompt set had no unprompted questions (v2) | "nothing unprompted to measure" |
| `NO_AUTHORITY_DATA` | No cited domain in this scan has an authority tier, so there is no input to measure Citation Strength with. v2.1–v2.2: fired on every scan, because no authority source existed at all; since v3 only when the scan's citations are all unclassified | "no authority source" |
| `NO_COMPETITOR_SET` (Citation Strength, v3) | Tiered domains were cited but no competitor set exists to normalise against — same code, same reason as Share of Voice | "no comparison was made" |
| `CRAWL_DISALLOWED` | Technical Foundation: the site's robots.txt forbids AVPScanBot, so the audit read nothing (2026-09-29) | "Blocked by robots.txt" |
| `CRAWL_ADDRESS_NOT_PUBLIC` | Technical Foundation: the site's address, or an address the site sent the crawler to, is not on the public internet, so the audit kept nothing (2026-10-01) | "Address not public" |
| `CRAWL_POLICY_UNREADABLE` | Technical Foundation: the site's robots.txt could not be read at all (no answer, an error, redirects that never reach a file), so the audit read nothing; the site forbade nothing (2026-10-03) | "Could not read robots.txt" |

An excluded dimension's weight is redistributed proportionally across the rest.
**A null sub-score is never a zero** — a brand nobody mentioned has not been
spoken of badly, and scoring it zero would punish the same absence twice.

**`degradationFlags`** record documented fallback paths, so a depressed number
can be explained: `WEAK_COMPETITOR_SET` (Epic 3 detection was weakly
corroborated — SERP-only precision measured ~58%), `NO_CITATIONS_IN_SCAN`,
`NO_COMPETITOR_SET`. `NO_AUTHORITY_DATA` appears as a flag only on scores
computed before `v2.1`, where Citation Strength was scored on a stand-in
(whether the brand's own domain was cited, against every domain cited in the
scan); from `v2.1` the dimension is excluded under that code instead, and
**`competitors[].citationStrength` is `null`** whenever the subject's is
excluded — a column means one thing. Since `v3` (scoring-spec.md) the
dimension is measured from a two-tier citing-domain authority input, and
each rival's `citationStrength` is measured exactly as the subject's, against
the same best-in-scan denominator, so the best-placed brand in the table
reads `100.00`. **Since `v5`** (2026-09-29) each brand's authority is the
mean, over awareness answers that name it, of that answer's authority sum —
not one sum over every citing domain, which grew with how often the brand
was named and tracked Mention Rate (Spearman 0.781, zeros excluded). A brand
named in no awareness answer reads `0.00`, not `null`.

**`status: "insufficient_data"`** with `composite: null` and
`reasonCode: "INSUFFICIENT_DATA"` when no engine call answered, a scan that has
not run yet for one. An unrunnable scan is never rendered as a bad score. A scan
whose every engine call failed ends `failed` (`ALL_ENGINE_CALLS_FAILED`) and is
refused, below, rather than scored as `insufficient_data`.

**`inputsDigest`** is a SHA-256 over the exact EngineResult and Competitor rows
scored. Two scores sharing a digest were computed from identical data, so a
changed composite is always attributable to either changed inputs or a changed
`formulaVersion`.

**Re-scoring is idempotent per formula version.** A unique constraint on
`(scanId, formulaVersion)` means re-running under the same formula refreshes
that row; a formula change inserts alongside it, leaving prior versions intact.

**Competitors carry no composite.** Sentiment is classified toward the subject
only and Technical Foundation is Epic 6, so 25% of the weight has no
per-competitor input. A composite on a different weight basis would not be
comparable to the subject's, which is the point of a comparison.

**A `failed` scan is not scored** (checklist 3.30, extending 3.24): `409
/problems/conflict`, `detail` "This scan failed, so it cannot be scored.", and no
Score row is written or refreshed. A failed scan has no score that is ever shown,
and a row it kept from before it failed (a deadline that came after scoring) is
neither changed nor deleted (scoring-spec.md rule 5). This route had no refusal
for a scan it could not score — a scan with no answered result still gets a `201`
with an `insufficient_data` row — so this is a new one, in the same `409` family as
`failed-scan-not-shareable`. The agency check runs first, here and on both reads
below: another agency's failed scan is the same `404` as an unknown one. The status
is read under a row lock (`FOR UPDATE` on the scan) held until the score is committed,
database reads and one insert or update with no outbound call, so a scan that fails
while this runs either fails first (`409`) or is scored first and fails after. `partial`,
`succeeded` and every other status are scored as before.

**A scan whose brand matches were made under an earlier rule is not re-scored** (checklist
3.97, founder decision): `409 /problems/conflict`, `detail` "This scan's brand matches were
made under an earlier rule, and answer text is not kept, so it cannot be re-scored under the
current one. Run a new scan instead.", and no Score row is written or refreshed. `formulaVersion`
v7 changed how a brand is MATCHED (a 2-4 character short form in capitals now counts), not only the
arithmetic, and answer text is never stored (facts only), so a scan matched before v7 cannot be
matched again. Scoring it here read its stored matches and wrote a row labelled `v7` from matches v7
did not make. What matched a scan is recorded on it (`Scan.matcher_version`, not in any response):
the run stamps the current matcher when it starts, a new row defaults to it, and a row written
without it (every scan that existed when the column was added, bar those the migration found scored
only by v7, and any an older instance inserts during a deploy) reads `pre-v7`, "not recorded". Any
scan not matched by the current rule is refused. The checks run in this order: the agency check
(another agency's scan is the same `404` as an unknown one, whatever matched it), then the failed
scan above (its own `409` wins), then this one. The rows the scan already has are neither changed nor
deleted (scoring-spec.md rule 5). A scan's own run still scores it at the end, and the other routes
(`GET .../score`, `GET .../scores`, the report) are unchanged. No request or response shape changes;
this is a new reason on the `409`.

**Errors:** `401`, `404` (unknown scan, or another agency's), `409` (failed scan, or a scan matched
under an earlier rule).

#### `GET /api/v1/scans/{scanId}/score`
**Auth required.** The most recent stored Score, with the competitor comparison
and the subject's average position derived from persisted rows on read
(`scoring_runner.compare_on_read`). Reading a score computes no score, writes
nothing and logs no `scoring.completed`: that line says a Score was written.
The rivals' figures are derived by the current formula with the platform's tiers
as they are at the time of the read; the stored Score is as it was when it was
scored, under its own `formulaVersion`.

**A `failed` scan has no score** (checklist 3.30, extending 3.24): the same `404
/problems/not-found` as a scan not yet scored, with `detail` "This scan failed, so
it has no score." — whatever Score rows the scan kept, which are not read, changed
or deleted. `succeeded` and `partial` scans are served as before.

**Errors:** `401`; `404` — unknown scan, another agency's, *"This scan has not been
scored yet."*, or *"This scan failed, so it has no score."*

#### `GET /api/v1/scans/{scanId}/scores`
**Auth required.** Every Score for the scan, newest first — the audit trail of
which `formulaVersion` produced which composite from which `inputsDigest`.

**A `failed` scan lists none** (checklist 3.30, extending 3.24): `200` with `[]`, the
same answer as a scan not yet scored, whatever rows the scan kept (rows under older
formula versions included), which are not read, changed or deleted. `succeeded` and
`partial` scans list as before.

### Technical audit — Epic 6

#### `POST /api/v1/scans/{scanId}/audit`
**Auth required.** Crawls the client's own site for structural signals and
records a verdict for each check.

**No model or search calls** — one page load plus two side fetches
(`robots.txt`, `sitemap.xml`). Cost is bandwidth and a few seconds.

**Response `201`** — `TechnicalAuditOut`:
```json

  "id": "taud_01J...", "scanId": "scan_01J...",
  "urlAudited": "https://helpscout.com", "status": "ok",

  "components": {
    "indexation": "100.00", "structuredData": "87.50",
    "contentFreshness": "75.00", "schemaPresence": "90.00"
```

**`checks` is the primary deliverable** (§7: "pass/fail + detail for each
check"), returned in display order — crawlability first, since it gates
everything else, then markup, then content, then lab measurements.
`status` is `pass | warn | fail | not_applicable | error`; `detailCode` is
machine-readable (`NO_STRUCTURED_DATA`, `META_ROBOTS_NOINDEX`,
`ROBOTS_TXT_DISALLOW`, …), never prose.

**`technicalFoundation`** is the §6 sub-score, a string-encoded decimal 0–100,
or `null` when the technical check could not be completed (`status: "failed"`).
**A check that could not be completed says nothing about the site's technical
foundation** — the two must not collapse into one number, which is why
`status: "failed"` exists.

**A `failed` scan's audit carries no `technicalFoundation` and no `components`**
(checklist 3.30, extending 3.24), on `POST` and `GET` alike: `technicalFoundation` is
`null` and `components` is `{}`, whatever the audit measured. The sub-score is a score
input and a failed scan shows no score; the component scores are what it is the weighted
sum of, so they go with it (the report empties `dimensions` the same way).
`componentWeights` stays. It is this audit's own weighting, the nominal weights with an
unmeasured component's share redistributed (`effective_weights(components)`), which says
how the audit was measured and is not a score. So does every fact about the site: the
checks and their values, the booleans, the counts, the dates, the schema types and
`excludedComponents`. The stored row keeps its values, and re-auditing a failed scan still
refreshes it. On `POST` the scan's status is read again after the crawl, so a scan that
fails while the audit runs is blanked too. The report blanks `audit.technicalFoundation`
through the same helper and carries no components at all. `succeeded` and `partial` scans
are unchanged, and the agency check comes first: another agency's failed scan is the same
`404` as an unknown one.

**Withheld here means not computed and not shown.** The facts about the site come back,
and the sub-score is computed from nine of them (`isIndexable`, `hasSitemap`,
`canonicalPresent`, `schemaTypes`, the four `has…Schema` flags and `contentAgeDays`), so
it can be worked out from this response (checklist 3.37 review). Whether the audit
routes should withhold more is the founder's decision and is open.

| `status` | Meaning |
|---|---|
| `ok` | Every component measurable; `components` and `componentWeights` filled. |
| `partial` | Read the page, but a component had no signal (e.g. no date anywhere). Scored on what was measurable; `components` and `componentWeights` show the measured ones, and `excludedComponents` lists those left out with their reason (e.g., `content_freshness: NO_DATE_SIGNAL_AVAILABLE`). |
| `failed` | The technical check could not be completed. `technicalFoundation`, `components` and `componentWeights` are all empty. |

A `failed` audit's `errorCode` says why. Three codes mean the crawler declined to
read the site rather than failed to:

- `ROBOTS_DISALLOWED` (2026-09-29): the site's robots.txt was read and forbids
  AVPScanBot the homepage. Page checks are `not_applicable` with that `detailCode`; a
  blanket `Disallow: /` under `User-agent: *` still fails `indexable` with
  `ROBOTS_TXT_DISALLOW`, because robots.txt itself was read.
- `ROBOTS_UNREACHABLE` (2026-10-03, launch checklist 3.41): the site's robots.txt, or
  that of an address the site sent the crawler to (a redirect hop, or where the browser
  landed), could not be read: no answer (a timeout, a refused connection, a name that
  does not resolve, a response that had not finished within 10 s), a 5xx, a 429, or
  redirects that never reach a file. The crawler fetches nothing then, exactly as for
  `ROBOTS_DISALLOWED` (RFC 9309 §2.3.1.4; a 429 is treated like a 5xx), but the site
  forbade nothing and the code says so. Until then these were stored as
  `ROBOTS_DISALLOWED`. Only what was actually read is reported, so what the checks say
  depends on whose file it was:
  - **The site's own robots.txt could not be read.** Every check but `cwv_inp` is
    `not_applicable` with that `detailCode`, `robots_txt_present` and `sitemap_present`
    included, because a file that did not answer is not a missing one: nothing here is a
    finding. The AI crawler table is `unknown` for every agent (`robotsReadable: false`).
  - **Another host's file could not be read**, the site's own having been read (a redirect's, or
    where the browser landed). The site's own checks are what they were: `robots_txt_present`
    passes, or is the `NO_ROBOTS_TXT` warning when its own file was a 404; `sitemap_present`
    passes, or is the `NO_SITEMAP_XML` warning when the sitemap it was allowed to ask for was
    not there. They are findings, as they would be for any audit, and the report lists them.
    The checks that needed the page are `not_applicable` with `ROBOTS_UNREACHABLE`.
  A missing file (a 404 or any 4xx but 429) is an answer, not this: the crawl goes on.
- `ADDRESS_NOT_PUBLIC` (2026-10-01): the run ends when the site's own
  address, a navigation's redirect hop or landing, robots.txt or its redirect,
  or an address Chromium reports it connected to is not on the public
  internet. Nothing is kept, so every check is `not_applicable` with that
  `detailCode`. A page's sub-resource or iframe, and the sitemap (or its
  redirect), refused before it is sent is skipped and the run goes on; a
  skipped sitemap reads as not found.

The other codes: `BROWSER_ERROR` (the browser failed, or a connection the egress
guard could not verify), `FETCH_FAILED` (the home page returned no response),
`TIMEOUT` and `BROWSER_BUSY` are reports about our attempt and never a finding
about the site, while `HTTP_<status>` (the home page answered 400 or above) is the
site's own answer. Each leaves one `site_reachable` check with the code as its
`detailCode`, `error` for ours and `fail` for an HTTP status, and excludes
Technical Foundation as `AUDIT_FAILED` (`NOT_YET_MEASURED` before 2026-10-05).

- `TIMEOUT`: one browser run is cut at **244.5 s** (`audit_run_cap_s`, the sum of
  every step at its own limit, so only a hang reaches it; 2026-10-02). Since then it
  also ends a read that never returns, such as the page read after the vitals wait,
  which has no timeout of its own, and the scan goes on (launch checklist 3.20). The
  facts robots.txt and the sitemap gave, read before the browser started, are
  kept; nothing the page gave is, because the cap can fall before the last egress
  check has said the page's facts may be kept. An audit whose reads before the browser
  (robots.txt, the sitemap, the homepage's redirects) have not finished within **60 s**
  in total (`PRE_BROWSER_BUDGET_S`, 2026-10-03) ends `TIMEOUT` too, with no browser started;
  it keeps the side files' facts if they had finished, and nothing otherwise.
- `BROWSER_ERROR` (2026-10-03): kept apart from a reading like `TIMEOUT`. The
  browser can fail after the page was read and before the last egress check said
  what it showed may be kept (or while it closes), and what the page gave up to
  then is not stored: only what robots.txt and the sitemap said, read before the
  browser started, is. So **no `failed` audit carries a page reading**: its schema
  types and flags, canonical, heading and word counts, freshness and vitals fields
  are always their empty values, for every code above.
- `BROWSER_BUSY` (2026-10-02): the API reads one page at a time in its one
  browser, and another read held it for the whole wait, so no browser was started
  for this audit. Only the audit inside a scan (phase 6) records it, after waiting
  **120 s** (300 s until 2026-10-03: a run ahead that finishes is waited out, one that
  hangs until its own cap is not); the scan goes on to scoring, alerts and fixes,
  without a Technical Foundation. The robots.txt and
  sitemap facts, read before the wait, are kept. `POST /scans/{scanId}/audit` never
  stores it: after **60 s** it answers `429 rate-limited` and the audit already
  stored for the scan is kept.

**Core Web Vitals are measured and reported, but carry NO weight in the
sub-score.** `lcpMs` and `cls` are single-cold-load **lab** measurements, not
field data — every CWV check carries `LAB_MEASUREMENT_NOT_FIELD_DATA`. Letting a
noisy measurement move a client-facing score would make the score noisy.
**`inpMs` is always `null`**: INP measures real user interaction latency, and a
crawler that never interacts cannot produce one. Real INP needs CrUX or RUM.

**`components` and `componentWeights` — 2026-09-30.** Both are populated for `ok`
and `partial` audits; `failed` audits omit both. (A `failed` *scan* omits `components`
only, whatever its audit measured; see above.) `components` holds each
component's score (0–100 decimal), calculated only from the measured signals; a
partial audit drops the one with no signal. `componentWeights` holds the weight
applied to each component after redistribution — when one is excluded, its weight
is split proportionally among the rest, exactly as `Score.excludedDimensions`
works. The weighted sum of `components` times `componentWeights` (÷100) equals
`technicalFoundation`, and a client can draw the latter as a Luminance Ledger
whose total lit height is the score. `excludedComponents` lists the components the
audit could not measure and the reason each was dropped (e.g., `content_freshness: NO_DATE_SIGNAL_AVAILABLE`).

**Scored components and their nominal weights inside Technical Foundation:**
indexation 30, structured data 25, content freshness 25, schema presence 20.
Indexation is heaviest because it is a precondition — a site telling crawlers to
stay out has no foundation whatever its markup looks like.

**Facts only** (the facts-only rule). Schema **type names**, presence booleans,
counts, durations and a day count. No page copy, no meta description text, no
Open Graph values — `openGraphTagCount` is a count, and the tags' contents are
never read.

One audit per scan, refreshed on re-run: a scan is a point-in-time claim about a
site, so a second audit is a correction rather than a new observation.

**One site read per agency at a time, and four at once (2026-10-02).** This route
reads the site in the API's one browser, so it shares the agency's single place, and
the four-agency cap, with `POST /clients` (with classification) and
`POST /clients/{clientId}/reclassify`: past either limit this is
`429 rate-limited` with `Retry-After: 60`. A read that waits more than 60 s for the
browser is refused with the same `429` and writes nothing: the audit already stored
for the scan is kept. See `POST /clients` for the limits and the bounds. The audit
inside a scan is not one of these and is never refused.

**Errors:** `401`, `404` (unknown scan, or another agency's), `429 rate-limited`.

#### `GET /api/v1/scans/{scanId}/audit`
**Auth required.** The scan's audit with checks in display order.
`404` — unknown scan, another agency's, or *"This scan has not been audited yet."*

**A `failed` scan's audit carries no `technicalFoundation` and no `components`** here too
(checklist 3.30, extending 3.24): `null` and `{}`, `componentWeights` and every other
field as stored. See `POST` above, including what "withheld" does not mean: the nine
facts the sub-score is computed from are returned.

#### Effect on scoring

Once an audit exists, `POST /scans/{scanId}/score` includes Technical Foundation
instead of excluding it as `NOT_YET_MEASURED`, and the effective weights return
to §6's table exactly (30/25/20/15/10). A **failed** audit leaves the dimension
excluded — a check that could not be completed is not a measured zero.
The exclusion reason is `NOT_YET_MEASURED` when the scan has no audit row, and
`AUDIT_FAILED` for a failed audit with any code but the three below (2026-10-05),
except `CRAWL_DISALLOWED` for an audit failed with `ROBOTS_DISALLOWED`, `CRAWL_ADDRESS_NOT_PUBLIC` for one
failed with `ADDRESS_NOT_PUBLIC` and `CRAWL_POLICY_UNREADABLE` for one failed with
`ROBOTS_UNREACHABLE`. All five give the same composite, with the same dimensions
excluded in the same cases; only the reason differs, so `FORMULA_VERSION` did not change
for any. The reason enters `inputsDigest` when it is set (a score read as
`CRAWL_POLICY_UNREADABLE` has its own digest), so a stored score keeps the digest and the
reason it was computed with. `inputsDigest` therefore records the reason: a score
computed for a failed audit now carries `AUDIT_FAILED` (and a different digest from
before), while rows stored earlier keep `NOT_YET_MEASURED`.

### Report — Epic 7

#### `GET /api/v1/scans/{scanId}/report`
**Auth required.** Everything the narrative report screen needs, in one response.

**Presents; does not compute.** Score, competitor set and audit are read from the
rows Epics 3–6 wrote. The only new numbers are aggregates — citation counts per
domain, mention shares, per-engine coverage — and each is a count over stored
facts. Makes no provider calls and costs nothing.

**An excluded dimension is present with `included: false` and a null
`subscore`** — never `0`, and never omitted. It keeps its **nominal** §6 weight
so the report can say what the dimension would have been worth; the **included**
weights are the effective post-redistribution ones and always sum to 100. That
is what preserves the ledger identity (total lit height == composite) through an
exclusion.

**`competitorCitedDomains` ranks competitor-attributed domains above
unattributed ones,** then by citation count. Who is cited *instead of* the
subject is the evidence this section exists to show; a pure count ranking buried
it under review blogs on the first real scan. `MAX_CITED_DOMAINS` caps each list
at 12.

**`unclaimedCitedDomains` (Epic 7.1) is its own field for a reason.** It holds
domains that were cited and belong to **neither the subject nor any detected
competitor**, ranked by citation count alone, floored at 2 citations and capped
at 3. `competitorCitedDomains` already contains these rows — but it ranks
attributed domains above them *deliberately* (see above) and then truncates at
12, so on the real Help Scout scan the heaviest unclaimed domain (`eesel.ai`, 6
citations, twice the subject's 3) sorted **third**, below two rivals cited once
each. The fix beat names this domain as a concrete recommendation, and a
recommendation must not inherit an evidence table's display cap. Computed from
the full set, before that ranking and before the cap.

**`promptShelf` (Epic 7.1) is the one place the projection is not aggregated.**
Every other field here collapses the scan to totals; this keeps one row per
answer, with the brands it named in the order it named them. It exists because
"in THIS question, who stood where, and was the subject there at all" is not
recoverable from `mentionShares`, which is keyed by entity across the whole scan.
Capped at 20 prompts, in **whole prompts** — a row missing one of its engines
reads as that engine not answering.

  * `subjectPresent` reads `EngineResult.mentioned`, the authoritative flag —
    never the length of `slots`. `BrandMention.position` is nullable, so a
    positionless mention takes no slot, and deriving presence from the slots
    would report an absence in an answer that named the subject.
  * `slots` carries **stored** ordinals, never re-indexed. A brand named 5th is
    `position: 5` even when 2–4 are not in the competitor set.
  * `answered: false` means the engine errored. It is **not** the same as
    answering without naming the subject, which is `answered: true,
    subjectPresent: false` — see the status note below.
  * `promptText` is **our own generated question**, the same string
    `PromptOut.text` has returned since Epic 4. It is the only prose-bearing
    field in the whole report projection, and it is registered by name in
    `test_facts_only.py`'s sweep rather than left to pass by not matching a word
    on the forbidden list.

**`ANSWERED_NO_MENTION` counts as answered (corrected in Epic 7.1).** Epic 7 read
`status is OK` when computing `answeredResults`, `engineCoverage.answered`, the
citation totals and the mention shares — which folded every *confirmed absence*
in with the timeouts. `EngineResult`'s own comment has always said otherwise:
"the engine answered but the brand was absent. Distinct from ERROR: a confirmed
absence is a valid, scoreable data point." On a scan naming the subject in 3 of 6
answers, the proof beat reported **"Answered 3 of 6"** and **"Named <subject> 3 of
3"** — a 100% mention rate on a subject named half the time — and discarded the
citations and rival mentions the other three answers carried, which is the most
damning evidence the beat has. It never surfaced because no fixture contained one:
the Help Scout scan names the subject in all six of its answers, and `seed_dev.py`
had no absent answer either until this epic added two.

**`score`, `competitorSet` and `audit` are nullable, and null means "never
ran".** That is distinct from a score whose `status` is `insufficient_data`,
which means "ran, and could not be scored". Both are distinct from zero. A
report renders all three states differently.

**A `failed` scan's report carries no score** (checklist 3.24), even if the scan
kept a score row: `score` is `null`, `dimensions` is `[]`, each competitor's
`mentionRate` and `shareOfVoice` are `null`, `audit.technicalFoundation` is
`null`, and `actionItems` is `[]` (checklist 3.30: the fix generator was handed the
score, so nothing it wrote is served; the fix beat then renders its deterministic
derivation, as for a scan with no fixes generated). `proof.crossEngine.standings`
is `[]` too (checklist 3.37): each standing is one engine's mention rate and
sentiment, computed by the same functions as two score dimensions, and the
sentiments add up to the Sentiment sub-score the scan does not show. The web draws
no cross-engine section for an empty list, as for a scan with no answers.
`splits`, `comparablePrompts` and `agreementRate` stay, with every other count,
boolean, domain and position in `proof`, because they are facts about what was
measured; `proof.engineCoverage` still gives each engine's answers and answers
naming the subject. The shared report and its PDF do not serve a `failed` scan at
all: its share link is refused like a withdrawn one (checklist 3.29, under
`POST /api/v1/reports/shared`). No row is changed or deleted: the Score row is not
read, the fix rows are read and not served, and the answers the standings were
computed from are read as they always were. Every other status serves `standings`
as before.

**"Withheld" here means not computed and not shown. It does not mean "cannot be derived
from what the scan stored"** (checklist 3.37 review). A failed scan's stored rows are
unchanged and its own routes serve them as stored: `GET /api/v1/scans/{scanId}` (the
prompt set with each prompt's `intent`, and every engine result), `.../results`,
`.../prompts` and `.../audit` return every input Mention Rate, Share of Voice, Sentiment
and Technical Foundation are computed from. Whether those routes should withhold anything
for a failed scan is the founder's decision and is open.

**`visibilityFlags` is served as for any status.** `NAMED_ONLY_WHEN_PROMPTED` is kept as a
finding about where the mentions came from, and on a failed scan it says that the Mention
Rate the scan does not show was 0 (no question that left out the subject's name produced
a mention, while one that included it did).

**`outranksSubject`** is arithmetic over stored counts and ordinals — more
appearances wins; on a tie, the better position wins. Not a judgement.

**Facts only** (the facts-only rule). Every field is a name, a domain, a URL, a
count, an ordinal, an enum member, a machine code, or a number. There is no
field capable of carrying an engine's answer or a competitor's copy, and
`test_report_projection_exposes_no_third_party_prose` sweeps the whole schema
module to keep it that way. Audit findings carry `detailCode`; the human wording
lives in the frontend string table, as with every other check code.

**Errors:** `401`, `404` (unknown scan, or another agency's).


### Public share link — Epic 9.8

The Epic 9 **send** path. §7's Epic 9 acceptance is that a pilot agency can
"generate and **send** at least one real prospect report", and every surface
before this one is cookie-authenticated and agency-scoped — the person a report
is *about* had no way to read it.

**This is the first unauthenticated read surface in the product.** The rules
below are narrow on purpose and are asserted in `tests/test_share_link.py`.

#### `GET /api/v1/scans/{scanId}/report.pdf`
**Auth required.** The same report, as a PDF — Epic 9 send path, slice 3.

**A rendering target, not a second report.** It calls the same `build_report`
the JSON route calls and renders what comes back. There is no second query, no
second aggregation, and no second set of numbers — a PDF assembled
independently would eventually disagree with the page it was downloaded from,
and the disagreement would reach a client.

**Response `200`** — `application/pdf`, with
`Content-Disposition: attachment; filename="<subject>-ai-visibility.pdf"` and
`Cache-Control: private, no-store`. The filename is derived from the subject's
own name and reduced to `[A-Za-z0-9._-]`, because a client name is
caller-supplied data and a `Content-Disposition` header is a header.

**A downloaded file outlives revocation of the share link** (Epic 9.21), and
nothing can change that. This route is agency-authenticated, so the holder is
the agency itself rather than a prospect, but the property is the same one the
public PDF route states at length.

**It degrades exactly as the web report does**, because it is derived from the
same payload: a null composite prints **"Not scored"** and never a zero,
`insufficient_data` gets its own sentence distinct from never-scored, an
excluded dimension prints its reason and no sub-score, a null `competitorSet`
says detection did not run rather than dropping the beat, and an empty
`actionItems` renders the deterministic fix derivation — the case the note on
that field above describes.

**No dependency was added.** product-spec.md §5.1 names React-PDF or WeasyPrint;
both were assessed against the dependency-licensing rule rather than assumed. WeasyPrint
hard-requires **Pyphen**, whose classifiers are GPLv2+/LGPLv2+/MPL-1.1 — all
blocked. React-PDF is MIT but is a Node library, so a Python endpoint would need
a subprocess in the request path, and its own `StyleSheet` primitives mean
`ReportView` could not be reused in any case. `fpdf2` is LGPL-3.0-only;
`reportlab` is BSD and clean but pulls a native Pillow wheel for a document with
no images. The writer is `services/pdf.py`, using the PDF standard-14 fonts and
stdlib `zlib`.

The fix beat's derivation lives in TypeScript (`lib/report/derive.ts`) and is
duplicated in Python (`services/report_narrative.py`) because a Python process
cannot call it. The duplication is **policed, not trusted**: two test suites
read the same checked-in fixtures and assert the same checked-in expected
output, so changing either derivation reddens one of them.

**Errors:** `401`, `404` (unknown scan, or another agency's).

#### `GET /api/v1/scans/{scanId}/report.csv`
**Auth required. Off unless `REPORT_CSV_ENABLED` is on** (2026-10-06, F3; labels and sections as
revised after review the same day). The report's figures as one CSV file: the facts the
signed-in report already shows, for an agency to take into its own spreadsheet or deck.

**A rendering target, not a second report.** It calls the same `build_report` the JSON
route calls and writes what comes back (`services/report_csv.py`): no second query, no
second aggregation, and nothing the report does not already hold. Makes no provider call
and costs nothing; built in memory per request.

**One long table, one header row, six columns:** `Section,Engine,Prompt,Item,Measure,Value`.
Every row is one fact, every label is plain words, and a figure carries its unit in its
`Measure`. Six sections, in this order:

| `Section` | One row per | `Measure` and `Value` |
|---|---|---|
| `Scan` | fact about the scan (three rows) | `Item` is the client's name. `Scan date` (an ISO date, UTC); `Scan status` (`Complete`, or for a `partial` scan the PDF cover's own sentence, "This scan is partial: not every planned question was answered, so these results rest on fewer answers than planned."); `Overall score (out of 100)` (the stored composite, or `Not scored` for a scan never scored or with too little data, never a zero) |
| `Dimension scores` | dimension, heaviest first | `Score (out of 100)`, or `Left out of the score because` with the reason as the report words it (`Not yet checked`). Never a zero for a dimension left out; no rows for a scan never scored |
| `Share of voice` | the client and each competitor, as the report's "Rivals in the same answers" table lists them | `Share of voice (out of 100)` (a blank when the scan made no comparison, never `0`). No rows when the scan has no competitors |
| `Answers` | engine (`Prompt` blank), and engine and prompt | per engine, for the whole scan: `Prompts asked (count)`, `Prompts listed below (count)` (the report lists the first 20 prompts of a scan, so this says how many of the asked ones are below), `Answers received (count)`, `Answers naming the client (count)` and `Sentiment (out of 100)` (when the engine named the client at all); per prompt: `Answered (yes/no)` and, if it answered, `Named the client (yes/no)` and `Position when named (1 = first)` (when it was named and the position was stored). `Item` is the client's name. The prompt text is ours, generated |
| `Cited domains` | domain cited | `Citations (count)` and `Attributed to` (the client's name for its own pages, a competitor's name, or `Third party`). Both of the report's citation tables, each as capped by the report (12 domains) |
| `Fixes` | fix on the report's list | `Priority`, `Effort (S, M or L)` and `Points the score gains` (none for an audit fix, which has no measurable value). The title is `Item` |

**The fix list is the report's, not the projection's `actionItems`.** The report derives
which fixes exist, their order and their points itself, and generated wording is laid on
by key; the CSV takes that derivation (`report_narrative.derive_narrative`, the one the PDF
runs), so a scan whose fixes were never generated has the list its page shows. A fix's
`detail` is not in the file.

**Numbers are written as the report serves them**: a decimal as stored (two places, never
an exponent), counts as integers, a fix's points to one place as the page shows them. The
web page rounds its tables to one place; the file keeps the stored figure, as the PDF does,
and the button says so. A figure that does not exist is not a row; one the report shows as a
dash is a blank cell. Left out because the brief did not name them: the weights, a rival's
mention rate, citation strength and average position, a citation's page address, the audit's
checks and a fix's detail.

**Response `200`** — `text/csv; charset=utf-8`, with
`Content-Disposition: attachment; filename="<client>-ai-visibility-<date>.csv"` and
`Cache-Control: private, no-store`. The client's name is reduced to `[A-Za-z0-9._-]` exactly as
the PDF's name is (a run of any other characters becomes `-`, a leading or trailing `-` or `.` is
dropped, 60 characters at most), because a client's name is caller-supplied data and a header is
a header; `<date>` is the scan's date in UTC, or the day the report was made when the scan has
none; a name with nothing left after the reduction gives `ai-visibility-<date>.csv`, which
keeps the date. Nothing else an operator typed is in it. The body starts with a UTF-8
byte-order mark and rows end `\r\n`.
**Excel-safe:** every cell that begins with `=`, `+`, `-`, `@`, a tab, a carriage return or a
full-width `＝`, `＋`, `－`, `＠` (OWASP's list, and the full-width forms), with white space in
front of it or not, gets a leading apostrophe; and an apostrophe goes straight after a `;`, a
tab, a carriage return or a line feed inside a cell when a formula character follows it (white
space between or not), because a spreadsheet that splits on `;` or a tab starts a new cell there,
and one in a `;` locale ends the record at a line break even inside the quotes `csv` writes, so
what follows starts a record of its own. `csv` quotes a cell for a comma, a quote or a line break
and for neither a `;` nor a tab. Where a `;` and a line break both come before a formula, the
apostrophe goes after both, so the new line begins with `'`. The header and our own words are
guarded the same, so a client name, a competitor name, a prompt or a fix title is text and
never a formula. Quoting is Python's `csv` module.

**Facts only.** Every cell is a name, a domain, a count, an ordinal, a yes or a no, a number, a
date, one of our own words, our own generated prompt, or the title of one of our fixes.
`tests/test_facts_only.py` holds the builder to that.

**No token route.** A share link opens the report and its PDF and never this file; there is
no `POST /reports/shared/csv`, and `csvExportAvailable` is `false` on every public response.

**Errors:** `401` (signed out, whatever the setting); `404` (unknown scan, another agency's, **or
the setting is off**, with the body an unknown path gets: type `/problems/not-found`, detail
`Not Found`); `409` `/problems/scan-not-exportable` for a scan with no figures to give. The
agency check runs first, so another agency's scan is a `404` in every status and never a
`409`. The `detail` is one plain sentence, and names no code and no figure:

| Scan status | `detail` |
|---|---|
| `failed` (its score is withheld, as for sharing) | "This scan failed, so its figures cannot be exported." |
| `queued` | "This scan has not started yet, so there are no figures to export. Try again when it has finished." |
| `running` | "This scan is still running, so its figures are not final. Try again when it has finished." |
| any other status except `succeeded` and `partial` (`cancelled`, which nothing writes today) | "This scan did not finish, so its figures cannot be exported." |

`succeeded` and `partial` are exported: the list is an allow-list, so a status added later is
refused until somebody says it should be exported.

#### `POST /api/v1/reports/shared/pdf`
**No auth.** The signed report as a PDF, by share token.

**Request**
```json
{ "token": "uG6-k3CTaiAyPY0-OAOiezBwUerycAGiepPbgMwWlMk" }
```

**Response `200`** — `application/pdf`, with
`Content-Disposition: attachment; filename="<subject>-ai-visibility.pdf"` and
`Cache-Control: private, no-store`. The filename is derived from the subject's
own name and reduced to `[A-Za-z0-9._-]`, because a client name is
caller-supplied data and a `Content-Disposition` header is a header.

**The decision, stated rather than defaulted: a stranger holding a share token
CAN download the PDF, and the share page offers it.** It exposes nothing new —
strictly the facts `POST /reports/shared` already serves the same holder,
rendered differently — and Epic 9.8 minted this token precisely because "the
prospect a report is about has no account, and must not need one to read it".
Granting the harder-to-forward form (a live URL) while withholding the easy one
(a file they can keep) is backwards for a mechanism whose job is *send*.

**What it costs, said plainly: a downloaded PDF outlives revocation.** Epic 9.14
accepted that when the cost was zero — links had no expiry and no revocation, so
the file gave away nothing the link did not already give away permanently — and
marked this "the route to revisit when revocation ships". **Epic 9.21 shipped it,
and this is that revisit.** A revoked or expired link stops serving files
immediately, on the same lookup as the JSON route, and so does a link whose scan
`failed` (checklist 3.29, below). What revocation cannot do is
recall a copy already on someone's disk, and nothing can. That residual gap is
real, bounded and named: **revocation governs the link from the moment it is
invoked, never a file already downloaded.**

**Every rule the JSON share route states holds unchanged, because it is the same
lookup: read-only, one code path, `404` for every rejection with no shape
pre-check, and never a `401`.** The token travels in the body so it never appears
in a request log.

**Errors:** `404 not-found` for an unknown, revoked or expired token, or one whose
scan `failed` — one reply for all four, and the problem's `instance` is
`/api/v1/reports/shared/pdf`, so no token is echoed. `422 validation-failed` for a
missing, empty, non-string or over-512-character token; this reply is the same
for a real and a fake token.

#### `POST /api/v1/scans/{scanId}/share`
**Auth required.** Mints (or returns) the scan's public share token. `200`.

**An explicit act, not a side effect of running a scan.** A scan is a private
measurement until an agency decides otherwise; minting a token for every scan
and relying on the URL being unknown would make that decision for them.

**`200`, not `201`, and idempotent.** While the scan has a live link, calling
again returns that link exactly as it is: the *same* token, the same URL and the
same `expiresAt`, and nothing is written. Every extra token would be a URL
nobody is tracking, so the second call mints nothing and does not claim to.
Serialised with `SELECT … FOR UPDATE`: two
concurrent calls on a scan with no link would otherwise generate two different
tokens and issue two UPDATEs against the same row, and the loser would walk away
holding a URL that 404s. There is no unique violation to catch in that race, so
the lock is load-bearing rather than defensive. The loser reads the winner's
link off the locked row and returns it as it is.

**Response `200`** — `ShareLinkOut`:
```json
{
  "scanId": "scan_01J...",
  "token": "uG6-k3CTaiAyPY0-OAOiezBwUerycAGiepPbgMwWlMk",
  "url": "http://localhost:3000/share#uG6-k3CTaiAyPY0-OAOiezBwUerycAGiepPbgMwWlMk",
  "expiresAt": "2026-10-08T09:22:00Z"
}
```

**A press on a live link does not move its end — Epic 9.21, changed by
checklist 3.28 (founder decision).** A link is *live* when its token is set and
its `expiresAt` is in the future. A press on a live link returns it exactly as it
is: the same token and the same `expiresAt`, with nothing written. Epic 9.21 first
had a second call push `expiresAt` out to 30 days from that press, and bring an
ended token back to life; it no longer does either. The share bar says links
last 30 days from when they are created and shows "The link works until …" for
the end the link was given, so a press that moved the end would have made both
untrue of the link already sent, and silently: pressing "Get shareable link" is
also how the signed-in report gets the URL back, because the report carries
`shareExpiresAt` and never the token.

A press makes a link only when none is live, and what it makes is **new**:

| The scan's link | A press returns |
|---|---|
| live | the same token and `expiresAt`; nothing written |
| never made, or withdrawn | a new token, `expiresAt` 30 days from the press |
| ended (`expiresAt` in the past) | a new token, `expiresAt` 30 days from the press; the ended token is replaced, so its address stays dead on both public routes |

A link's end is never moved in place. A link that has ended is replaced by
pressing again; a live one that has to be replaced sooner is withdrawn first,
and withdrawing ends the address that was sent. A scan that `failed` is refused
before any of this (`409`, below).

**Links live 30 days** (`share.SHARE_TTL`), from when they are made. It must outlive the conversation it
was sent for — a report is read, forwarded, and put in front of a budget holder
over days to a couple of weeks — and must not outlive the data, since a month on
a re-scan would show different numbers and the link would be making a stale
claim about a live business. Expiry is the blunt instrument for a link nobody
remembers sending; revocation below is the sharp one.

`url` is built from `PUBLIC_WEB_BASE_URL`, **never** from the request's `Host`
or `Origin` header. Those are attacker-controlled, and a share link built from a
spoofed Host is a phishing URL carrying a real token. Configuration, not
reflection.

**A `failed` scan cannot be shared** (checklist 3.24): `409 /problems/failed-scan-not-shareable`, and no token is minted. A failed scan has no score on the dashboard or the report. `partial` and every other status mint as before. The status is read again under the row lock, so a scan that fails while the request is in flight gets the same `409` and nothing is written: no token minted, and a live link's end not moved.

**A link minted before the scan failed no longer opens its report** (checklist 3.29, founder decision): both public routes refuse it like a withdrawn one (see `POST /api/v1/reports/shared`). The token is not cleared. `DELETE .../share` still takes it down, and the signed-in report's `shareExpiresAt` still reports it, so the screen can offer that.

**Errors:** `401`, `404` (unknown scan, or another agency's), `409` (failed scan).

**`proof.crossEngine` — where the engines disagree (Epic 9.23).** Present on
every report. Carries `standings` (each engine's own mention rate and
sentiment, computed by `scoring.mention_rate` and `scoring.sentiment_score` on
that engine's slice — not recomputed, so the per-engine figures cannot drift
from the composite), `splits` (prompts one engine answered naming the subject
and another answered without it), `comparablePrompts`, and `agreementRate`. For a
`failed` scan `standings` is `[]` (checklist 3.37; see the report's failed-scan note
above) and the rest is served as for any status.

Two rules the shape enforces. **Only engines that ANSWERED appear on either
side of a split** — a rate-limited or timed-out call is missing data, not
evidence of absence, and counting it would turn a provider outage into a
visibility finding. And **`agreementRate` is null when nothing was comparable,
which is not 100%**: a scan where one engine answered agrees with itself
trivially, and `comparablePrompts` is the denominator that keeps the
distinction readable.

#### `PATCH /api/v1/agencies/{agencyId}/branding`
**Auth required, admin or owner.** An agency's logo and accent colour. `200` —
`BrandingOut` — Epic 9.22.

**What may be changed is a logo and ONE colour, and the shortness of that list
is the decision.** §7 line 2 asked for "logo, custom domain, colours". The
report's palette is *notation*, not decoration: `--avp-vis-*` encodes the score
on a monotonic lightness ramp that survives greyscale and colour-vision
deficiency, `--avp-competitor-{1..5}` is neutral so no rival reads as endorsed
or attacked, `--avp-beacon-*` marks the subject **being scanned** (the prospect,
not the agency — a confusion worth naming), and the semantic four say a scan
failed or a quota is low. An agency free to recolour any of those changes what
the document *means*. `BrandingRequest` therefore has no field capable of
naming one; the guarantee is the type, and a test asserts the model has exactly
two fields.

**The accent reaches chrome only** — the letterhead rule under the masthead.
`--avp-agency-accent` is set inline on that element and nowhere above it, so it
is not in scope for a single beat of the report. `AgencyBranding.test.tsx`
asserts the colour never appears after the first beat, never shares an element
with an encoded token, and is never defined on the page root.

**No `customDomain`.** Deferred, not forgotten: it needs DNS verification,
certificate issuance and request routing before it does anything, and a column
storing a value nothing honours is a field that looks built.

**Request** — both fields optional, and **null means remove**. An absent field
is left alone; an agency that set the wrong logo needs a way back to unbranded.

```json
{ "logoUrl": "https://cdn.example/acme.png", "accentColor": "#1f6feb" }
```

`logoUrl` must be an absolute `https://` URL, and `accentColor` must match
`^#[0-9a-fA-F]{6}$`. Both land on the **unauthenticated** share page — the logo
as an `<img src>`, the accent as a CSS custom property value — so `javascript:`
and `data:` are script execution and an unanchored colour string closes the
declaration and opens another. Validated at the schema for a readable message
**and** by CHECK constraints on `agencies`, so a bad value cannot be stored
however it arrived. The logo is **never fetched server-side**, which is what
keeps an agency-supplied URL from being an SSRF vector.

**The PDF does not carry the logo, and that is deliberate.** `report_pdf.py`
was built at zero dependencies behind an explicit licensing survey; a logo is
the first image the document has ever needed, and adding one would reopen that
survey *and* require a server-side fetch of a customer-chosen URL. A test
asserts the PDF writer never learns about either field.

**Errors:** `401`, `403` (member seat — how every report an agency sends is
branded is an agency-level decision), `404` (another agency's id, never `403`),
`422`.

#### `DELETE /api/v1/scans/{scanId}/share`
**Auth required.** Takes the public link down. `204`, no body — Epic 9.21.

The inverse of the `POST` above, on the same path, because the thing being
removed is the resource that path names. Clears **both** `share_token` and
`share_expires_at`, which the `ck_scans_share_token_and_expiry_together` CHECK
requires and which is also the honest state: a token with no expiry is not a
link, and an expiry with no token is a date about nothing.

**Idempotent.** Revoking a scan that was never shared, or revoking twice, is
`204` and not an error: the caller asked for it not to be readable, and it is
not. A `404` there would report on something they did not ask about, and a
`409` would invite a retry loop over a state that is already correct.

**After this, both read routes 404 for the old token** — JSON and PDF — on the
same code path as a token that never existed. A revoked token is not a special
case of the indistinguishable-rejection rule below; it is the same rule, which
is why the check lives in one lookup (`share.scan_for_share_token`) rather than
in either route. A test asserts the two responses match field for field, minus
`instance`, which echoes the request path.

**It does not reach a PDF already downloaded.** Nothing can — see the PDF route
above.

**Errors:** `401`, `404` (unknown scan, or another agency's).

#### `POST /api/v1/reports/shared`
**No auth.** The report behind a share token.

**Request**
```json
{ "token": "uG6-k3CTaiAyPY0-OAOiezBwUerycAGiepPbgMwWlMk" }
```

**Response `200`** — `ReportOut` (the same shape as
`GET /api/v1/scans/{scanId}/report`), with
`Cache-Control: private, no-store`.

Returns **exactly** the same `ReportOut` as
`GET /api/v1/scans/{scanId}/report` — `build_report` is reused, not
reimplemented, so the facts-only sweep in `test_facts_only.py` covers this
response too. A second assembly path would be a second place for a snippet to
slip in. `generatedAt` is a clock read and is the only field that differs
between the two; a test asserts the rest are byte-identical.

**The token is the whole credential.** There is no account behind it, which is
the point — a prospect must not need one. It is `secrets.token_urlsafe(32)`:
**256 bits from the OS CSPRNG**, the same generator and entropy as a session
token (`security.new_share_token`, beside `new_session_token`). It is never the
scan's ULID, which is already in the authenticated URL and in logs. **The token
travels in the body so it never appears in a request log.**

**Revoked and expired tokens 404 identically** — Epic 9.21. Both are filtered in
`share.scan_for_share_token`, so neither route can drift into treating them as
their own kind of wrong. A missing `share_expires_at` is **not** "never
expires": the comparison is strict, so a token that somehow reached the table
without one serves nothing. Fail-closed, for a credential.

**A `failed` scan's token 404s the same way** — checklist 3.29, founder decision.
A failed scan's score is never shown, so there is no report to send, and a link
minted while the scan was still running used to keep serving it without a score.
It is now refused like a withdrawn one: the same status, the same `type`, the
same `detail` ("No report with that link."), on this route and on
`POST /reports/shared/pdf`, because the status test is one more condition in
`share.scan_for_share_token`'s query rather than a check in either route. The
token is **not** cleared: the agency's own report still carries `shareExpiresAt`
for it, and `DELETE /scans/{scanId}/share` still takes it down. Every other
status (`partial` included) is served as before.

**`404` for every rejection, on one code path.** A malformed token, an unknown
token and a well-formed miss are indistinguishable in both status and body.
There is deliberately no shape or length pre-check: rejecting an implausible
token faster than a plausible one is a timing oracle that makes enumeration
cheaper. **Never `401`** — that would confirm the token is real.

**Read-only.** No sibling route mutates anything by token. A holder cannot edit
the competitor set, re-run the scan, or reach any other scan; the token resolves
to exactly one row.

**Errors:** `404 not-found` for an unknown, revoked or expired token, or one whose
scan `failed` — one reply for all four, and the problem's `instance` is
`/api/v1/reports/shared`, so no token is echoed. `422 validation-failed` for a
missing, empty, non-string or over-512-character token; this reply is the same
for a real and a fake token.


### Action list (generated fixes) — Epic 8

#### `POST /api/v1/scans/{scanId}/fixes`
**Auth required.** Generates the scan's prioritised fix list. `201`.

**Costs one model call.** Which dimension gaps are worth a line, which audit
findings warrant a fix, and in what order — all of that is decided *before* the
call, by the same rules the report client already applies (`derive.ts`:
`gap >= 2`, at most 3 dimension fixes, at most 5 fixes, crawl-blocking checks
promoted). The model words those candidates and judges priority and effort. It
cannot add a recommendation the measurement did not produce: a returned fix whose
`candidateId` matches no candidate is discarded, and `rank` and `pointsUpside`
are always taken from the candidate, never from the response.

**One row per candidate per scan, refreshed on re-run.** A regenerated list is a
better statement of the same measurement, not a second measurement — the same
framing as the technical audit. But `status` belongs to the operator, so it
survives regeneration, and a candidate that has been worked is kept even once it
stops being measured. Enforced by `uq_action_items_scan_source_key`.

**A provider failure writes nothing** and returns `status: "failed"` with a
reason code, leaving any previous list intact. The report still renders its
deterministic fix list in that case, which is a weaker list rather than a wrong
one.

**A `failed` scan has no fixes served** (checklist 3.30, extending 3.24). For a scan still
running, the generator's input includes its score (founder's decision), and what it
writes can quote it ("share of voice at 30 out of 100"). If the scan then fails, nothing
it wrote is served, on any route, and the rows are kept. `POST` for a `failed` scan is
`409 /problems/conflict`, `detail` "This scan failed, so no fixes are written for it.",
with no model call and no row written or changed. The agency
check comes first, so another agency's failed scan is the same `404` as an unknown one. A
scan that fails *while the generation runs* gets the same `409` (its status is read again
after the call); what the call wrote is kept, and not served. `succeeded`, `partial` and
every other status are unchanged. The report serves none either: see its `actionItems`
below.

#### `GET /api/v1/scans/{scanId}/fixes`
**Auth required.** The scan's fix list as last generated, in rank order.

**A `failed` scan has no fixes served** here too (checklist 3.30, extending 3.24): `200`
with `status: "empty"` and `items: []`, the same answer as a scan whose fixes were never
generated, whatever rows the scan kept. They are not changed or deleted. See `POST` above.

Returns an empty list with `status: "empty"` rather than `404` when nothing has
been generated yet: "no fixes yet" is a state of a scan that exists.

**Response `200`** — `ActionItemListOut`:

this product cannot support or quotes one of our internal identifiers back.

### `POST /api/v1/clients/{clientId}/prompt-runs` — ad-hoc prompt, Epic 9.24

Ask ONE prompt an operator typed, against every engine, now. Facts persisted.

```jsonc
// request
{ "prompt": "best privacy-focused website analytics for a small SaaS" }

// 201
{
  "id": "prun_01M1D…", "clientId": "clnt_01M15…",
  "promptText": "best privacy-focused website analytics for a small SaaS",
  "status": "ok",                     // ok | partial | failed
  "subjectName": "Plausible Analytics", "subjectDomain": "plausible.io",
  "createdAt": "2026-09-01T05:44:00.109593Z",
  "results": [{
    "id": "prre_01M1D…", "engine": "claude_search",
    "engineVersion": "claude-opus-5/web_search_20260209/direct",
    "status": "ok", "errorCode": null, "latencyMs": 28335,
    "mentioned": true, "position": 1, "prominence": "0.984", "brandsMentioned": 3,
    "brands":    [{ "name": "Plausible Analytics", "domain": "plausible.io",
                    "isSubject": true, "position": 1 }],
    "citations": [{ "url": "https://…", "domain": "dev.to",
                    "sourceType": "third_party", "position": 1,
                    "citesSubject": false }]
  }]
}
```

**Synchronous, and slow on purpose.** Three concurrent engine calls bounded by
`ENGINE_CALL_CEILING` (122s worst case; 17.9s / 28.3s / 5.4s measured live on
the three engines). A scan is backgrounded because nobody waits six minutes for
it; the operator IS waiting for this one, so backgrounding it would mean
inventing a status to poll for a request that finishes inside the window a
browser holds open. It is the same work one `PROMPT_CONCURRENCY` slot does
inside a scan.

**It writes no `Scan` and no `Score`.** A run is a question, not a measurement,
and must never reach a trend, the dashboard's figures or a client's scan
history where it would be read as one. Asserted in `test_prompt_runs.py`.

**`status` is the three-way shape a scan uses.** An engine that answered without
naming the subject is `answered_no_mention` — a finding, not a failure, and the
single most useful thing this endpoint returns. `partial` means some engine was
genuinely down.

**Errors.** `422` for a blank or over-long prompt (`PROMPT_EMPTY`,
`PROMPT_TOO_LONG`; the cap is 500 characters after whitespace collapse). `429`
for the throttle. `404` for another agency's client — never `403`, which would
confirm the id exists.

**The throttle: 30 runs per client per hour.** Sized against what a scan
already costs rather than picked. One run is 4 engine calls (the default
engines since 2026-09-12); one scan is 20 prompts × 4 engines = 80. So 30
runs/hour = 120 calls = **1.5 scans**, and the worst an unattended loop on one
client's screen can spend in an hour is one and a half scans — spend this
product already absorbs from a single click on the dashboard's Re-run button.
(When this was written a scan was 24 prompts × 3 engines = 72 calls and the
same 30 runs were 90 calls, 1.25 scans; the ceiling has not moved, the scan
under it has.) Lower would obstruct the real work (an
operator iterating on phrasing legitimately fires 5–10 in minutes); higher and
the ad-hoc path stops being a rounding error against scan spend and becomes its
own line item, which is a pricing decision, not a tuning one. **Per client, not
per agency**, because the abuse vector is a loop on one client's screen and a
per-agency ceiling would let one busy client exhaust every other client's
allowance. Counted from the rows, not Redis: the rows are written anyway, the
count is exact, and a counter that resets on restart is useless exactly when a
runaway loop is still running. `test_prompt_runs.py` asserts the ratio rather
than the literal 30 — and reads both the engine count and the prompt count
from the constants that set them, so a change to either re-runs the arithmetic
— which means raising the ceiling forces the argument to be made again.

**Facts only.** `promptText` is the operator's own words — the same
deliberate exception `prompts.text` is. No field in `results` can carry an
engine's answer; a SHA-256 digest is kept so a re-ask can detect the answer
CHANGED without retaining what it said.

Newest first, unlike `GET /clients/{id}/history` — that one is a timeline and

### `GET /api/v1/clients/{clientId}/history` — gains `sentiment`, Epic A

Each `HistoryScanOut` now carries one row per engine that answered anything:

```jsonc
"sentiment": [
  { "engine": "chatgpt", "positive": 6, "neutral": 2, "negative": 1, "unclassified": 3 },
  { "engine": "claude",  "positive": 4, "neutral": 3, "negative": 2, "unclassified": 1 }
]
```

**Counts, not a rate.** A rate needs a denominator, and the only honest one here
is "answers where the subject was named" — which is exactly what
`unclassified` lets a caller compute. Baking one in would pick for them.

**`unclassified` is a fourth bucket, never a neutral.** It is answers in which
the subject never appeared, so `classify_sentiment` was not called at all —
tone toward a brand that does not appear is meaningless, and scoring-spec.md
excludes it rather than scoring it zero. Reporting it as neutral would claim
the engines described the brand indifferently, which is a measurement nobody
took.

**An engine that FAILED contributes no row.** Aggregation excludes every status
outside `OK` / `ANSWERED_NO_MENTION`, so an outage cannot be counted as
indifference. `terminal_status_for` draws the same line.

Grouped in SQL rather than in Python: a scan is 20 prompts × 4 engines = 80
`EngineResult` rows (24 × 3 = 72 when this was written), and pulling all of
them per scan across a whole history to compute four integers is the N+1 this
service exists to avoid.

### `POST /api/v1/clients/{clientId}/prompt-runs` — gains tone, Epic A

`PromptRunResultOut` gains `sentiment` and `sentimentConfidence`, matching the
pair `EngineResult` has carried since Epic 4.

**This is a correction, not a feature.** Epic 9.24 deliberately built ad-hoc
runs through the same `ask_all` and `extract_facts` a scan uses, so that "does
this prompt name my client?" could not answer differently on the two paths. It
then stopped one step short: the scan path classified tone and the ad-hoc path
did not, so the same question asked two ways produced different depth.

**Cost is unchanged where the client is not named.** `classify_sentiment` is
called only when `mentioned` is true — a run where no engine named the client
costs exactly what it cost before Epic A. Asserted, not assumed:
`test_prompt_runs.py` counts the calls.

**NULL means "never asked", not "neutral".** Every run made before this shipped
reads as tone-not-measured, and no backfill is possible or wanted: the answers
those runs were derived from are gone, which is the point of the facts-only rule.

**Still facts only.** A label and a confidence. There is no field here capable
of carrying what was classified.

### `GET /api/v1/clients/{clientId}/answer-gaps` — Epic B

Prompts where a rival was named and this client was not, for one scan, plus a
cross-scan rival rollup. Optional `?scanId=`; without it the newest griddable
scan is used and `availableScanIds` lists the rest so a picker needs no second
request.

**Reads only.** No engine call, no model call, no write. Every figure is an
aggregation over `engine_result_brand_mentions` and `engine_result_citations`
rows some earlier scan already persisted.

```jsonc
{
  "scanId": "scan_01…", "scannedAt": "2026-08-30T10:00:00Z",
  "availableScanIds": ["scan_02", "scan_01"],
  "engines": ["chatgpt", "claude", "claude_search"],
  "brands": [
    { "name": "PSM Digital", "isSubject": true,  "answersNamed": 4, "promptsNamed": 2 },
    { "name": "WebFX",       "isSubject": false, "answersNamed": 9, "promptsNamed": 3 }
  ],
  "rows": [{
    "promptId": "prmt_01…", "text": "how do i find a good seo agency…",
    "intent": "awareness", "kind": "absent",
    "enginesAnswered": 3, "subjectNamedOn": 0, "rivalsNamedOn": 3, "noBrandOn": 0,
    "subjectCited": false, "absentOn": 3,
    "cells": [{ "brand": "PSM Digital", "namedOn": 0 }, { "brand": "WebFX", "namedOn": 3 }]
  }],
  "rivals": [{ "name": "WebFX", "answersWon": 9, "scansPresent": 2 }],
  "prompts": 24, "absent": 9, "partial": 0, "uncited": 4,
  "covered": 1, "noBrands": 10, "unanswered": 0,
  "subjectCitable": true

```

**`no_brands` is a sixth kind, never folded into `absent`.** A prompt where NO
engine named ANY brand is not a question this client lost — it is a question
with no commercial answer, so there was nothing to be absent from. On the real
`avp_dev` rows this is not a rounding error: the worst client measured carries
**9 genuine absences beside 10 no-brand prompts**, so conflating them would
report 19 of 24 as gaps and roughly double the finding. The same discipline
Epic A applied to `unclassified` sentiment.

**`absentOn` counts ENGINES, and that is a correction to the brief.** The brief
asked for gaps "sortable by how often the gap recurs", which assumed prompts
persist between scans. They do not: `scan_runner.build_prompt_set` calls
`prompts.generate_prompts` fresh every scan, so prompt text is newly written
each time. Measured — **Plausible's three scans hold 72 prompts with 71
distinct texts; Notion's two hold 48 with 48 distinct.** There is no prompt
identity to recur on. What does recur is the engine (a gap holding on 3 of 3
is a stronger finding than 1 of 3) and the rival, which is what `rivals`
counts across the client's whole history.

**`uncited` is claimed only when `subjectCitable` is true.** There is no content
inventory anywhere in this schema — `TechnicalAudit` stores `pages_crawled` as
a COUNT and one `url_audited`, not a page list — so the brief's "the client has
relevant content (per Sources) but no citation" cannot be read as written. What
CAN be read is whether the engines ever cited this client's own domain in this
scan. If they did, the domain is demonstrably citable and a prompt that named
the client without citing it is a real gap. If they never did, the claim is
unsupported and **no row is reported as `uncited` at all** — the real Notion
scan is exactly this case, and reports 0 rather than 22.

**The grid is bounded by competitor detection.** `extract_facts` SEARCHES for
the brands it is handed and discovers none, so a rival absent from the scan's
`CompetitorSet` leaves no `BrandMention` row and cannot appear as a column
however often an engine named it. The screen says so in words rather than
presenting a short grid as a complete one.

**`null`, not 404, when the client has no griddable scan** — a normal state the
screen has an empty view for, not a missing resource. A `scanId` belonging to
another client also returns `null`, for the reason `get_client` 404s rather
than 403s: neither may confirm that an id exists in another agency.

**Four grouped reads, assembled in Python.** Joining mentions to citations to
results in one statement returns the product, not the grid — a scan carrying 72
results, 1,355 mentions and 2,399 citations would multiply out. Each read is
grouped in the database and returns at most a few hundred rows.

**Facts only.** Counts, booleans, ordinals, entity names, and OUR OWN prompt
text (Epic 4 generated it). `test_answer_gaps.py::TestIpSafety` asserts the
response echoes no phrase from an engine answer.

### `GET /api/v1/clients/{clientId}/alerts` — Epic E

What changed between a scan and the scan it was compared against, newest first.
**Newest first**, unlike `/history` — that is a trend and reads from its
earliest point; this is a log, and the entry an operator wants is the most
recent. `/prompt-runs` orders itself the same way.

**Reads only.** Alerts are generated once at the end of a scan (phase 7b of the
chain, after scoring) and never recomputed on read: an alert that re-derived on
every request could appear and disappear between two page loads of the same
data, and an acknowledgement would have nothing stable to attach to.

```jsonc
{
  "clientId": "clnt_01…",
  "alerts": [{
    "id": "alrt_01…", "kind": "sentiment_decline",
    "detail": "Net tone fell 60%, from +10 to +4.",
    "engine": "claude_search",
    "scanId": "scan_02", "baselineScanId": "scan_01",
    "scannedAt": "2026-08-31T02:39:36Z", "baselineScannedAt": "2026-08-29T04:55:26Z",
    "createdAt": "2026-09-02T08:34:31Z", "acknowledgedAt": null
  }],
  "unacknowledged": 3,
  "scansTotal": 2, "scansCompared": 1, "minBaselineHours": 20
}
```

**The baseline is not "the previous scan", and this is the epic's correction.**
An alert compares against the most recent scan at least `minBaselineHours`
older. Measured on the real `avp_dev` rows, comparing adjacent scans would have
been wrong: of three consecutive-scan pairs, **two are re-runs 43 minutes and
2h11m apart** and only one spans a real interval. On those re-runs, with nothing
having happened, the composite moved −0.93 and +0.68, net tone moved up to 6
points, and competitor citations swung by 26. Adjacent-scan comparison reports
engine nondeterminism as a business event — most often for the operator who
re-runs a scan to check something.

**`scansTotal` / `scansCompared` are returned because an empty feed is
ambiguous.** Most clients have one scan and can therefore never produce an
alert; nine of eleven in `avp_dev` are in exactly that state. Reporting "0
alerts" alone would read as an all-clear the data cannot support.

**A visibility alert from a `failed` scan is left out** (checklist 3.30, extending
3.24). A `visibility_drop` alert quotes its scan's composite ("Visibility fell
25.0%, from 80.0 to 60.0."), and a failed scan's score is never shown. Alerts are
written in phase 7b, while the scan is still `running`, so a scan that the deadline
then ends `failed` can already have one: the feed does not list it, and
`unacknowledged` and `scansCompared` do not count it (`scansCompared` is the number
of scans that have an alert in the feed). This route does not delete or change the row,
and no `visibility_drop` alert is created for a scan that is already `failed`. Nothing
that runs today deletes the row either, but that rests on alert generation running once
per scan, in phase 7b: generation deletes a scan's alerts before it rebuilds them, so a
second generation for a scan that had since failed would delete its visibility alert and
write no new one. The other two kinds, `sentiment_decline` and `owned_citation_lost`, are
not about the score and are listed and counted as before; so is every alert from a
`succeeded` or `partial` scan. `scansTotal` is unchanged: it counts the client's
`succeeded` and `partial` scans. The web reads all of this from this one feed, so its
Alerts page, its outstanding count and its trend markers follow the same rule.

**`scannedAt` is `COALESCE(finished_at, created_at)` — the same expression
`HistoryScanOut.scanned_at` uses, and it must be identical.** The trend charts
annotate a point by matching this against the point's `stamp`, and that stamp IS
the history's `scanned_at`. The first draft selected `created_at`; the two
differed by the scan's duration, no key ever matched, and every marker silently
failed to draw. Guarded by a test that reads both endpoints, because the defect
lives in the gap between them.

**Two of the three kinds are not what the brief asked for**, and the enum names
say so:

* `sentiment_decline`, not `sentiment_negative`. "Net tone crossing to negative"
  fires **zero times** across every scan on record — the minimum net tone ever
  measured is **+4**. It would also have said nothing about the clearest tone
  event in the data: Notion's net falling 13→6, 12→5 and 10→4 across all three
  engines at once. The rule is a relative decline, with a sign change retained
  as an additional trigger for when it eventually happens.
* `owned_citation_lost`, not "a rival took the citation". That is **structurally
  impossible**: `classify_citation` returns `cites_subject` as
  `domain == subject_domain`, a pure function of the domain string, so a source
  the client owned in one scan is its own in every scan. Confirmed in the data —
  no domain in any client's history carries two different `cites_subject`
  values. What is measurable is the client's own domain going from cited to
  uncited.

**Thresholds are set from measured re-run variance**, and `test_alerts.py`
asserts them as relationships rather than literals — so raising one forces the
argument to be made again, the way Epic 9.24's prompt-run throttle does. The
sample behind them is two re-run pairs and one real interval: enough to show the
re-run problem is real, nowhere near a variance estimate.

### `POST /api/v1/alerts/{alertId}/acknowledge` — Epic E

Marks an alert as seen. **Idempotent** — acknowledging twice returns the
original timestamp rather than moving it, so a double click cannot rewrite when
somebody first looked.

**No un-acknowledge, deliberately.** Dismissing is a record that a person
looked, and a log an operator can quietly un-read is not a log.

Scoped by the denormalised `agency_id` on the row — one predicate, no join —
and 404s rather than 403s on another agency's id, like every other
agency-scoped route here.

### `GET /api/v1/clients/{clientId}/ai-crawler-access` — Epic F

What this client's `robots.txt` **asks** each known AI crawler to do, as read
during one scan's technical audit.

```jsonc
{
  "clientId": "clnt_01J...",
  "scanId": "scan_01J...",
  "scannedAt": "2026-09-03T10:26:08Z",
  "urlAudited": "https://notion.so",
  "robotsReadable": true,
  "agents": [
    {
      "agent": "Amazonbot",
      "vendor": "Amazon",
      "purpose": "search",          // training | search | user_action
      "verdict": "blocked",         // allowed | blocked | unspecified | unknown
      "ruleSource": "explicit",     // explicit | wildcard | none | unreadable
      "matchedToken": "amazonbot",  // the group that decided it, or "*"
      "disallowRules": 1
    }
  ],
  "summary": {
    "total": 14, "allowed": 13, "blocked": 1,
    "unspecified": 0, "unknown": 0,
    "searchBlocked": 1, "explicit": 1
  },
  "availableScanIds": ["scan_01J..."]
}
```

**It answers "CAN an AI crawler read this site", not "IS one reading it".** The
roadmap's "Crawler activity" line asked for the second; that is a fact about
the client's own server logs and nothing in this system ingests them — there is
no log drain, no collector endpoint, and no column anywhere capable of holding
a bot hit. No field above can be rendered as activity, and none is named as
though it could be.

**A stated policy is not proof of compliance.** `robots.txt` is advisory; a
crawler may ignore it, and a block applied at a CDN or WAF is invisible here.

**Reads. Fetches nothing.** The verdicts were parsed during the scan's audit,
from the `robots.txt` it already fetched, and persisted then. Re-fetching on
read would let the same URL answer differently between two page loads and would
turn this endpoint into a way to make the API issue outbound requests on
demand; `test_crawler_access.py::TestTheEndpointDoesNotFetchAnything` asserts
it does not.

`scanId` selects one scan; without it the newest scan **carrying a policy** is
used. That filter is the audit's rows and deliberately not `ScanStatus`: a scan
can succeed on every engine while its audit failed, and — because the audit's
side fetch runs before the page render — a scan whose audit is `FAILED` can
still carry a full set of verdicts. What the picker offers is what can be
displayed.

Returns `null`, not 404, when no scan has ever recorded a policy — which is
every scan predating this feature. A `scanId` belonging to another client also
returns `null`, for the same reason `get_client` 404s rather than 403s.

**The four verdicts, and why there is no fifth.** A `partial` verdict was
drafted for "root permitted, some paths disallowed" and cut after measurement:
it fired on **seven of the nine** live client domains, on housekeeping rules
like `/api/`, `/cdn-cgi/` and `/humans.txt`. A verdict that is almost always
true carries as little information as Epic E's rules that fired never, and
making it mean something would need to separate `/blog/` from `/wp-admin/` —
which Epic B established there is no content inventory to do. Path-level
restriction survives as `disallowRules`, a count that qualifies `allowed`
rather than a verdict of its own.

`unspecified` is deliberately not folded into `allowed` even though their
practical effect is identical. A fetched `robots.txt` is a COMPLETE document,
so an agent nobody named is permitted by the file's own semantics (RFC 9309
§2.2.1) — but a site that named GPTBot and let it in decided something, and one
that never mentions it did not. On the live client domains the second is
overwhelmingly the common case, and it is the finding the screen exists to
surface. `unknown` is the genuinely absent measurement — `robots.txt` could not
be fetched — and is never merged with an allow.

**`searchBlocked` is separated from `blocked`** because only one of them has a
cost attached. Blocking a TRAINING crawler is a rights decision that costs no
citations; blocking a SEARCH crawler removes the site from the retrieval index
an engine cites from, which is this product's whole subject. A single count
cannot tell those apart, and they are different conversations with a client.

**Facts only.** Every field is a verdict, a count, an agent product token, a
vendor name, or OUR OWN classification of that agent's purpose. `matchedToken`
is a user-agent token — a product name or the literal `*` — never a URL. No
path or rule body is carried, and `ai_crawler_access` has no column one could
be stored in; `TestIpSafety` asserts both the behaviour and the column set.

**Not an input to any score.** `robots_allows_crawl` continues to feed Technical
Foundation exactly as it did in Epic 6, read by the older and weaker blanket
check that has always produced it. That check was deliberately NOT reimplemented
on top of this epic's RFC 9309 parser: it is a scored input, and re-deriving it
would move Technical Foundation for every client whose file the old reader got
wrong, inside a diff about crawler policy, with no way to tell a fixed score
from a regressed one. `robots.txt` is therefore read twice per audit, on
purpose, in one fetch.

### `GET` and `PUT /api/v1/clients/{clientId}/other-sites` — a brand's other sites, M1 task 1.1

**Auth required, any member of the agency.** The report counts a cited domain as the client's
own only on exact equality, so a brand's own site under another public suffix (RMIT
University's `rmit.edu.au` and the `rmit.edu.vn` of RMIT Vietnam) is cited as an independent
third party. The founder-approved plan: a domain that carries a brand's name under **another
public suffix** is **proposed** as the brand's other site, and counts as the brand's own only
once the **agency confirms** it. **A proposal changes nothing.** These two routes build the
lists; **nothing reads them yet** to type a citation, score a scan or draw a report (tasks 1.2
and 1.3), and no web screen uses them.

**The rule** (`same_brand_elsewhere` in `services/other_sites.py`): the label left of each
domain's public suffix is equal and not empty, and the suffixes differ. The split is the Public
Suffix List's own, read by the extractor that reduces every cited domain, and **only under the
list's ICANN section** (`crawl.name_and_icann_suffix`, the founder's decision of 2026-10-09): the
rule is false when either domain's public suffix is a private one, so `rmit.github.io`,
`rmit.blogspot.com` and `rmit.vercel.app` are never proposed for `rmit.edu.au`, and a brand at
`acme.github.io` has no other sites. (Citations are still reduced with the private section in, so a
cited `rmit.github.io` stays its own domain.) `rmit.edu.vn` for `rmit.edu.au` and `monash.edu.my` for
`monash.edu` are the brand's other sites; `rmit-online.com` for `rmit.edu.au` and
`pineapple.com.vn` for `apple.com.au` are not (another name); `rmit.edu.au` for itself is not
(the same suffix is not "elsewhere"); an empty string, an IP address and `localhost` are no one's.

**One host, two spellings.** A cited domain keeps the spelling the engine gave and a typed one the
spelling typed (`bücher.de` or `xn--bcher-kva.de`; `пример.рф` or `пример.xn--p1ai`), so
**every comparison is made on the DNS form** (`intake.dns_form`: lower case ASCII, each
internationalised label IDNA-encoded, which is how `PUT /clients/{clientId}/competitors`
compares a rival's domain with the client's): the rule, whether a domain is a brand's own,
whether it is confirmed or dismissed or listed twice, which brand claims it, and which rival's
row a request names. `пример.xn--p1ai` for a client at `пример.рф` is the client's own host, not
another site of it; `bücher.at` for a client at `xn--bcher-kva.de` is.

```jsonc
// GET and the answer to PUT
{
  "confirmed": [
    { "domain": "rmit.edu.vn", "brandKind": "client", "brandName": "RMIT University",
      "brandDomain": "rmit.edu.au" },
    { "domain": "monash.edu.my", "brandKind": "rival", "brandName": "Monash University",
      "brandDomain": "monash.edu" }
  ],
  "proposals": [
    { "domain": "rmit.com.sg", "citations": 4, "brandKind": "client",
      "brandName": "RMIT University", "brandDomain": "rmit.edu.au" }
  ],
  "dismissed": ["wikipedia.org"]
}
```

`GET` **reads and writes nothing.**

- **`confirmed`**: the client's own confirmed sites, then those of each active rival of the list
  the client's **next** scan will use, in rank order (the client's next list if it has one, else
  its latest scan's set: the list `GET /clients/{clientId}/competitors` returns). A struck rival,
  or one with no domain, lists nothing. `brandName` is the client's brand name, else its name, or
  the rival's name. `domain` is **what is stored, in the DNS form** (`xn--bcher-kva.at` for
  `bücher.at`); `brandDomain` is the brand's own domain as it is held, in the spelling it was
  typed. A host the lists hold twice in two spellings (a list written by hand, or by a save from
  before the DNS form was stored) is listed once.
- **`proposals`**: from the client's **latest finished scan** (`succeeded` or `partial`, with at
  least one answered result), citations counted **per registrable domain** across its answered
  results (an engine that timed out cited no one). A cited domain is proposed for the client if
  the rule holds for it; otherwise for the **first rival in rank order** for which it holds.
  Never the client's own domain or a rival's own domain, and never one already confirmed (for any
  brand) or dismissed, in either spelling. **A proposal keeps the spelling the engine cited** (the
  domain it cited: `bücher.at`), though it is matched on the DNS form. Most-cited first, then by
  domain. Empty for a client with no finished scan.
- **`dismissed`**: the domains the agency said are nobody's own, **one list per client**, for the
  client and its rivals alike, **as stored, in the DNS form**. They are never proposed again.

`PUT` body (camelCase, **all three lists named**; a body that leaves one out is a `422` and
clears nothing):

```json
{
  "client": ["rmit.edu.vn"],
  "rivals": [ { "rivalDomain": "monash.edu", "sites": ["monash.edu.my"] } ],
  "dismissed": ["wikipedia.org"]
}
```

It **replaces all three**. A rival left out of `rivals` has its sites cleared. The answer is the
`GET` body. Every domain is **checked** by the check `PUT /clients/{clientId}/competitors` makes
of a rival's domain (`intake.rival_domain`, launch checklist 3.81): lower-cased, ONE trailing dot
and ONE leading `www.` dropped, and what is left must be its own registrable domain with a
valid hostname. A scheme, a path, a port or a subdomain is refused, never cut down to another
site. It is then **stored in the DNS form**: `bücher.at` is stored, listed and answered as
`xn--bcher-kva.at`. That is lower case ASCII, which a JSONB column holds in a database of any
encoding, and it makes a list hold **one entry per host**: a host named twice in one list, in
any spellings, is one entry, and saving a host again in the other spelling changes nothing (a
save that changes no rival's sites makes no next list). A rival is named by its `rivalDomain` in
either spelling and is that rival. At most 10 entries in `rivals`.

**The caps count entries as sent, and are checked before any site is read.** At most 20 sites
for a brand and 200 dismissed domains: a list of 21 with one domain repeated is refused, though
it names 20. Only the rivals' own domains (at most 10) are read before the caps are checked, so
what a refusal costs is bounded by the caps and not by how long a list the request carried.

**Where the lists live.** The client's confirmed sites and the dismissed list are on the client
(`clients.other_sites`, `clients.dismissed_other_sites`). **A rival's sites are on its row**
(`competitors.other_sites`) **on the client's next list**, never on a scan's own set: the list the
next scan will adopt is edited in place, or made as a copy of the latest scan's set exactly as
`PUT /clients/{clientId}/competitors` does when it has none. **A scan that has started keeps the
set it started with**, so a save moves nothing a finished scan shows. A save that changes no
rival's sites (the client's own lists, the dismissed list) makes no next list. Both columns
default to `[]`, and every client and rival that existed before is correct as it stands.

**A rival's sites are carried wherever its row is.** Copying a set (a scan carrying the latest
set forward, a save or a detection run making the next list) copies them. A `PUT
/clients/{clientId}/competitors` that keeps a rival at the same host keeps them, and one that
moves it to another host, or drops its domain, clears them: they were confirmed against the old
domain. The same host in the other spelling (`xn--bcher-kva.com` for `bücher.com`) is the same
host. A detection run keeps them on a rival it finds again at its host, clears them on a rival
it finds again at another host, and gives a new rival none.

**While the client's most recent scan is `running`**, `PUT` answers `409 conflict` ("A scan of
this client is running. Change its other sites after it finishes.") and writes nothing, as for the
competitors list. A `queued` or finished scan is no reason to refuse.

**Errors.** `401 authentication-required`. `404 not-found` ("No client with that identifier."):
another agency's client is the same `404` as an unknown or malformed id, on both routes.
`409 conflict` (above). **`422 validation-failed`**, before anything is written, for the first
thing wrong: `detail` is **one plain sentence that names the domain** as the person typed it
(lower-cased, `www.` and a root dot dropped; never its DNS form), `errors[0].message` is the
same sentence, `errors[0].field` is where (`client.1`, `rivals.0.rivalDomain`,
`rivals.0.sites.2`, `dismissed.0`, or the list itself for a cap) and `errors[0].type` is one of
the codes below. **The order is fixed, so one request always gets the same answer:**

1. a `rivalDomain` that is not a bare domain (`invalid_domain`), the rivals' own domains being
   the first thing read;
2. the caps (`too_many_sites` for the client's list, then each rival's in order;
   `too_many_dismissed`), on the lists as sent, before any site is read;
3. a site or a dismissed domain that is not a bare domain (`invalid_domain`: the client's sites,
   then each rival's, then the dismissed);
4. the rivals named: each in order, `repeated_rival` then `unknown_rival`;
5. the sites, the client's then each rival's, each in order: `a_brands_own_domain`, then
   `not_the_same_name` (or `shared_hosting` when the site's own public suffix is a private one),
   then `one_brand_only`;
6. `confirmed_and_dismissed`.

Every comparison in 4 to 6 is on the DNS form. The codes:

| `errors[0].type` | Sentence (for the domain named) |
|---|---|
| `invalid_domain` | intake's own sentence for the address (a `rivalDomain`, a site or a dismissed domain): not a hostname, no public domain, or "Enter just the domain, like rival.com: no https://, page path or subdomain." It quotes nothing typed (an address can carry a password), so `field` says which entry. |
| `too_many_sites` | "{brand domain} can have at most 20 other sites." (the client's list, or one rival's; entries counted as sent) |
| `too_many_dismissed` | "At most 200 domains can be dismissed." |
| `repeated_rival` | "{domain} is listed more than once." |
| `unknown_rival` | "{domain} is not one of this client's rivals." (not an active rival of the list the next scan will use) |
| `a_brands_own_domain` | "{domain} is a brand's own domain here, so it cannot be confirmed as another site." (the client's own, or an active rival's own) |
| `not_the_same_name` | "{domain} is not the same name as {brand domain} with a different ending, so it cannot be confirmed as one of its other sites." |
| `shared_hosting` | "{domain} is an address on a service anyone can sign up to, so it cannot be confirmed as one of {brand domain}'s other sites." (the site's public suffix is in the private section of the list: `rmit.github.io`) |
| `one_brand_only` | "{domain} can be confirmed for one brand only." |
| `confirmed_and_dismissed` | "{domain} cannot be both confirmed and dismissed." |

A body that is not shaped like the request (a list missing, a domain over 253 characters, more
than 10 `rivals`, more than 1000 domains in one list) is the ordinary `422` of any request, with
pydantic's own `errors[]`.

**Logged:** one line on a successful `PUT`, `other_sites.saved`, with `client_id` and the counts
`client_sites`, `rival_sites` and `dismissed`. No domain, and no address of a person.

**Facts only.** Every field is a domain, a count, or the name and domain of a brand already
stored. **No new dependency, outbound host or setting.**

### Finding 2 — industry classification confidence is uncalibrated

`Client.industry_confidence_score` is the model's own stated confidence, and
nothing has ever checked it against outcomes. A high score does not mean a
correct label. It is consumed as a threshold in `classify.decide`, so a
miscalibrated score silently changes what gets stored as a classification
rather than as `ambiguous`.

Consequences reach further than Epic 2: a wrong industry seeds SERP queries in
Epic 3, which seeds the competitor set, which feeds Share of Voice in Epic 5.
`CompetitorSet.used_industry_seed` exists specifically so this is answerable
after the fact.

Open because calibrating it needs labelled outcome data this system does not
yet collect. Recorded across `build-log.md` Epics 2.6, 2.8, 3.0, 3.5 and in the
Epic 2 section above.

### Finding 4 — a competitor override destroyed citation and mention attribution

**Fixed in Epic 3.9.** Recorded in full because the register flagged the fix as
possibly needing a product decision, and it turned out not to.

`Citation.competitor_id` and `BrandMention.competitor_id` are the only two FKs
pointing at `competitors.id`, and both are `ON DELETE SET NULL`. Both competitor
write paths used to hard-delete rows — `apply_override` deleted every row before
re-inserting, and `persist_detection` deleted every non-manual row on each run —
so an override *or a re-detection* silently nulled the attribution for the whole
scan. The finding as originally written named only `apply_override`; Epic 3.9
confirmed `persist_detection` had it too and fixed both.

**Both now reuse the row when the rival is unchanged**, keyed on
`slugify(name)` — the key both functions already used for other purposes — with
an `_apply_*` helper shared between the reuse and insert paths, matching the
discipline `scoring_runner` and `audit_runner` use. Keeping the id keeps the
foreign keys.

A struck rival becomes a tombstone **in place** rather than being deleted and
replaced, so its attribution survives too; `active_competitors` still filters it
out, so a citation attributed to a struck rival resolves to no name and presents
as third party. The operator's correction is respected without the underlying
fact being destroyed. `apply_override` is now delete-free entirely.

`persist_detection` still deletes an auto-detected row that the current run did
**not** re-find, and its attribution is nulled with it. That is correct — the
rival has left the set — and it is now the only case where attribution is lost,
where previously every run lost all of it.

**The semantic concern this register raised did not apply.** "Replace the set
wholesale" is a statement about the resulting state — no partial merge, every
submitted row ends up `MANUAL` with signals zeroed — and that is unchanged. Only
the mechanism used to reach it changed. Nothing observable differs: `CompetitorOut`
exposes no `created_at`, and no consumer relies on competitor ids *changing*.

**A second, unrelated defect surfaced while fixing this one**, and is fixed with
it: deleting `Keep` and inserting `Keep` in one flush is a same-table
delete-then-insert on `uq_competitors_set_name`, and SQLAlchemy orders INSERTs
before DELETEs — so **re-running detection on a scan that re-found any rival
returned a 500**, and had since Epic 3. Reuse removes the delete/insert pair, so
the collision cannot arise. Covered by
`test_redetecting_the_same_rival_does_not_500`.

### Finding 5 — `verify_competitors.py` verifies a copy of the detection pipeline

`scripts/verify_competitors.py` is the live check for §7 Epic 3's acceptance
criterion. It calls `detect_for_client` **zero** times. Instead it reassembles
the pipeline itself from `build_queries`, `build_seed_prompts`,
`merge_candidates` and `score_candidates`, and measures that.

So it verifies a copy. If `detect_for_client` drifted from this reassembly — a
new gate, a changed ordering, a different cap — the script would keep reporting
the old behaviour's precision and keep printing PASS. The number it prints is
real (80% at last run, Epic 3.10) but it is a statement about the script's
reconstruction, not about what the API does.

This is the third instance of the same trap in this codebase. Epic 4.0 named it
("a guard that has never been observed to fail is not evidence"); Epic 3.6's
`verify_competitor_override.py` was written against a copy of `apply_override`
and passed against its own copy while the endpoint was still wrong; Epic 3.8's
first fix shipped a negative control that could not fail.

**Fixed in Epic 3.11** by the second option — extracting a database-free core.

**This register was wrong about the cost.** It said the change "is not a small
change" because `detect_for_client` takes a `Client` row. Re-reading the
function for Epic 3.11: it makes **zero** database calls and reads the `Client`
in exactly six places, every one of them a plain scalar (`brand_name`,
`domain`, `industry`, `industry_niche`, `name`, and `id` for a log line). The
ORM object was only ever an awkward way to pass six strings, so the "core" the
register imagined extracting was essentially the whole function.

`detect_from_facts` now holds the body and takes those six scalars;
`detect_for_client` is a thin unpack over it, so no existing caller changed.
The script calls `detect_from_facts` and holds no database connection, keeping
the property the register wanted to protect.

**A correction to the description above, and to Epic 3.10's write-up.** Both
said the script "reassembles the pipeline" and stopped there. It also called
`decide_detection`, with arguments structurally identical to the service's — so
the two were genuinely equivalent, and the 80% precision reported in Epic 3.10
was a sound number. Finding 5 was a **drift risk, not a live incorrectness**,
and saying so plainly matters: the entry as written implied the measurement had
been wrong all along, which would have been a much more serious thing.

`--serp-only` still assembles its own outcome, because `detect_from_facts`
always runs both signals. It now says so in the code rather than leaving a
reader to assume the diagnostic half measured what the API does.

Guarded by `TestDetectionHasOneImplementation`: the wrapper and the core must
return identical outcomes for identical facts; the core must stay free of
`session`/`select`/`commit`/`execute`, which is the property that lets a
database-free script call it; and the wrapper must hold no logic of its own,
since logic there would run in production but not in the script — reopening
this finding silently. Negative-controlled in both directions.

Not re-run live. The full script costs 60 SerpApi searches and 40 model calls,
the change is structurally verified with comments stripped (a naive grep
matches the explanatory comment's own prose, which named the old functions),
and re-spending to watch it print the same 80% was not worth it.

### Finding 6 — no verification script covers the five-dimension scoring path

`scripts/verify_scoring.py` never runs a technical audit, so
`technical_foundation` is always `NOT_YET_MEASURED` and only the degraded
four-of-five-dimension path is exercised. `scripts/verify_audit.py` covers the
audit and the dimension, but on a scan that already has one it measures a
re-audit, not the transition that closes the exclusion.

So since Epic 6 added the fifth dimension, no live script has verified the
complete formula end to end. That is not hypothetical: Epic 3.10 found that
`compute_inputs_digest` had been omitting `technical_foundation` for the same
four epics, and the reason nothing caught it is exactly this gap.

**Addressed in Epic 3.11** by the first option: `verify_scoring.py` gained an
audit step. The crawl is one page of Playwright and costs nothing, so the
argument against adding it was about what the script is *for*, not about money
— and a scoring verification that cannot exercise one of the five scored
inputs is not verifying the formula.

The script now scores **before** the audit, runs the audit, and scores again,
asserting four things about the transition rather than printing a caveat:
`technical_foundation` becomes included, every dimension in the `Dimension`
enum is included (derived from the enum, not a hardcoded 5 — the hardcoded-list
defect class this codebase keeps hitting), the `TECHNICAL_FOUNDATION_NOT_MEASURED`
flag is gone, and **the `inputs_digest` moves**. That last one is the live
regression test for the Epic 3.10 defect: everything else about the scan is
byte-identical across the two scores, so a digest that does not move means
`technical_foundation` is not in it.

The determinism loop now runs over the five-dimension path too, which was the
other half of the gap — reproducibility had only ever been demonstrated for a
formula that excluded one of its inputs.

`--skip-audit` restores the old behaviour and prints the same caveat the script
used to print unconditionally, so the four-dimension mode stays available and
stays honest about what it covers.

**Verified live**, against a throwaway database, on 2026-08-24. Real SerpApi
detection, real model calls, real Playwright crawl. `avp_dev` untouched — the
run's scan is absent from it, and the only `Scoring Verification` agency there
dates from 2026-08-21.

    composite     : 59.22  ->  62.05
    inputs_digest : 7604bc4c41fb26af  ->  75429cf57317e2ec
    included      : 5/5
    flags         : [NOT_MEASURED, NO_AUTHORITY_DATA] -> [NO_AUTHORITY_DATA]
    RESULT: PASS   deterministic across 5 re-scores, one score row

Three of the four assertions are self-evidently non-vacuous: the run printed
the failing state and then the passing state within a single execution, which
is better evidence than a synthetic control could give.

The digest assertion was negative-controlled separately, against the rows that
run persisted. Reverting `compute_inputs_digest` to its Epic 3.10 defect
collapses both digests to one value (`7785e2c34b073f0a`) and the assertion
returns False — so the script would have failed. Restored, it returns True and
reproduces the two digests the live run printed exactly.

### Finding 3 — `detectionConfidence` describes a mixed competitor set

`CompetitorSet.detection_confidence` is computed as the share of the returned
set that SERP and co-citation surfaced **independently of each other**. It is
therefore a statement about *detected* rows only.

`apply_override` clears it to null, which is correct — an operator's set was
corroborated by nothing. But a subsequent **re-detection** sets it again from
that run's outcome (`services/competitors.py`, `persist_detection`), and that
outcome measured agreement across only the rows detection found. Any manual
rows that survived are not in the calculation. The report then presents a
single corroboration figure for a set that is part-detected, part-hand-set, and
`ReportCompetitorSetOut.detectionConfidence` gives a reader no way to tell.

**Not a bug in the arithmetic** — the number is correct for what it measures.
The defect is that the field's meaning is undefined once a set is mixed, and
the API presents it as though it describes the whole thing.

**Partly closed in Epic 3.11** by the second option: scope it explicitly.

`CompetitorSetOut` and `ReportCompetitorSetOut` now both carry
`confidenceCovers` — the number of rows in the set that detection produced,
which is what the figure is a statement about. Derived from the rows at
projection time via `CompetitorSet.detected_competitors` rather than stored, so
it cannot go stale against the list it counts. The stored value's arithmetic is
untouched; only what the API says about its scope changed.

The report now renders the figure at all, which it never did. That is worth
recording on its own: the note under the competitor table referred the reader
to "the corroboration figure above", and no such figure was ever on the page —
so the copy pointed at nothing for five epics. It now reads "Search results and
AI answers independently surfaced 75% of the 4 rivals detection found. The
remaining 1 of the 5 below were set by hand and are not in that figure."

`confidenceCovers` is deliberately **not** the figure's own denominator, and is
documented as not being it. Detection computes the ratio over every candidate
it ranked, including ones the operator had already named or struck, which are
then held back from the set. The published count is the number of rows a reader
can actually see it apply to, which is the number the report needs.

It is also not a proxy for the confidence being present: a set where only one
signal ran carries a null confidence and a full complement of detected rows,
and a set where re-detection re-found nothing but rivals the operator had
already named carries a real confidence and zero of them.

**Still open: what the field should MEAN on a mixed set.** Scoping it stops the
API overstating what it measured, which was the misleading part. It does not
decide whether Epic 5 should treat a 0.80-over-4-of-6 set as more or less solid
a comparison base than a 0.80-over-6-of-6 one. That is still a scoring-semantics
decision, and the third option — a per-row property — is still the more
principled long-term answer.

Guarded on both projections independently (`TestConfidenceSaysWhatItCovers` and
`TestCompetitorSetScope`), because they are separate schemas built by separate
functions and fixing one would have left the figure misleading in the place a
client actually reads it. Negative-controlled: making either projection count
all active rows fails that projection's tests and only that projection's.

Surfaced by Epic 3.6's competitor-provenance badge, which is what made a mixed
set visible in the first place. `scripts/verify_competitor_override.py` prints
it as a `NOTE` on every run rather than failing, so it stays on the record.

### Finding 7 — the Report's two charts outgrow their own type

`verify_chart_scale.py` reports 25 offenders across five viewports, all of them
`avp-ledger__svg` or `avp-shelf__svg`. An SVG at `width: 100%` over a fixed
viewBox scales its TYPE with its box, so the Ledger's 10px dimension labels
render at up to 28.2px against 14px body copy — the defect Epic 9.19 fixed for
one figure and Epic 9.21 fixed for `TrendChart`, still present on these two.

**Measured, not assumed: 25 before Epic 9.24 and 25 after.** That epic took the
style guide from 6 charts to 7 and its new Working-palette `TrendChart` added
zero, so this pre-dates it entirely and is unrelated to the accent layer.

**Left open deliberately.** The Ledger and the Shelf are the *Report's* charts.
The fix is `style={{ maxWidth: layout.width }}`, the same one-line bound
`TrendChart` carries — and applying it would change how the Report renders,
which Epic 9.24's brief explicitly put out of scope ("the Report gets zero
visual changes of any kind"). It is a small, well-understood fix waiting for a
brief that is allowed to touch the document.
