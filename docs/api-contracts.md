# API Contracts

Every endpoint in `apps/api` is recorded here in the same task that adds it:
method, path, request shape, response shape, auth, error cases.

**Status:** Epic 6 complete — 25 endpoints.
**Machine-readable source of truth:** `packages/shared-types/openapi.json`,
generated by `apps/api/scripts/export_openapi.py`. This document explains
intent; the schema defines the shapes.

---

## Conventions (set in Epic 0, applied from Epic 1)

- Base path: `/api/v1`
- Content type: `application/json; charset=utf-8`
- Casing: `camelCase` in JSON bodies, `kebab-case` in path segments.
- IDs: prefixed ULIDs (e.g. `scan_01J...`) so an ID is self-describing in logs.
- Errors: RFC 9457 `application/problem+json` — `{ type, title, status, detail, instance }`.
- Pagination: cursor-based — `?limit=&cursor=`, response `{ data: [], nextCursor: string | null }`.
- Timestamps: RFC 3339 UTC strings.

### Authentication

An **httpOnly session cookie** (`avp_session`), not a bearer token.

Chosen because this is seat-based software: when an agency removes a seat, that
person's access must end immediately. A JWT cannot be revoked without a
server-side blocklist consulted on every request — which is a session store
with extra steps. Consequences: `httpOnly` means XSS cannot read the cookie,
revocation is a `DEL`, and "sign out everywhere" is a set scan.

Sessions live in Redis; only the SHA-256 digest of the token is stored, so a
Redis dump does not yield working cookies. Every authenticated request re-reads
the user and agency from Postgres, so a suspended user or deleted agency loses
access on their *next* request.

Cross-origin callers must send `credentials: 'include'`, and the origin must be
listed in `CORS_ALLOW_ORIGINS` — browsers reject wildcard CORS with credentials.

### Error types

| `type` | Status | Meaning |
|---|---|---|
| `/problems/validation-failed` | 422 | Body failed validation. Carries `errors[]` |
| `/problems/authentication-required` | 401 | No, expired, or invalid session |
| `/problems/invalid-credentials` | 401 | Login failed |
| `/problems/permission-denied` | 403 | Authenticated but wrong role |
| `/problems/not-found` | 404 | No such resource in the caller's agency |
| `/problems/conflict` | 409 | Generic conflict |
| `/problems/email-already-registered` | 409 | Signup email in use |
| `/problems/seat-limit-reached` | 409 | Carries `seatsUsed`, `seatLimit` |
| `/problems/rate-limited` | 429 | Too many requests |
| `/problems/invalid-url` | 409 | Submitted URL has no public domain |

Validation problems add an `errors` member:

```json
{
  "type": "/problems/validation-failed",
  "title": "Request validation failed",
  "status": 422,
  "detail": "One or more fields were invalid.",
  "instance": "/api/v1/auth/sign-up",
  "errors": [
    { "field": "password", "message": "String should have at least 12 characters", "type": "string_too_short" }
  ]
}
```

## Endpoints

### Health

#### `GET /api/v1/health`
Liveness. **No auth.** Touches no dependency deliberately — a liveness probe
that checks the database causes an orchestrator to restart healthy API pods
during a database blip, turning a partial outage into a total one.

```json
{ "status": "ok", "version": "0.1.0" }
```

#### `GET /api/v1/ready`
Readiness. **No auth.** Verifies Postgres and Redis. Returns `503` with
`status: "degraded"` if either is unreachable.

```json
{ "status": "ready", "checks": { "postgres": "ok", "redis": "ok" } }
```

### Auth

#### `POST /api/v1/auth/sign-up`
Create an agency and its first user, and sign them in. **No auth.**

The first user of an agency is always `owner` — an agency with no owner has
nobody who can manage seats. Signing in as part of signup is deliberate:
requiring a fresh login right after choosing a password is friction with no
security value.

**Request**
```json
{
  "agencyName": "Meridian Search Partners",
  "fullName": "Dana Whitfield",
  "email": "dana@meridiansearch.example",
  "password": "at least 12 characters"
}
```

Password rules follow NIST SP 800-63B: 12–256 characters, no composition
requirements. Composition rules push users toward predictable substitutions.
A password using fewer than 5 distinct characters is rejected.

**Response `201`** — body is `MeOut` (below). Sets the `avp_session` cookie.

**Errors:** `409 email-already-registered`, `422 validation-failed`.

#### `POST /api/v1/auth/login`
**No auth.**

```json
{ "email": "dana@meridiansearch.example", "password": "..." }
```

**Response `200`** — `MeOut`. Sets the `avp_session` cookie.

**Errors:** `401 invalid-credentials`.

Unknown email, wrong password, and suspended account all return an *identical*
response, and the unknown-email path performs a dummy Argon2 verification so
that response latency does not leak account existence.

#### `POST /api/v1/auth/logout`
**Auth required.** Revokes the current session only. **`204`, no body.**

#### `POST /api/v1/auth/logout-all`
**Auth required.** Revokes every session for the caller, on every device.
**`204`, no body.**

#### `GET /api/v1/auth/me`
**Auth required.** The whole authenticated context in one call, so the web app
shell does not need three round trips per page load.

**Response `200`** — `MeOut`:
```json
{
  "user": {
    "id": "user_01J...",
    "email": "dana@meridiansearch.example",
    "fullName": "Dana Whitfield",
    "role": "owner",
    "status": "active",
    "lastLoginAt": "2026-08-20T05:31:44Z",
    "createdAt": "2026-08-20T05:29:02Z"
  },
  "agency": {
    "id": "agcy_01J...",
    "name": "Meridian Search Partners",
    "slug": "meridian-search-partners",
    "seatLimit": 3,
    "createdAt": "2026-08-20T05:29:02Z"
  },
  "seats": { "used": 1, "limit": 3 }
}
```

**Errors:** `401 authentication-required`.

### Dashboard

#### `GET /api/v1/dashboard`
**Auth required.** Scoped to the caller's agency.

**Query:** `limit` (1–50, default 10) — how many recent scans to include.

**Response `200`**
```json
{
  "agency": { "...": "AgencyOut" },
  "seats": { "used": 1, "limit": 3 },
  "clientCount": 0,
  "scanCount": 0,
  "recentScans": [],
  "isEmpty": true
}
```

`isEmpty` is true when the agency has no clients and no scans, so the frontend
can show the onboarding path rather than an empty table.

Each entry in `recentScans` is a `ScanSummaryOut`:

```json
{
  "id": "scan_01J...",
  "clientId": "clnt_01J...",
  "clientName": "Northaven Dental",
  "clientDomain": "northaven-dental.example",
  "status": "succeeded",
  "compositeScore": "38.35",
  "createdAt": "2026-08-20T05:40:11Z",
  "finishedAt": "2026-08-20T05:43:02Z"
}
```

`compositeScore` is a **string-encoded decimal or `null`**. It is a string
because the value is `NUMERIC(5,2)` in Postgres and a JSON number would
reintroduce binary-float error on the wire, which `docs/scoring-spec.md`
determinism rule 3 exists to prevent. It is `null` both when a scan is unscored
and when scoring returned `INSUFFICIENT_DATA` — **the UI must render null as
"—", never as 0.** An unrunnable scan must never appear to a client as a bad
score.

Scans are ordered newest-first by `id`. IDs are ULIDs, so that is creation
order and the same column serves as the pagination cursor.

**Errors:** `401 authentication-required`.

### Clients (intake & classification) — Epic 2

#### `POST /api/v1/clients`
**Auth required.** §5.4 step 1: submit a URL, crawl it, classify its industry.

Runs **synchronously**. §7's acceptance criterion is a classified industry
within 30 seconds of submitting a URL; the measured path is a few seconds, so
one round trip is both sufficient and simpler than a polling protocol.

**Request**
```json
{ "url": "northaven-dental.com", "name": null, "classify": true }
```

`url` is permissive — a bare domain, a full URL, or any page on the site. It is
normalised server-side against the Public Suffix List. `name` is an optional
operator label; when absent, the classifier's extracted brand name is used,
falling back to the domain. `classify: false` creates the record without
spending an LLM call (used by tests and by Epic 10's bulk upload).

**Response `201`** — `ClientDetailOut`:
```json
{
  "id": "clnt_01J...",
  "agencyId": "agcy_01J...",
  "name": "Northaven Dental",
  "domain": "northaven-dental.com",
  "kind": "prospect",
  "industry": "dental practice",
  "industryNiche": "cosmetic and implant dentistry",
  "brandName": "Northaven Dental",
  "classificationStatus": "classified",
  "classificationReasonCode": null,
  "industryConfidence": "high",
  "industryConfidenceScore": "0.920",
  "classifiedAt": "2026-08-20T18:04:11Z",
  "classifierModel": "claude-opus-5",
  "crawl": {
    "pagesFetched": 3,
    "urlsFetched": ["https://northaven-dental.com/", "https://northaven-dental.com/about"],
    "schemaTypes": ["LocalBusiness", "Dentist"],
    "wordCount": 1584,
    "h1Count": 1,
    "hasTitle": true,
    "hasMetaDescription": true,
    "detectedLanguage": "en"
  },
  "createdAt": "...", "updatedAt": "..."
}
```

**`classificationStatus` is the field to branch on.** It has four values, and
three of them mean `industry` is `null`:

| Status | `industry` | Meaning |
|---|---|---|
| `pending` | `null` | Created with `classify: false`; not yet attempted |
| `classified` | **set** | Confident result |
| `ambiguous` | `null` | Crawled fine, but the evidence did not support a confident call |
| `unclassifiable` | `null` | Could not read the site, or it is not a business site |

**The UI must never render a null industry as an empty field or a dash that
reads like data.** `ambiguous` is a distinct outcome that needs its own
treatment, for the same reason a null score is not a zero: a wrong industry
silently poisons Epic 3's competitor detection and Epic 4's prompt generation,
and neither has any way to detect that its input was wrong. This is enforced in
the database by `ck_clients_industry_matches_classification_status`.

`classificationReasonCode` explains a non-`classified` status:

| Code | Cause |
|---|---|
| `LOW_CONFIDENCE` | Model confidence below the 0.70 threshold |
| `NOT_A_BUSINESS_SITE` | Parked domain, error page, login wall, directory listing |
| `INSUFFICIENT_CONTENT` | Page carried too little text to classify |
| `FETCH_FAILED` | Site did not resolve or the browser could not load it |
| `HTTP_404`, `HTTP_403`, … | Site answered with that HTTP status (bot or geo blocking) |
| `PROVIDER_QUOTA_EXHAUSTED` | Anthropic credit balance exhausted |
| `PROVIDER_RATE_LIMITED` / `PROVIDER_UNREACHABLE` / `PROVIDER_ERROR` | Upstream model call failed |
| `PROVIDER_REFUSED` | Model declined to answer |

`industryConfidenceScore` is a **string-encoded decimal or `null`**
(`NUMERIC(4,3)`), for the same reason as `compositeScore`: a JSON number is an
IEEE double.

**`crawl` contains FACTS only** — counts, booleans, URLs, and schema.org type
names. Page text is never returned (ip-safety.md #7); the projection in
`routers/clients.py:_crawl_summary` names every field explicitly so adding one
to `CrawlSignals` cannot silently start returning it.

**Errors:** `401`, `409 invalid-url`, `409 conflict` (domain already tracked by
this agency — carries `clientId`), `422 validation-failed`.

An unreachable site is **`201` with `classificationStatus: "unclassifiable"`**,
not an error status. A site that will not load is a normal outcome for a tool
pointed at an arbitrary URL.

#### `GET /api/v1/clients`
**Auth required.** Cursor-paginated, newest first.

**Query:** `limit` (1–100, default 25), `cursor`.
**Response `200`** — `{ "data": [ClientOut], "nextCursor": string | null }`.

#### `GET /api/v1/clients/{clientId}`
**Auth required.** Returns `ClientOut`.

**Errors:** `404 not-found` — returned both for an unknown id and for a client
belonging to another agency. Confirming that an id exists is itself a leak
across a tenant boundary, so it is never a `403`.

#### `POST /api/v1/clients/{clientId}/reclassify`
**Auth required.** Re-crawls and re-classifies an existing client, returning
`ClientDetailOut`. Needed because sites change, and because an `ambiguous`
result is often worth retrying after an operator has looked at the site.

### Competitors (detection & override) — Epic 3

#### `POST /api/v1/clients/{clientId}/competitors/detect`
**Auth required.** §5.4 step 2: SERP discovery + AI co-citation discovery,
deduped and ranked.

Runs **synchronously** and **costs money** — roughly six SerpApi searches and
four model calls per run — so it is explicitly operator-triggered rather than
implicit in intake.

**Response `201`** — `CompetitorSetOut`:
```json
{
  "id": "cset_01J...",
  "scanId": "scan_01J...",
  "status": "ok",
  "detectionConfidence": "0.800",
  "serpQueriesRun": 6,
  "coCitationPromptsRun": 4,
  "candidatesConsidered": 26,
  "usedIndustrySeed": true,
  "detectedAt": "2026-08-21T10:31:02Z",
  "competitors": [
    {
      "id": "comp_01J...", "name": "Calendly", "domain": "calendly.com",
      "rank": 1, "detectionSource": "both",
      "serpMentions": 4, "coCitationMentions": 3,
      "corroborated": true, "signalCount": 7,
      "score": "2.184", "isManualOverride": false
    }
  ]
}
```

**`detectionConfidence` is null, not zero, when only one signal ran.** Zero means
"two independent signals looked and agreed on nothing"; null means agreement was
never measurable. Rendering null as `0%` would be a false claim about evidence
that does not exist — the same distinction as a null score vs a zero score.

**`status`:**

| Status | Meaning |
|---|---|
| `ok` | Usable set with cross-signal agreement |
| `weak_signal` | Ran, but fewer than 3 rivals, no corroboration, or only one signal available. Show it, flag it, invite an override. |
| `no_signal` | Neither signal produced a usable candidate. `competitors` is `[]`. |

**`detectionSource`** is `serp`, `co_citation`, `both`, or `manual`. `both` is
the strongest evidence available: two methods that fail differently agreed.

**Measured precision by source** (10-URL verification, build-log Epic 3.4):
`both` 100%, `co_citation` 100%, `serp`-only **45%**. Treat a `serp`-only rival
as a suggestion, not a finding.

**`usedIndustrySeed`** records whether `Client.industry` seeded the queries.
Industry classification confidence is uncalibrated (Finding 2, open), so when an
operator reports a bad set the first question is whether a bad industry label
seeded it — this makes that answerable without re-running.

**Errors:** `401`, `404 not-found` (unknown client, or another agency's).

#### `GET /api/v1/clients/{clientId}/competitors`
**Auth required.** The client's most recent set, competitors in rank order.

**Errors:** `401`; `404` if detection has never run — detail: *"No competitor
set for this client. Run detection first."*

#### `PUT /api/v1/clients/{clientId}/competitors`
**Auth required.** Replace the set by hand.

```json
{ "competitors": [ { "name": "Zendesk", "domain": "zendesk.com" } ] }
```

Replaces wholesale rather than patching rows: an operator correcting a bad
detection is asserting "these are the rivals", and reconciling that against
auto-detected rows invites a half-applied state.

Everything supplied is marked `isManualOverride: true` and **survives later
re-detection**, keeping the top ranks. An empty array clears the set and returns
`status: "no_signal"`.

**Anything currently in the set and not sent back is STRUCK, and stays struck.**
A struck rival is recorded rather than deleted, so a later detection run that
surfaces it again does not reinstate it. Until Epic 3.6 it was simply deleted,
which recorded nothing: additions survived re-detection and removals silently
reverted, so half of "correcting a set" did not hold. Struck rivals never appear
in any response — they are bookkeeping for the next detection run, not
competitors.

Re-sending a struck rival revives it, so an operator can change their mind.

**`detectionConfidence` is cleared to null.** It measures agreement between two
automated signals, and neither produced this set — keeping the old value would
attach a corroboration claim to rows that were never corroborated.

⚠️ **Known, open:** a later *re-detection* sets `detectionConfidence` again from
its own run, and that figure describes only the rows detection found — not the
operator's. The report then presents one corroboration figure for a set that is
part-detected and part-hand-set. Changing this means redefining what the field
measures, which is a scoring-semantics decision rather than a UI one. Recorded
in build-log Epic 3.6.

Max 10 competitors. **Errors:** `401`, `404`, `422`.

**CORS:** `PUT` was missing from `allow_methods` until Epic 3.6. This is the only
PUT in the API, nothing in a browser called it until the override UI shipped, and
the test suite drives the app through `ASGITransport`, which never issues a
preflight — so the endpoint was unreachable from a browser for five epics while
its own tests passed. `tests/test_cors.py` now derives the allowed method list
from the registered routes.

### Scans (prompt generation & engine execution) — Epic 4

#### `POST /api/v1/clients/{clientId}/scans`
**Auth required.** §5.4 steps 3–4: generate a prompt set, run it against every
engine, extract and persist facts.

Runs **synchronously and costs real money** — a full scan is 20–30 prompts across
every engine, plus a sentiment call per mention. The grounded engine has been
measured at up to 216s for a single prompt, so a full run takes minutes.

**Request**
```json
{ "promptLimit": 6, "engines": ["claude", "claude_search"] }
```

Both fields optional. `promptLimit` (1–30) caps the generated set for cost
control; omit for a real scan. `engines` defaults to both.

**Response `201`** — `ScanDetailOut` with `promptSet` and one `results` entry
per **prompt × engine pair**.

```json
{
  "id": "scan_01J...", "status": "succeeded",
  "promptCount": 6, "engineResultCount": 12,
  "engineVersions": {
    "claude": "claude-opus-5/parametric",
    "claude_search": "claude-opus-5/web_search_20260209"
  },
  "promptSet": {
    "generatedBy": "claude-opus-5",
    "generationParams": { "industry": "customer support software", "usedIndustrySeed": true },
    "prompts": [{ "id": "prmt_01J...", "text": "...", "intent": "awareness", "position": 1 }]
  },
  "results": [{
    "id": "eres_01J...", "promptId": "prmt_01J...",
    "engine": "claude_search", "status": "ok",
    "mentioned": true, "position": 2, "prominence": "0.812",
    "sentiment": "positive", "sentimentConfidence": "0.900",
    "brandsMentioned": 5, "responseDigest": "3513cdb4a7e1...", "latencyMs": 26997,
    "brandMentions": [{ "entityName": "Zendesk", "isSubject": false, "position": 1 }],
    "citations": [{ "sourceDomain": "g2.com", "sourceType": "review", "citesSubject": false }]
  }]
}
```

**Prompts are interleaved by intent.** `position` follows that order, so any
prefix of the set is representative of the buyer journey. This matters for
`promptLimit`: without interleaving a capped scan would measure awareness only
while reporting a mention rate that looks whole.

**`responseDigest` is a SHA-256 of the answer, and the answer itself is never
stored or returned** (ip-safety.md #7). It exists so a re-scan can detect "the
answer changed" without retaining it.

**`status` on each result:**

| Status | Meaning |
|---|---|
| `ok` | Answered, subject mentioned |
| `answered_no_mention` | Answered, subject absent — **a finding, not a failure** |
| `rate_limited` / `timeout` / `error` | The call did not produce an answer |

**Scan-level `status`:** `succeeded` (no failed calls), `partial` (some engines
failed), `failed` (all failed, with `errorCode: ALL_ENGINE_CALLS_FAILED`).
`partial` exists so a report can say "one engine was down" rather than
presenting a depressed mention rate as fact.

**`position` is the subject's rank among detected brands by first appearance.**
Brand detection is scoped to the subject plus **known competitors** — never
open-ended entity extraction. A scan run before Epic 3 detection reports
position 1 of 1 for every mention, because there is nothing else to detect.

**Errors:** `401`, `404` (unknown client, or another agency's), `422`.

#### `GET /api/v1/scans/{scanId}`
**Auth required.** The scan with its prompt set and every engine result.
`404` for an unknown scan or another agency's — never `403`.

#### `GET /api/v1/scans/{scanId}/results`
**Auth required.** Cursor-paginated engine results, ascending by id.
Separate from the scan detail because a full scan is 60+ rows with nested
mentions and citations.

**Query:** `limit` (1–200, default 25), `cursor`.

#### `GET /api/v1/scans/{scanId}/prompts`
**Auth required.** The generated prompt set, ordered by `position`.
`404` if the scan has no prompt set yet.

#### `GET /api/v1/clients/{clientId}/scans`
**Auth required.** A client's scans, newest first. Cursor-paginated.

### Scores (AI Visibility Score) — Epic 5

#### `POST /api/v1/scans/{scanId}/score`
**Auth required.** Computes and stores the composite score for a scan.

**Makes no provider calls and costs nothing.** Scoring is pure arithmetic over
rows Epic 4 already persisted. Sentiment is read from `EngineResult.sentiment`,
never re-classified (scoring-spec.md rule 4) — that is what makes re-scoring
reproducible.

**Response `201`** — `ScoreDetailOut`:
```json
{
  "id": "scor_01J...", "scanId": "scan_01J...", "status": "scored",
  "composite": "63.41",
  "mentionRate": "83.33", "shareOfVoice": "41.18",
  "citationStrength": "50.00", "sentiment": "75.00",
  "technicalFoundation": null,
  "formulaVersion": "v1.1",
  "weights": {
    "citation_strength": "22.22", "mention_rate": "33.33",
    "sentiment": "16.67", "share_of_voice": "27.78"
  },
  "excludedDimensions": { "technical_foundation": "NOT_YET_MEASURED" },
  "degradationFlags": ["NO_AUTHORITY_DATA", "TECHNICAL_FOUNDATION_NOT_MEASURED"],
  "reasonCode": null,
  "inputsDigest": "1f3a422c367d9c3f...",
  "competitors": [
    { "competitorId": "comp_01J...", "name": "Zendesk",
      "mentionRate": "100.00", "shareOfVoice": "35.29", "citationStrength": "25.00" }
  ]
}
```

**All score values are string-encoded decimals.** A JSON number is an IEEE
double, which is precisely what scoring-spec.md rule 3 forbids.

**`weights` are the EFFECTIVE weights after exclusions**, not the §6 table.
They always sum to 100, so a stored breakdown re-sums against its own weights.
The §6 table lives in `docs/scoring-spec.md`.

**`excludedDimensions` is `{dimension: reason}`,** and the reasons are not
interchangeable:

| Reason | Meaning | How a report should word it |
|---|---|---|
| `NOT_YET_MEASURED` | The capability does not exist yet (Technical Foundation, pending Epic 6) | "not yet checked" |
| `NO_POPULATION` | Nothing to measure for this brand (no mentions → no sentiment) | "nothing to measure" |
| `NO_COMPETITOR_SET` | Competitor detection returned nothing | "no comparison was made" |

An excluded dimension's weight is redistributed proportionally across the rest.
**A null sub-score is never a zero** — a brand nobody mentioned has not been
spoken of badly, and scoring it zero would punish the same absence twice.

**`degradationFlags`** record documented fallback paths, so a depressed number
can be explained: `NO_AUTHORITY_DATA` (there is no Domain Authority source in
this system, so Citation Strength normalises against the best-cited brand in the
same scan), `WEAK_COMPETITOR_SET` (Epic 3 detection was weakly corroborated —
SERP-only precision measured ~58%), `NO_CITATIONS_IN_SCAN`, `NO_COMPETITOR_SET`.

**`status: "insufficient_data"`** with `composite: null` and
`reasonCode: "INSUFFICIENT_DATA"` when no engine call answered. An unrunnable
scan is never rendered as a bad score.

**`inputsDigest`** is a SHA-256 over the exact EngineResult and Competitor rows
scored. Two scores sharing a digest were computed from identical data, so a
changed composite is always attributable to either changed inputs or a changed
`formulaVersion`.

**Re-scoring is idempotent per formula version.** A unique constraint on
`(scanId, formulaVersion)` means re-running under the same formula refreshes
that row; a formula change inserts alongside it, leaving prior versions intact.

**Competitors carry no composite.** Sentiment is classified toward the subject
only and Technical Foundation is Epic 6, so 25% of the weight has no
per-competitor input. A composite on a different weight basis would not be
comparable to the subject's, which is the point of a comparison.

**Errors:** `401`, `404` (unknown scan, or another agency's).

#### `GET /api/v1/scans/{scanId}/score`
**Auth required.** The most recent stored Score, with the competitor comparison
recomputed from persisted rows on read.

**Errors:** `401`; `404` — unknown scan, or *"This scan has not been scored yet."*

#### `GET /api/v1/scans/{scanId}/scores`
**Auth required.** Every Score for the scan, newest first — the audit trail of
which `formulaVersion` produced which composite from which `inputsDigest`.

### Technical audit — Epic 6

#### `POST /api/v1/scans/{scanId}/audit`
**Auth required.** Crawls the client's own site for structural signals and
records a verdict for each check.

**No model or search calls** — one page load plus two side fetches
(`robots.txt`, `sitemap.xml`). Cost is bandwidth and a few seconds.

**Response `201`** — `TechnicalAuditOut`:
```json
{
  "id": "taud_01J...", "scanId": "scan_01J...",
  "urlAudited": "https://helpscout.com", "status": "ok",
  "technicalFoundation": "87.50", "excludedComponents": {},
  "lcpMs": 812, "cls": "0.053", "inpMs": null,
  "schemaTypes": ["VideoObject", "WebSite", "Corporation"],
  "hasOrganizationSchema": true, "hasLocalbusinessSchema": false,
  "isIndexable": true, "hasSitemap": true, "canonicalPresent": true,
  "h1Count": 1, "wordCount": 877, "contentAgeDays": 0,
  "checks": [
    { "checkKey": "indexable", "status": "pass", "detailCode": null },
    { "checkKey": "schema_present", "status": "pass", "value": "3" },
    { "checkKey": "cwv_inp", "status": "not_applicable",
      "detailCode": "FIELD_METRIC_REQUIRES_REAL_USER_DATA" }
  ]
}
```

**`checks` is the primary deliverable** (§7: "pass/fail + detail for each
check"), returned in display order — crawlability first, since it gates
everything else, then markup, then content, then lab measurements.
`status` is `pass | warn | fail | not_applicable | error`; `detailCode` is
machine-readable (`NO_STRUCTURED_DATA`, `META_ROBOTS_NOINDEX`,
`ROBOTS_TXT_DISALLOW`, …), never prose.

**`technicalFoundation`** is the §6 sub-score, a string-encoded decimal 0–100,
or `null` when the site could not be read. **A site we could not reach is not a
site with a bad technical foundation** — the two must not collapse into one
number, which is why `status: "failed"` exists.

| `status` | Meaning |
|---|---|
| `ok` | Every component measurable |
| `partial` | Read the page, but a component had no signal (e.g. no date anywhere). Scored on what was measurable; `excludedComponents` says which was dropped. |
| `failed` | Could not read the site. `technicalFoundation` is `null`. |

**Core Web Vitals are measured and reported, but carry NO weight in the
sub-score.** `lcpMs` and `cls` are single-cold-load **lab** measurements, not
field data — every CWV check carries `LAB_MEASUREMENT_NOT_FIELD_DATA`. Letting a
noisy measurement move a client-facing score would make the score noisy.
**`inpMs` is always `null`**: INP measures real user interaction latency, and a
crawler that never interacts cannot produce one. Real INP needs CrUX or RUM.

**Scored components and their weights inside Technical Foundation:**
indexation 30, structured data 25, content freshness 25, schema presence 20.
Indexation is heaviest because it is a precondition — a site telling crawlers to
stay out has no foundation whatever its markup looks like. A component with no
signal is excluded and its weight redistributed, exactly as
`Score.excludedDimensions` works.

**Facts only** (ip-safety.md #7). Schema **type names**, presence booleans,
counts, durations and a day count. No page copy, no meta description text, no
Open Graph values — `openGraphTagCount` is a count, and the tags' contents are
never read.

One audit per scan, refreshed on re-run: a scan is a point-in-time claim about a
site, so a second audit is a correction rather than a new observation.

**Errors:** `401`, `404` (unknown scan, or another agency's).

#### `GET /api/v1/scans/{scanId}/audit`
**Auth required.** The scan's audit with checks in display order.
`404` — unknown scan, or *"This scan has not been audited yet."*

#### Effect on scoring

Once an audit exists, `POST /scans/{scanId}/score` includes Technical Foundation
instead of excluding it as `NOT_YET_MEASURED`, and the effective weights return
to §6's table exactly (30/25/20/15/10). A **failed** audit leaves the dimension
excluded — an unreadable site is not a measured zero.

### Report — Epic 7

**Presents; does not compute.** Score, competitor set and audit are read from the

### Action list (generated fixes) — Epic 8

#### `POST /api/v1/scans/{scanId}/fixes`
**Auth required.** Generates the scan's prioritised fix list. `201`.

**Costs one model call.** Which dimension gaps are worth a line, which audit
findings warrant a fix, and in what order — all of that is decided *before* the
call, by the same rules the report client already applies (`derive.ts`:
`gap >= 2`, at most 3 dimension fixes, at most 5 fixes, crawl-blocking checks
promoted). The model words those candidates and judges priority and effort. It
cannot add a recommendation the measurement did not produce: a returned fix whose
`candidateId` matches no candidate is discarded, and `rank` and `pointsUpside`
are always taken from the candidate, never from the response.

**One row per candidate per scan, refreshed on re-run.** A regenerated list is a
better statement of the same measurement, not a second measurement — the same
framing as the technical audit. But `status` belongs to the operator, so it
survives regeneration, and a candidate that has been worked is kept even once it
stops being measured. Enforced by `uq_action_items_scan_source_key`.

**A provider failure writes nothing** and returns `status: "failed"` with a
reason code, leaving any previous list intact. The report still renders its
deterministic fix list in that case, which is a weaker list rather than a wrong
one.

#### `GET /api/v1/scans/{scanId}/fixes`
**Auth required.** The scan's fix list as last generated, in rank order.

Returns an empty list with `status: "empty"` rather than `404` when nothing has
been generated yet: "no fixes yet" is a state of a scan that exists.

### Finding 2 — industry classification confidence is uncalibrated

`Client.industry_confidence_score` is the model's own stated confidence, and
nothing has ever checked it against outcomes. A high score does not mean a
correct label. It is consumed as a threshold in `classify.decide`, so a
miscalibrated score silently changes what gets stored as a classification
rather than as `ambiguous`.

Consequences reach further than Epic 2: a wrong industry seeds SERP queries in
Epic 3, which seeds the competitor set, which feeds Share of Voice in Epic 5.
`CompetitorSet.used_industry_seed` exists specifically so this is answerable
after the fact.

Open because calibrating it needs labelled outcome data this system does not
yet collect. Recorded across `build-log.md` Epics 2.6, 2.8, 3.0, 3.5 and in the
Epic 2 section above.

### Finding 4 — a competitor override destroyed citation and mention attribution

**Fixed in Epic 3.9.** Recorded in full because the register flagged the fix as
possibly needing a product decision, and it turned out not to.

`Citation.competitor_id` and `BrandMention.competitor_id` are the only two FKs
pointing at `competitors.id`, and both are `ON DELETE SET NULL`. Both competitor
write paths used to hard-delete rows — `apply_override` deleted every row before
re-inserting, and `persist_detection` deleted every non-manual row on each run —
so an override *or a re-detection* silently nulled the attribution for the whole
scan. The finding as originally written named only `apply_override`; Epic 3.9
confirmed `persist_detection` had it too and fixed both.

**Both now reuse the row when the rival is unchanged**, keyed on
`slugify(name)` — the key both functions already used for other purposes — with
an `_apply_*` helper shared between the reuse and insert paths, matching the
discipline `scoring_runner` and `audit_runner` use. Keeping the id keeps the
foreign keys.

A struck rival becomes a tombstone **in place** rather than being deleted and
replaced, so its attribution survives too; `active_competitors` still filters it
out, so a citation attributed to a struck rival resolves to no name and presents
as third party. The operator's correction is respected without the underlying
fact being destroyed. `apply_override` is now delete-free entirely.

`persist_detection` still deletes an auto-detected row that the current run did
**not** re-find, and its attribution is nulled with it. That is correct — the
rival has left the set — and it is now the only case where attribution is lost,
where previously every run lost all of it.

**The semantic concern this register raised did not apply.** "Replace the set
wholesale" is a statement about the resulting state — no partial merge, every
submitted row ends up `MANUAL` with signals zeroed — and that is unchanged. Only
the mechanism used to reach it changed. Nothing observable differs: `CompetitorOut`
exposes no `created_at`, and no consumer relies on competitor ids *changing*.

**A second, unrelated defect surfaced while fixing this one**, and is fixed with
it: deleting `Keep` and inserting `Keep` in one flush is a same-table
delete-then-insert on `uq_competitors_set_name`, and SQLAlchemy orders INSERTs
before DELETEs — so **re-running detection on a scan that re-found any rival
returned a 500**, and had since Epic 3. Reuse removes the delete/insert pair, so
the collision cannot arise. Covered by
`test_redetecting_the_same_rival_does_not_500`.

### Finding 5 — `verify_competitors.py` verifies a copy of the detection pipeline

`scripts/verify_competitors.py` is the live check for §7 Epic 3's acceptance
criterion. It calls `detect_for_client` **zero** times. Instead it reassembles
the pipeline itself from `build_queries`, `build_seed_prompts`,
`merge_candidates` and `score_candidates`, and measures that.

So it verifies a copy. If `detect_for_client` drifted from this reassembly — a
new gate, a changed ordering, a different cap — the script would keep reporting
the old behaviour's precision and keep printing PASS. The number it prints is
real (80% at last run, Epic 3.10) but it is a statement about the script's
reconstruction, not about what the API does.

This is the third instance of the same trap in this codebase. Epic 4.0 named it
("a guard that has never been observed to fail is not evidence"); Epic 3.6's
`verify_competitor_override.py` was written against a copy of `apply_override`
and passed against its own copy while the endpoint was still wrong; Epic 3.8's
first fix shipped a negative control that could not fail.

**Fixed in Epic 3.11** by the second option — extracting a database-free core.

**This register was wrong about the cost.** It said the change "is not a small
change" because `detect_for_client` takes a `Client` row. Re-reading the
function for Epic 3.11: it makes **zero** database calls and reads the `Client`
in exactly six places, every one of them a plain scalar (`brand_name`,
`domain`, `industry`, `industry_niche`, `name`, and `id` for a log line). The
ORM object was only ever an awkward way to pass six strings, so the "core" the
register imagined extracting was essentially the whole function.

`detect_from_facts` now holds the body and takes those six scalars;
`detect_for_client` is a thin unpack over it, so no existing caller changed.
The script calls `detect_from_facts` and holds no database connection, keeping
the property the register wanted to protect.

**A correction to the description above, and to Epic 3.10's write-up.** Both
said the script "reassembles the pipeline" and stopped there. It also called
`decide_detection`, with arguments structurally identical to the service's — so
the two were genuinely equivalent, and the 80% precision reported in Epic 3.10
was a sound number. Finding 5 was a **drift risk, not a live incorrectness**,
and saying so plainly matters: the entry as written implied the measurement had
been wrong all along, which would have been a much more serious thing.

`--serp-only` still assembles its own outcome, because `detect_from_facts`
always runs both signals. It now says so in the code rather than leaving a
reader to assume the diagnostic half measured what the API does.

Guarded by `TestDetectionHasOneImplementation`: the wrapper and the core must
return identical outcomes for identical facts; the core must stay free of
`session`/`select`/`commit`/`execute`, which is the property that lets a
database-free script call it; and the wrapper must hold no logic of its own,
since logic there would run in production but not in the script — reopening
this finding silently. Negative-controlled in both directions.

Not re-run live. The full script costs 60 SerpApi searches and 40 model calls,
the change is structurally verified with comments stripped (a naive grep
matches the explanatory comment's own prose, which named the old functions),
and re-spending to watch it print the same 80% was not worth it.

### Finding 6 — no verification script covers the five-dimension scoring path

`scripts/verify_scoring.py` never runs a technical audit, so
`technical_foundation` is always `NOT_YET_MEASURED` and only the degraded
four-of-five-dimension path is exercised. `scripts/verify_audit.py` covers the
audit and the dimension, but on a scan that already has one it measures a
re-audit, not the transition that closes the exclusion.

So since Epic 6 added the fifth dimension, no live script has verified the
complete formula end to end. That is not hypothetical: Epic 3.10 found that
`compute_inputs_digest` had been omitting `technical_foundation` for the same
four epics, and the reason nothing caught it is exactly this gap.

**Not fixed in Epic 3.10** because it needs a scan that is audited *during* the
run rather than before it, which means either `verify_scoring.py` gaining an
audit step (adding a live crawl to a script that is otherwise provider-and-crawl
separable) or a new combined script. Both are design decisions about what each
script is *for*, which is the kind of thing this register exists to hold.

### Finding 3 — `detectionConfidence` describes a mixed competitor set

`CompetitorSet.detection_confidence` is computed as the share of the returned
set that SERP and co-citation surfaced **independently of each other**. It is
therefore a statement about *detected* rows only.

`apply_override` clears it to null, which is correct — an operator's set was
corroborated by nothing. But a subsequent **re-detection** sets it again from
that run's outcome (`services/competitors.py`, `persist_detection`), and that
outcome measured agreement across only the rows detection found. Any manual
rows that survived are not in the calculation. The report then presents a
single corroboration figure for a set that is part-detected, part-hand-set, and
`ReportCompetitorSetOut.detectionConfidence` gives a reader no way to tell.

**Not a bug in the arithmetic** — the number is correct for what it measures.
The defect is that the field's meaning is undefined once a set is mixed, and
the API presents it as though it describes the whole thing.

**Partly closed in Epic 3.11** by the second option: scope it explicitly.

`CompetitorSetOut` and `ReportCompetitorSetOut` now both carry
`confidenceCovers` — the number of rows in the set that detection produced,
which is what the figure is a statement about. Derived from the rows at
projection time via `CompetitorSet.detected_competitors` rather than stored, so
it cannot go stale against the list it counts. The stored value's arithmetic is
untouched; only what the API says about its scope changed.

The report now renders the figure at all, which it never did. That is worth
recording on its own: the note under the competitor table referred the reader
to "the corroboration figure above", and no such figure was ever on the page —
so the copy pointed at nothing for five epics. It now reads "Search results and
AI answers independently surfaced 75% of the 4 rivals detection found. The
remaining 1 of the 5 below were set by hand and are not in that figure."

`confidenceCovers` is deliberately **not** the figure's own denominator, and is
documented as not being it. Detection computes the ratio over every candidate
it ranked, including ones the operator had already named or struck, which are
then held back from the set. The published count is the number of rows a reader
can actually see it apply to, which is the number the report needs.

It is also not a proxy for the confidence being present: a set where only one
signal ran carries a null confidence and a full complement of detected rows,
and a set where re-detection re-found nothing but rivals the operator had
already named carries a real confidence and zero of them.

**Still open: what the field should MEAN on a mixed set.** Scoping it stops the
API overstating what it measured, which was the misleading part. It does not
decide whether Epic 5 should treat a 0.80-over-4-of-6 set as more or less solid
a comparison base than a 0.80-over-6-of-6 one. That is still a scoring-semantics
decision, and the third option — a per-row property — is still the more
principled long-term answer.

Guarded on both projections independently (`TestConfidenceSaysWhatItCovers` and
`TestCompetitorSetScope`), because they are separate schemas built by separate
functions and fixing one would have left the figure misleading in the place a
client actually reads it. Negative-controlled: making either projection count
all active rows fails that projection's tests and only that projection's.

Surfaced by Epic 3.6's competitor-provenance badge, which is what made a mixed
set visible in the first place. `scripts/verify_competitor_override.py` prints
it as a `NOTE` on every run rather than failing, so it stays on the record.
